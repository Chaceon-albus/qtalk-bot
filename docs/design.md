# 设计

总约束见根目录 `AGENTS.md`。本文记录方向、已经定下来的决定和还没定的事。

「已定」一节是用户确认过的；其余各节写的是方向和建议，实现到那一步时先和用户确认细节，不要当成既定事实照着做。已经实现的部分和实现时定下的细节见「实现进度」。

## 目标

- 管理员在聊天里生成邀请链接，经链接添加机器人的用户可以和大模型对话。
- 对用户无感：QQ 与机器人的单聊只有一个会话，不让用户用 `/new`、`/list` 这类命令管理 session，分段与回溯由机器人自己完成。
- 能在 2 核 2G 的机器上跑起来。

要支持的能力，由简到繁：

1. 用户提问，大模型回答。
2. 按消息的性质选模型：先做一次分类，再交给对应类别的模型（例如解决问题用一个，情感支持用另一个）。类别与模型的对应关系是配置出来的列表。
3. 语音输入：模型支持音频就原样给，不支持就先转成文字。
4. 多个输入对应一次提问：一条消息里同时有图片和文字；先发图片或文件，再用文字或语音提问。
5. 话题回溯：聊过 A，又聊了 B、C，再回到 A 时能带上 A 的上下文，同时知道 B、C 的存在。
6. 提醒事项：「提醒我 / 告诉我 / 帮我……」，到点由机器人主动发出。
7. 联网搜索：直接用服务商内置的搜索工具，本项目不自己实现搜索。
8. 展示处理过程：模型思考、搜索时让用户看到进展，类似 ChatGPT 的思考摘要。

## 已定

| 事项 | 决定 |
| --- | --- |
| QQ 侧 | 只经由 pyqbot |
| 部署 | docker compose：机器人本体加其它服务 |
| 密钥 | 环境变量，由 `.env` 经 compose 的 `environment:` 逐项注入，每个服务只拿自己需要的 |
| 静态设置 | TOML 配置文件：模型列表、决策提示、各种时长与配额 |
| 运行时会变的数据 | 数据库：授权名单、邀请令牌、对话与记忆 |
| 大模型调用 | 官方 SDK：`openai`、`google-genai`（这两个依赖已获同意）；每个模型可以配置推理强度 |
| 代理与端点 | 模型侧按服务商配置接口地址与代理（http、https、socks5、socks5h），为此加了依赖 `socksio`；QQ 侧可以改接口地址，代理等 pyqbot 支持后再加 |
| 选模型 | Decisions API；OpenAI 与 Gemini 两家都适配，配置里固定选一家 |
| 记忆 | 自己做「话题线加一次决策调用」，见下文；暂时不引入 Hindsight、mem0 这类外部记忆服务 |
| 联网搜索 | 只用服务商内置的搜索工具。两家的展示条款由用户另行确认，见「查证过的外部事实」的「内置搜索」 |
| 处理过程的展示 | 过程一条消息，回答另起一条；过程消息在 2 分钟内可以撤回，撤回可由配置关闭。见「展示处理过程」 |

同一个值只有一个来源：密钥不进配置文件，配置文件里的设置不再从环境变量覆盖。

暂时不用外部记忆服务的理由：调研到的记忆库存的都是提炼出的事实，没有一个会自动给连续对话分段；服务商自带的会话状态只是一条线性历史；Hindsight 的部署对 2G 的机器太重。以后引入的可能性很低，但不排除。

### 已定要做的功能

除上面八项能力外，这些也从一开始就做，细节实现时再定：

1. **邀请带备注**：创建邀请时填一个备注，兑换后成为该用户的名字，管理、用量、日志都用它。机器人看不到 QQ 号，昵称会改也会重名。
2. **管理员的管理面**：列出和停用用户、撤销邀请、查看用量、临时停机。用斜杠命令直接解析，不经过大模型；可以用 pyqbot 的按钮与自定义菜单做成点按。
3. **用量记账**：从第一条消息开始，每次调用记下用户、模型和 token。配额、限流、成本归因都靠它。
4. **遗忘与查看记忆**：「忘掉这件事」「你都记得我什么」做成模型的工具，用户照常说话即可。
5. **欢迎语与拒绝语**：授权成功时说明能做什么、聊天内容会发给第三方模型、提醒功能需要保持「允许主动发送」。未授权的人只回一次固定的拒绝，不调用大模型。
6. **出错时的表现与备用模型**：调用失败或超时时给用户一句明确的话，不沉默；每个类别可以配一个另一家服务商的备用模型。
7. **数据库的迁移与备份**：表结构从第一版就带版本号和迁移机制，并定时备份。
8. **不支持的消息的兜底**：转发的聊天记录、视频、卡片等先明确回一句「暂不支持」。表情包要单独处理，不能每张都触发看图和回复。
9. **「正在输入」**：模型还没开始输出时发，开始流式输出后就不需要了。pyqbot 已有 `send_typing()`。
10. **给管理员的告警**：机器人掉线、额度用尽等，直接发到管理员的 QQ。

### 不做

| 事项 | 态度 |
| --- | --- |
| 群聊 | 明确不做 |
| 自己实现搜索 | 明确不做，只用服务商内置的工具 |
| 主动关怀 | 暂时不做 |
| 到点执行一个请求 | 已定要做，但以后再做；提醒表先留好字段，见「提醒事项」 |

### 里程碑 1 定下的细节

配置（`src/qtalk_bot/config.py`）：

- 只用标准库：`tomllib` 加冻结的 dataclass，手写校验。
- 密钥的环境变量：`APP_ID`、`APP_SECRET`、`ADMIN_OPENID` 必填，`OPENAI_API_KEY`、`GEMINI_API_KEY` 可选。持有它们的对象在 `repr` 里只显示是否已设置。
- 配置文件的路径由环境变量 `QTALK_CONFIG` 指定，默认是当前目录下的 `config.toml`；文件不存在时报错，不静默用默认值。
- 目前只有两个字段：`timezone`（默认 `Asia/Shanghai`）和 `data_dir`（默认 `data`，相对路径按配置文件所在目录解析）。其它表由各里程碑自己添加。
- 未知的键、类型不符、取值非法都报错，一次列出全部；报错只说键名和原因，不回显任何取值。

存储（`src/qtalk_bot/storage.py`）：

- 标准库 `sqlite3`，数据库文件是 `data_dir` 下的 `qtalk.db`。只有一个连接，所有访问都在一个专用线程里执行，对外是 async 接口。
- 多条语句要原子执行时用 `db.transaction(fn)`：`fn` 是同步函数，在数据库线程里整体执行，中间没有 `await`。
- 表结构由有序的迁移列表维护，版本记在 `PRAGMA user_version`。已发布的迁移只能在末尾追加；迁移不得自行提交或回滚事务；版本高于程序已知的数据库拒绝打开。
- WAL 模式，`synchronous=NORMAL`：断电时可能丢最后几个事务，但不会损坏数据库。
- 新建的数据库和备份文件权限是 `0600`。
- 取消是尽力而为：被取消的数据库操作可能已经执行并提交，调用方不能把取消当作没有发生。

留给部署阶段：`zoneinfo` 依赖系统的时区数据，镜像里没有时要装系统的 tzdata，或者加 `tzdata` 这个依赖。

### 里程碑 2 定下的细节

启动：`uv run --env-file .env python -m qtalk_bot`。配置有误时退出码是 2，数据库有误或连不上平台时是 1，都只打印原因。

模块：

| 模块 | 职责 |
| --- | --- |
| `access.py` | 数据层：同步函数，在调用方的事务里执行 |
| `commands.py` | 管理员命令的解析与执行 |
| `gate.py` | 授权核心，不依赖 pyqbot：输入普通数据，输出「回复什么」或「交给对话处理器」 |
| `chat.py` | 对话处理器的协议 `ChatHandler`，以及上线前的占位实现 |
| `texts.py` | 所有面向用户的固定文案 |
| `bot.py` | 接线层：把 pyqbot 的事件转给 `gate`，再按结果回复 |
| `__main__.py` | 启动入口 |

邀请：

- 邀请码是 32 个十六进制字符，创建时必须带备注（最多 30 个字），兑换后备注成为用户的名字。
- 默认值在 `[invites]`：`ttl_hours`（默认 168，最大 87600）、`max_uses`（默认 1，最大 32）。
- 两条兑换途径共用同一个邀请码：经链接添加机器人（只认 `FRIEND_ADD` 的 `scene_param`），或在单聊里发来一条内容恰好是邀请码的消息。兑换是一个原子操作，是否过期在事务里判断。

谁能用（用户已确认）：

- 管理员只看 `ADMIN_OPENID`。他在用户表里也有一行，方便流水和用量按用户编号记；没有邀请记录、又不是现任管理员的行没有权限，所以更换管理员后旧账号不会保留权限。
- 陌生人只回一次拒绝语，持久化记录，重启后也不重复。
- 发来已失效（过期、撤销、次数用完）的邀请码时每次都回「邀请码已失效」，不占用那一次拒绝。
- 被停用的用户只回一次说明；重新启用后再停用可以再回一次。
- 暂停只影响已授权用户的对话：他们的消息每条都回「暂停中」。陌生人、已停用的人仍按各自的规则处理，兑换邀请不受影响，管理员不受影响。
- 欢迎语里有「聊天内容会发给第三方大模型」的告知。只有确认欢迎语发出后才记下「已告知」；没告知过的用户发来消息时先回欢迎语，这条消息不交给对话处理器。

管理员命令：`/invite <备注>`、`/invites`、`/revoke <编号>`、`/users`、`/disable <编号>`、`/enable <编号>`、`/pause`、`/resume`、`/help`。只对管理员生效，直接解析，不经过大模型。

重复推送与回复失败：

- 每条消息按消息 ID、每次加好友按事件 ID 记进 `processed_events`，与这次处理的全部数据库改动在同一个事务里提交；记过的直接丢弃。记录保留 7 天。
- 代价是「至多一次」：事务提交后、回复发出前进程退出，这次回复就丢了，但不会重复。
- 只有平台明确拒绝时（`bot.is_rejection()`：带错误码的 `APIError`，或 HTTP 4xx）才改发备用文案，并撤销「只回一次」的占位；不确定是否送达时两样都不做。这个判据是按 pyqbot 的实现推出来的，pyqbot 没有现成的标志。

对话处理器：`ChatHandler.handle(user, message)`，`message` 是 pyqbot 的原始消息。放行决定与真正开始处理之间有一个很小的窗口，所以实现者必须在开始有代价的操作之前，在自己的事务里调用 `access.chat_allowed()` 再确认一次。

日志：不记 openid 与消息正文，提到用户时用编号和名字；`httpx2` 的日志压到 WARNING，因为它在 INFO 级别会记下带 openid 的请求地址。

### 里程碑 3 定下的细节

接口：OpenAI 用 Responses API，Gemini 用 Interactions API，都是流式，都关掉服务端存储（`store=False`），历史每次由本地完整带上。SDK 是 `openai` 3.55.1 与 `google-genai` 3.6.1。

模块：

| 模块 | 职责 |
| --- | --- |
| `llm/__init__.py` | 与服务商无关的对话模型接口：请求、消息、流式事件、`ModelError`。不 import 任何 SDK |
| `llm/openai_responses.py`、`llm/gemini_interactions.py` | 两个适配器，SDK 的类型只出现在这里 |
| `llm/providers.py` | 按配置创建模型，同一家服务商共用一个客户端 |
| `conversation.py` | 一轮对话的核心逻辑，不依赖 pyqbot 与 SDK |
| `journal.py` | 消息流水与用量的数据层，所有查询都按用户过滤 |
| `prompt.py` | 拼系统提示词、组装请求 |
| `markdown_guard.py` | 发出前处理模型的输出，对流式的分片边界安全 |

一轮对话：

1. 同一个用户的消息串行处理，不同用户互不阻塞。
2. 一个事务里：用 `access.chat_allowed()` 再确认一次，写入用户消息，取出这个用户最近若干轮。
3. 模型还没开始输出时发「正在输入」；出现非空白的正文后才开始流式消息。
4. 结束后在一个事务里写入：用户实际看到的回复、送达状态、每次模型调用的用量。
5. 这次只处理文字，没有文字的消息回一句「暂时只支持文字」。

上下文是系统提示词加最近 `history_turns` 轮的原文。系统提示词由三部分组成：配置里的人设、一段固定的格式说明（告诉模型 QQ 能渲染什么）、当前时间。

事件接口留了扩展的余地：调用方必须忽略不认识的事件，以后加思考摘要、工具调用前的说明、搜索进展时各加一个事件类型即可；消息内容是若干「部分」，现在只有文字。

出错时：

- 模型调用失败、超时或只给出空白：只要还没有任何内容交给 QQ，并且配置了备用模型，就换备用模型重试一次，调用前再确认一次授权。否则给用户一句固定的说明。
- 流式回复被平台拒绝：把全文改用纯文本的普通消息再发一次，仍然失败就发固定说明。
- 发送出错、说不准是否送达：立即停止读模型，不改发，免得用户收到重复内容。
- 机器人关停时：限时收拢在途的发送，把已确认送达的部分和已知用量写进流水。这是尽力而为，事件循环提前结束时仍会丢。
- 超时按每次模型调用计（`timeout_seconds`），换备用模型时重新计时。

Markdown 的处理：把形如链接、目标却不是 http(s) 地址的那对圆括号换成全角括号，代码块和行内代码里的内容不动。没有用反斜杠转义，因为 QQ 会把 `\(…\)` 当成行内公式。全角括号能否通过平台审核还没有实测。

流水里每条回复有两个状态。`finish` 是模型一侧的结局：

| 取值 | 含义 |
| --- | --- |
| `completed` | 正常写完 |
| `max_tokens` | 达到输出上限 |
| `incomplete` | 其它原因没写完，如内容过滤 |
| `error` | 调用失败或流中途出错 |
| `timeout` | 超过 `timeout_seconds` |
| `empty` | 正常结束，但只有空白 |
| `aborted` | 发送出错后主动停止 |
| `cancelled` | 处理被取消 |
| `skipped` | 根本没有调用对话模型：决策之后发现用户已不能使用 |

`delivery` 是送达状态，`content` 记的总是已确认送达的回答，不含固定说明：

| 取值 | 含义 |
| --- | --- |
| `streamed` | 流式完整送达 |
| `interrupted` | 模型中途出错或超时；已送达的部分后面接了中断说明 |
| `unclosed` | 正文都已确认，结束分片被拒或说不准 |
| `plain` | 流式被拒，改用纯文本送达 |
| `rejected` | 流式和纯文本都被拒，固定说明已送达 |
| `failed` | 模型没给出回答，固定说明已送达 |
| `notice_lost` | 上面两种情况下，固定说明没能确认送达 |
| `uncertain` | 发送回答时出错，说不准送达了多少 |
| `withheld` | 换备用模型前发现用户已不能使用，就此停止 |
| `cancelled` | 处理被取消（关停） |

用量：每次模型调用记一条，含用户、模型的内部名字、当时的服务商与实际的模型名、输入与输出的 token 数。服务商没有返回时记空，不估算；失败的调用也记一条。`/usage` 按用户列出今天和累计的次数与 token 数。

配置（完整的写法见 `config.example.toml`）：

- `[[models]]`：`name`（内部名字）、`provider`（`openai` / `gemini`）、`model`、`default`、可选的 `fallback` 与 `reasoning`。至少一项，恰好一个默认。`reasoning` 原样传给服务商，本地不维护取值表。
- `[chat]`：`persona`、`history_turns`（默认 10）、`max_output_tokens`（默认 8192）、`timeout_seconds`（默认 120）。
- `[providers.openai]`、`[providers.gemini]`：可选的 `base_url` 与 `proxy`。代理支持 http、https、socks5、socks5h，地址不进 `repr`、日志与报错。
- `[qq]`：可选的 `base_url`。QQ 侧的代理等 pyqbot 加上参数后再做。
- 启动时交叉校验：配置里用到哪家服务商，对应的密钥就必须在环境变量里。

环境变量的影响：端点只有两个来源，配置里的 `base_url` 或官方默认值；`OPENAI_BASE_URL`、`GOOGLE_GEMINI_BASE_URL` 这类变量不采用，改走 Vertex、改接口版本的变量也都压住了。`OPENAI_CUSTOM_HEADERS`（SDK 会把它的内容作为附加请求头，还可能顶替鉴权头）没有对应的参数可以关掉，所以程序在创建 OpenAI 客户端之前把它从本进程的环境里去掉，并记一条日志。唯一照常生效的是系统级的代理变量：没配 `proxy` 时由它们决定。

两个要留意的地方：`base_url` 不能带查询串或片段，SDK 和 pyqbot 都是在它后面直接拼路径；Gemini SDK 的配置对象（`HttpOptions`）的 `repr` 里有明文的 API key，那是 SDK 自己放进请求头的，诊断时不要打印它。代理地址交给 SDK 之前包了一层，不会出现在这些 `repr` 里。

SDK 的实际情况，与文档或预期不同的地方：

- Gemini 的 SDK 请求的是 `/v1/interactions`，不是 `v1beta`。
- Gemini 的 SDK 默认会自动续写，一次调用可能拆成多个 HTTP 请求，每次只报告当次的用量，适配器做了累加。关掉服务端存储后每次续写都会重发原始输入，输入会重复计费。
- 两家 SDK 默认都会自动重试，已调低（OpenAI 重试 1 次，Gemini 共 2 次），更多的重试交给备用模型。
- OpenAI 的输出消息带 `phase`，文档说回放历史时要原样带回。现在只存纯文字，没有回传；做过程展示时要处理。

已知的限制：流式回复中途被平台拒绝、改发纯文本成功时，用户会先看到半截消息再看到完整的，流水只记了后者。做过程展示时一轮本来就有多条消息，届时一并设计发送记录。

实测用例在 `tests/live/`，默认不运行：`uv run --env-file .env pytest -m live -s tests/live`，对两家各发一句话，只打印事件种类、字数与用量。

实测记录（2026-11-18，两家各一次，都正常结束）：

| 模型 | 文字增量 | 用量（输入 / 输出） |
| --- | --- | --- |
| `gpt-6.2-sol` | 24 片，共 38 字 | 25 / 30 |
| `gemini-4-hydrogen` | 2 片，共 57 字 | 68 / 336 |

两点观察：Gemini 的增量比 OpenAI 粗得多，一句话只分了两片；Gemini 一句话用了 336 个输出 token，其中大部分是思考（它的默认思考级别是 `high`，用量里输出含思考），日常聊天值得在 `[[models]]` 里把 `reasoning` 调低。

### 里程碑 4 定下的细节

模块：

| 模块 | 职责 |
| --- | --- |
| `llm/decisions.py` | 与服务商无关的决策接口：一次调用问多道题，题型有选择题和是非题。不 import 任何 SDK |
| `llm/openai_decisions.py`、`llm/gemini_decisions.py` | 两个适配器 |
| `routing.py` | 选模型的核心：组装题目、选择规则、失败时的退路、生成决策记录。不碰 SDK 和数据库 |

流程：写入用户消息、取出上下文的事务之后，先发「正在输入」，再做决策，然后调用选出的模型。决策是联网操作，不在数据库事务里。

配置：

- `[decisions]`：不写这个表就不做决策，始终用默认模型。字段是 `provider`（必填）、`model`（默认 `gpt-6-luna` / `gemini-decision-1`）、`instructions`（题面）、`timeout_seconds`（默认 3）、`history_turns`（默认 3）、`switch_margin`（默认 0.2）。
- `[[models]]` 的 `description`：一句话说明这个模型适合回答什么样的消息，就是选择题里这个选项的描述。配置了 `[decisions]` 且模型多于一个时必填。
- 决策模型与同一家的对话模型共用客户端，`[providers.*]` 的接口地址与代理同样生效。
- 这些默认值都还没有实测依据。

选择规则：

- 题目的输入是 JSON：最近几轮对话加当前这条消息，只含这个用户自己的内容。每条历史最多 1000 字，当前消息最多 4000 字，超出的部分截断。
- 取概率最高的模型。它和这个用户上一轮实际回答的模型不同时，只有高出至少 `switch_margin` 才换，否则沿用上一轮的。
- 「上一轮实际回答的模型」取最近一条有文字送达的回复；只发了固定说明的失败轮次不算。
- 只有一个模型时不调用决策。
- 任何失败（超时、网络、HTTP 错误、拒答、安全拦截、坏响应）都不挡住回复：沿用上一轮的模型，没有上一轮就用默认模型。
- 选出的模型调用失败时，换它自己配置的 `fallback`。
- 决策最长要等 `timeout_seconds`，所以决策返回后、调用对话模型之前会再确认一次授权；这时已不能使用的，不调用对话模型，也不再发任何东西，已经发生的决策照常记账。
- 配置了 `[decisions]` 时最多 255 个模型，这是两家选择题选项数的共同上限。

坏响应的判定：两家 SDK 都不校验响应，还会做宽松的转换（漏掉题型时自动补上，布尔值的概率转成 1.0 / 0.0），所以适配器直接按原始 JSON 校验。缺题、题型不对、概率不是 0 到 1 之间的数字、各选项的概率之和与 1 相差超过 0.02（`PROBABILITY_SUM_TOLERANCE`），都算坏响应，走上面的退路。

用量的数字不可信时记空：不是整数、是负数，或单次调用超过 10 亿（`MAX_TOKENS_PER_CALL`）的 token 数，一律当作服务商没有报告，免得写库出错连带回滚整轮的记录。对话和决策两条路径都是如此；Gemini 的输出与思考用量先逐项检查再相加，无效的那一项按未报告处理，用量的问题不会让回答失败。`/usage` 用 SQLite 的 `total()` 汇总，即使库里有绕过检查的异常大数也不会溢出。

决策返回后的授权复查与真正启动对话模型之间仍有一个极小的窗口：管理员的 `/disable` 恰好在这一瞬间提交时，模型仍会启动。它与「停用发生在模型启动后的一瞬间」无法区分，消除它要让管理命令等待进行中的对话，所以接受。

记录：

- `decisions` 表每次决策调用一行：属于哪条用户消息、题目名、服务商与模型、各选项的概率、最终选了谁、是否因 `switch_margin` 沿用了上一轮、耗时、失败时的错误分类。不记题目的输入文本。
- 用量表加了 `purpose` 列（`chat` / `decision`）。`/usage` 的数字包含决策调用，并在后面注明其中有多少是决策。

两家的差别，由适配器抹平：

| | OpenAI | Gemini |
| --- | --- | --- |
| 调用 | `client.decisions.create(...)` | `client.aio.decisions.create(..., api_version="v1beta")` |
| 题目 | 带 `name` 的数组；是非题叫 `predicate` | 以题目名为键的对象；是非题叫 `noul` |
| 选项 | `choices: [{value, description}]` | `criteria: {取值: 描述}` |
| 拒答与拦截 | 单道题返回 `refusal`，其它题照常有答案 | 安全拦截返回 HTTP 400，或响应里带 `prompt_feedback.block_reason` |

Gemini 的 Decisions 在 `v1beta` 下，而对话用的 Interactions 在 `v1` 下，所以决策调用单独指定了接口版本。两家的 SDK 都不校验响应，适配器逐项检查：缺题、题型不对、概率不在 0 到 1 之间都算坏响应。

以后加「属于哪条话题线」这道题时，在同一次请求里再放一道选择题即可，接口和适配器不用动；决策记录本来就是按题目名一道题一行。

实测记录（2026-11-18，两家各连发 5 次同一道选模型的题）：

| 模型 | 耗时（最小 / 中位数 / 最大） | 概率 | 概率之和 | 输入 token |
| --- | --- | --- | --- | --- |
| `gpt-6-luna` | 205 / 227 / 1328 毫秒 | solve 1.000，support 0.000 | 1.0000 | 284 |
| `gemini-decision-1` | 225 / 332 / 440 毫秒 | solve 0.987，support 0.013 | 1.0000 | 245 |

- 题目是先倾诉工作压力、最后一句问 Python 排序，两家都按最后一句选了「解决问题」，五次结果完全一致。
- OpenAI 的第一次是 1.3 秒，之后都在 0.2 秒左右，应是首次建立连接的开销；机器人里客户端常驻复用，平时应接近后者，但空闲久了连接断开后的第一条消息仍会慢一些。默认的 3 秒时限两家都绰绰有余。
- 两家的概率之和都是 1，`PROBABILITY_SUM_TOLERANCE` 的 0.02 不会误伤正常结果。
- 两家都没有输出 token，与文档一致。

## 接入与授权

pyqbot 已有的能力（实测结论见 pyqbot 的 `docs/errata.md`）：

- `generate_share_link(callback_data=...)` 生成邀请链接，`callback_data` 最长 32 个字符。
- 用户经链接添加后，`FRIEND_ADD` 的 `scene_param` 就是 `callback_data`。这时 `scene` 实测是 1000，不是官方文档写的 2003 / 2004，所以只认 `scene_param`。

链接不是门禁：用户还能通过搜索、群、资料页添加机器人。授权是机器人自己存的一张名单，默认拒绝，对应 `AGENTS.md` 的第一条不变量。

已实现，细节见「实现进度」的里程碑 2：

- `callback_data` 用随机的邀请码，在本地记录有效期与可用次数，默认一次性。链接可以被转发。
- 兜底通道：同一个邀请码能在聊天里发给机器人兑换。
- 管理员用环境变量 `ADMIN_OPENID` 标识，机器人看不到 QQ 号。

## 一轮对话

```text
攒批 → 非文本转文字 → 决策 → 组装上下文 → 模型流式回复 → 后台更新摘要与档案
```

- **攒批**：把短时间内的多条输入合成一次提问。带文字或语音的消息稍等片刻再处理；只有图片或文件的消息多等一会儿，没有后续就直接回应它。同一个用户始终串行。
- **文字版**：每个非文本输入存一份文字版（语音转写、图片描述、文件摘要）。当前这轮，选中的模型支持该模态就给原件，否则给文字版。同一话题最近几轮里的图片和文件原样再带上，更早的只带文字版。
- **决策**：一次 Decisions 调用问两道选择题，见「记忆」。
- **回复**：用 pyqbot 的 `reply_stream()` 流式回复，只有单聊支持，且只能是被动回复。

## 记忆

每个用户存三样东西：

- **消息流水**：所有消息原样追加，是唯一的事实来源。
- **话题线**：自动划分的隐式 session，每条有标题、一段摘要和最近活跃时间。
- **用户档案**：几百字的稳定事实，如称呼、偏好、重要的人和事。

每轮的决策调用问两道题：

- **用哪类模型**：选项是配置里的模型列表，每项带一句类别描述。
- **属于哪条话题线**：选项是候选话题线的标题与一句话摘要，外加「新话题」。

Decisions 返回每个选项的概率，上下文按概率组装：

| 内容 | 何时带上 | 形式 |
| --- | --- | --- |
| 用户档案、话题目录（只有标题） | 每次 | 短文本，让模型知道别的话题存在 |
| 全局最近几轮 | 每次 | 原文，兜住「它」「刚才那个」这类指代 |
| 概率最高的话题线 | 每次 | 摘要加该话题最近若干轮原文 |
| 概率次高、超过阈值的话题线 | 拿不准时 | 只带摘要 |

这样一轮的上下文约 5k–8k token。几个候选模型的窗口都在 100 万 token 上下，限制不在窗口而在费用，所以不把整段历史都带上。

Decisions 只能选、不能写。新话题的标题、话题摘要和档案更新交给后台的小模型，在回复之后做，不占用户等待的时间。

用户引用旧消息时，pyqbot 会在 `msg_elements` 里带回被引用的内容，可以直接定位话题，不必靠猜。

### 留给以后的口子

用户要求留出拓展空间。建议守住三条：

- **流水只追加，其余都是可重建的派生数据。** 话题归属、摘要、档案、文字版都能从流水重新算出来，以后换提示词、阈值或算法时可以对历史重跑。唯一的例外是用户要求遗忘：对应的流水要彻底删除，再重建受影响的摘要和档案。
- **每轮存一条决策记录**：候选、各选项的概率、最终选择、带了哪些上下文、耗时与 token。效果不好时靠它查原因，延迟实测的数据也从这里来。
- **三个接口**：决策、对话模型、语音转写，SDK 隔在接口后面。「生成候选话题」与「在候选里选」分成两步，以后可以给前一步加关键词或向量召回。
- **一次回复是若干段内容，不是一个字符串。** 现在只有文字，以后可以加语音或图片形式的回复。
- **工具不一定在本地执行。** 联网搜索由服务商在它那边执行，工具调用的流程不能假设每个工具都有本地的处理函数。

### 已知的薄弱处

都还没有定做法，实现到相应部分时先和用户确认：

1. **候选话题从哪来**：选择题最多 255 个选项，实际只会列最近几十条，很久以前的话题会被判成「新话题」。
2. **新话题的空窗期**：后台还没写出标题和摘要时，下一条消息认不出这条话题。可以先拿首条消息的原文当临时描述。
3. **决策调用失败或被拦**：超时、安全拦截、拒答都可能发生，情感类内容最容易触发。选模型这道题已在里程碑 4 处理（硬超时，失败就沿用上一轮的模型）；话题那道题做的时候同样要有退路。
4. **流水里记什么**：平台可能拒发或流式中途失败，要记用户实际看到的内容，而不是模型生成的内容。
5. **模型来回切换**：两个模型交替回答会像换了个人。已在里程碑 3、4 处理：各模型共用人设，切换要求概率有明显差距（`switch_margin`），跨服务商的历史只存纯文本。
6. **连发消息**：攒批的等待可以和决策调用同时进行；期间来了新消息就取消重来，生成过程中来的排到下一轮。
7. **重复推送**：平台可能重复推送同一条消息，pyqbot 不去重。已在里程碑 2 处理，见「实现进度」。

## 展示处理过程

目标是像 ChatGPT 那样：处理时能看到进展，回答出来后过程不碍事。

已定：

- **过程与回答分成两条消息。** 过程用一条流式消息；回答开始时结束它，另起一条流式消息写回答。
- **过程消息在 2 分钟内撤回**，相当于折叠。超过 2 分钟平台不允许撤回，就留着。撤回可以由配置关闭。

QQ 侧的限制（官方文档快照与 pyqbot 的实测）：

- 消息的 Markdown 没有折叠语法，HTML 标签（如 `<details>`）不生效。
- 流式消息的 `replace` 只能接着已下发的内容往后写，不能删改用户已经看到的部分。过程和回答放在同一条流式消息里时，过程去不掉。
- 流式消息的请求体里没有键盘字段，不能带按钮。
- 撤回只在发出 2 分钟内有效，撤回后聊天里会留下一条撤回提示。
- 流式消息每来一片，手机会轻微震动一次。

建议，未定：

- **撤回的时机**：回答开始时，还是回答结束后。
- **过程只写步骤级的短句**（在查什么、发现了什么），放在引用块里，按步骤更新而不是逐字更新。
- **没有过程就不发过程消息。** 模型直接开始回答时只发「正在输入」。
- **按模型类别配置是否展示**，情感陪伴类默认不展示。
- **回答要能独立成立**，不依赖过程里说过的话。过程的全文存进决策记录，不进后续的上下文。
- 回答开始之后再出现的思考或搜索不再展示，只记录。

过程的内容有三个来源，两家服务商给的形式不同，见「查证过的外部事实」的「思考摘要与过程标记」：思考摘要、调用工具前的说明、搜索的查询词。让模型在调用工具前先说明的提示词（如「我先查一下……」）只适合 OpenAI：它用 `phase` 字段把说明和最终回答分开；Gemini 没有这种标记，官方也不建议强制模型在调用工具前输出文字。

## 提醒事项

建议，未定：

- 自己存一张提醒表，加一个「睡到最近一条到期」的 asyncio 任务，启动时补发已过期的。asyncio 自带定时但重启就丢；APScheduler 4 仍是 alpha，3.x 要持久化就得带上 SQLAlchemy。
- 时间解析交给主模型，把「设置提醒」做成工具，对所有模型类别开放；回复里复述解析出的时间，方便用户纠正。
- 到点发出的是主动消息：用户在资料卡关掉「允许主动发送」就会失败，要在用户下次发言时补上。

提醒有两种，区别在于到点时要不要再调用一次模型：

- **到点发一句话**：「8 点提醒我吃药」，到点发出事先定好的内容。第一版做这种。
- **到点执行一个请求**：「明早 8 点告诉我今天的天气」，内容在设定时还不存在，到点要让模型带着工具跑一轮再发出结果。已定要做，但以后再做。它只能作为主动消息发出，不能流式。

提醒表里先留好区分这两种的字段。

## 其它待定

- **配额的具体规则**：每个用户的每日上限、全局预算。工具执行时的用户身份取自当前会话，不取模型给的参数。
- **时间感**：上下文里标注当前时间，以及距上次对话过了多久。
- **数据去留**：用户删除好友后数据保留多久，附件的磁盘清理。
- **情感类的风险处置**：涉及自伤等内容时走固定的模型与回应方式，不交给路由决定。
- **每个模型类别各自的上下文组装方式**：情感陪伴更依赖档案和最近的对话，不像一个个话题。
- **提示词**放在 TOML 里还是独立文件。
- **`/users`、`/invites` 的分页**：现在把全部结果拼成一条消息，用户多了会超出单条消息的长度。
- **「平台明确拒绝」的判据**：现在按 pyqbot 的实现推断，更稳的做法是让 pyqbot 在 `APIError` 上直接给出这个标志。

## 需要实测

实测前按 `AGENTS.md` 先取得用户同意。

- 收到语音、图片、文件时的真实字段，附件地址的有效期，单聊里能不能收到文件。
- 表情包以什么形式到达：文本里的标记，还是图片附件。
- 单聊消息里的昵称字段有没有值。官方示例里是空串，pyqbot 的样本里有值，但可能是脱敏后的占位。
- 单条消息的长度上限，长回复要不要拆条。
- 邀请链接放进消息里能不能发出。
- 已是好友的人点邀请链接、机器人离线时有人添加，这两种情况会不会收到 `FRIEND_ADD`。
- 同一条用户消息能不能先后回两条流式消息。
- 流式消息能不能撤回，2 分钟从哪一片算起。单聊里撤回后会留下一条撤回提示（pyqbot 实测过普通消息）。
- 回答里带任意网站的引用链接时，平台会不会拒发。
- `gpt-6.2-sol` 是否返回思考摘要与 `phase`，账号是否需要先通过组织验证。

### QQ 平台

出处是 pyqbot 的 `docs/errata.md` 与官方文档快照：

- 单聊被动回复的有效期约 60 分钟，实测 55 分钟后仍能回复。
- 同一条消息实测能先发「正在输入」再被动回复 4 条。
- Markdown 里形如链接、目标却不是 URL 的文字会被判「消息内容违规」（40034006），大模型的输出要先处理。
- 语音附件带 `voice_wav_url`（转成 WAV 后的地址）与 `asr_refer_text`（识别的参考文本）。pyqbot 已有这两个字段，没有实测过。
- 单聊主动消息的官方限额是每个用户每天 1000 条。用户切换资料卡里的开关时，平台推的是 `type` 18 的互动事件。
