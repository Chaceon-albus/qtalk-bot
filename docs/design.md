# 设计

总约束见根目录 `AGENTS.md`。本文记录方向、已经定下来的决定和还没定的事。

「已定」一节是用户确认过的；其余各节写的是方向和建议，实现到那一步时先和用户确认细节，不要当成既定事实照着做。已经实现的部分和实现时定下的细节见「实现进度」。

## 目标

- 管理员在聊天里生成邀请链接，经链接添加机器人的用户可以和大模型对话。
- 对用户无感：QQ 与机器人的单聊只有一个会话，不让用户用 `/new`、`/list` 这类命令管理 session，分段与回溯由机器人自己完成。
- 能在 2 核 2G 的机器上跑起来。

要支持的能力，由简到繁：

1. 用户提问，大模型回答。
2. 按消息的性质选模型：先做一次分类，再交给对应类别的模型（例如解决问题用一个，情感支持用另一个）。类别与模型的对应关系是配置出来的列表。
3. 语音输入：模型支持音频就原样给，不支持就先转成文字。
4. 多个输入对应一次提问：一条消息里同时有图片和文字；先发图片或文件，再用文字或语音提问。
5. 话题回溯：聊过 A，又聊了 B、C，再回到 A 时能带上 A 的上下文，同时知道 B、C 的存在。
6. 提醒事项：「提醒我 / 告诉我 / 帮我……」，到点由机器人主动发出。
7. 联网搜索：直接用服务商内置的搜索工具，本项目不自己实现搜索。
8. 展示处理过程：模型思考、搜索时让用户看到进展，类似 ChatGPT 的思考摘要。

### 已定要做的功能

除上面八项能力外，这些也从一开始就做，细节实现时再定：

1. **邀请带备注**：创建邀请时填一个备注，兑换后成为该用户的名字，管理、用量、日志都用它。机器人看不到 QQ 号，昵称会改也会重名。
2. **管理员的管理面**：列出和停用用户、撤销邀请、查看用量、临时停机。用斜杠命令直接解析，不经过大模型；可以用 pyqbot 的按钮与自定义菜单做成点按。
3. **用量记账**：从第一条消息开始，每次调用记下用户、模型和 token。配额、限流、成本归因都靠它。
4. **遗忘与查看记忆**：「忘掉这件事」「你都记得我什么」做成模型的工具，用户照常说话即可。
5. **欢迎语与拒绝语**：授权成功时说明能做什么、聊天内容会发给第三方模型、提醒功能需要保持「允许主动发送」。未授权的人只回一次固定的拒绝，不调用大模型。
6. **出错时的表现与备用模型**：调用失败或超时时给用户一句明确的话，不沉默；每个类别可以配一个另一家服务商的备用模型。
7. **数据库的迁移与备份**：表结构从第一版就带版本号和迁移机制，并定时备份。
8. **不支持的消息的兜底**：转发的聊天记录、视频、卡片等先明确回一句「暂不支持」。表情包要单独处理，不能每张都触发看图和回复。
9. **「正在输入」**：模型还没开始输出时发，开始流式输出后就不需要了。pyqbot 已有 `send_typing()`。每次只请求几秒，有进展时再请求，像真人一样输一会、停一会（细节见 7b）。
10. **给管理员的告警**：机器人掉线、额度用尽等，直接发到管理员的 QQ。

### 里程碑 1 定下的细节

配置（`src/qtalk_bot/config.py`）：

- 只用标准库：`tomllib` 加冻结的 dataclass，手写校验。
- 密钥的环境变量：`APP_ID`、`APP_SECRET`、`ADMIN_OPENID` 必填，`OPENAI_API_KEY`、`GEMINI_API_KEY` 可选。持有它们的对象在 `repr` 里只显示是否已设置。
- 配置文件的路径由环境变量 `QTALK_CONFIG` 指定，默认是当前目录下的 `config.toml`；文件不存在时报错，不静默用默认值。
- 目前只有两个字段：`timezone`（默认 `Asia/Shanghai`）和 `data_dir`（默认 `data`，相对路径按配置文件所在目录解析）。其它表由各里程碑自己添加。
- 未知的键、类型不符、取值非法都报错，一次列出全部；报错只说键名和原因，不回显任何取值。

存储（`src/qtalk_bot/storage.py`）：

- 标准库 `sqlite3`，数据库文件是 `data_dir` 下的 `qtalk.db`。只有一个连接，所有访问都在一个专用线程里执行，对外是 async 接口。
- 多条语句要原子执行时用 `db.transaction(fn)`：`fn` 是同步函数，在数据库线程里整体执行，中间没有 `await`。
- 表结构由有序的迁移列表维护，版本记在 `PRAGMA user_version`。已发布的迁移只能在末尾追加；迁移不得自行提交或回滚事务；版本高于程序已知的数据库拒绝打开。
- WAL 模式，`synchronous=NORMAL`：断电时可能丢最后几个事务，但不会损坏数据库。
- 新建的数据库和备份文件权限是 `0600`。
- 取消是尽力而为：被取消的数据库操作可能已经执行并提交，调用方不能把取消当作没有发生。

留给部署阶段：`zoneinfo` 依赖系统的时区数据，镜像里没有时要装系统的 tzdata，或者加 `tzdata` 这个依赖。

### 里程碑 2 定下的细节

启动：`uv run --env-file .env python -m qtalk_bot`。配置有误时退出码是 2，数据库有误或连不上平台时是 1，都只打印原因。

模块：

| 模块 | 职责 |
| --- | --- |
| `access.py` | 数据层：同步函数，在调用方的事务里执行 |
| `commands.py` | 管理员命令的解析与执行 |
| `gate.py` | 授权核心，不依赖 pyqbot：输入普通数据，输出「回复什么」或「交给对话处理器」 |
| `chat.py` | 对话处理器的协议 `ChatHandler`，以及上线前的占位实现 |
| `texts.py` | 所有面向用户的固定文案 |
| `bot.py` | 接线层：把 pyqbot 的事件转给 `gate`，再按结果回复 |
| `__main__.py` | 启动入口 |

邀请：

- 邀请码是 32 个十六进制字符，创建时必须带备注（最多 30 个字），兑换后备注成为用户的名字。
- 默认值在 `[invites]`：`ttl_hours`（默认 168，最大 87600）、`max_uses`（默认 1，最大 32）。
- 两条兑换途径共用同一个邀请码：经链接添加机器人（只认 `FRIEND_ADD` 的 `scene_param`），或在单聊里把邀请码发给机器人。兑换是一个原子操作，是否过期在事务里判断。
- 在单聊里兑换时，未授权用户的消息里只要恰好包含一个邀请码（32 位十六进制，前后不紧挨字母数字）就算，这样对方把整段邀请原样发回来也能兑换；包含两个以上不同的码时不兑换。已授权用户和管理员的消息不受这条影响。
- 创建邀请时发两条：给管理员的一行状态（编号、备注、有效期、可用次数），和一条可以直接转发给对方的纯文本邀请，开头是「邀请您来和{机器人名}聊聊天！」，下面是链接与邀请码。机器人名在启动时经 `get_me()` 取得，取不到时写「这个机器人」。链接没能生成或被平台拒绝时，邀请里只留邀请码。

谁能用（用户已确认）：

- 管理员只看 `ADMIN_OPENID`。他在用户表里也有一行，方便流水和用量按用户编号记；没有邀请记录、又不是现任管理员的行没有权限，所以更换管理员后旧账号不会保留权限。
- 陌生人只回一次拒绝语，持久化记录，重启后也不重复。
- 发来已失效（过期、撤销、次数用完）的邀请码时每次都回「邀请码已失效」，不占用那一次拒绝。
- 被停用的用户只回一次说明；重新启用后再停用可以再回一次。
- 暂停只影响已授权用户的对话：他们的消息每条都回「暂停中」。陌生人、已停用的人仍按各自的规则处理，兑换邀请不受影响，管理员不受影响。
- 欢迎语里有「聊天内容会发给第三方大模型」的告知。只有确认欢迎语发出后才记下「已告知」；没告知过的用户发来消息时先回欢迎语，这条消息不交给对话处理器。

管理员命令：`/invite <备注>`、`/invites`、`/revoke <编号>`、`/users`、`/disable <编号>`、`/enable <编号>`、`/pause`、`/resume`、`/usage`、`/help`。只对管理员生效，直接解析，不经过大模型。`/help` 与几个列表用 Markdown 发送，备注和名字经 `texts.escape_markdown()` 转义（圆括号、方括号换成全角，其余特殊字符加反斜杠，换行换成空格）；平台明确拒绝时改发纯文本。单句的提示仍是纯文本。

重复推送与回复失败：

- 每条消息按消息 ID、每次加好友按事件 ID 记进 `processed_events`，与这次处理的全部数据库改动在同一个事务里提交；记过的直接丢弃。记录保留 7 天。
- 代价是「至多一次」：事务提交后、回复发出前进程退出，这次回复就丢了，但不会重复。
- 只有平台明确拒绝时（`bot.is_rejection()`：pyqbot 异常的 `outcome_unknown` 为假）才改发备用文案，并撤销「只回一次」的占位；不确定是否送达时两样都不做。`outcome_unknown` 为真的是请求发出后的网络错误、HTTP 5xx（不论有没有错误码）、没有错误码的 2xx/3xx 异常响应、`AuditPendingError`（已受理、等待审核）与 `PartialFailureError`（部分已生效）；为假的是带错误码的 2xx/3xx/4xx、HTTP 4xx、建连阶段的错误、取 access_token 失败。5xx 一律算说不准，比早先「带错误码就算拒绝」保守。所有用到「确定没发出 / 说不准」的地方（这里的备用文案与占位、对话的改发纯文本与停读、固定说明的送达状态）都经同一个判据（`bot._send_error()` 把它转成 `SendRejectedError` / `SendUncertainError`）。

对话处理器：`ChatHandler.handle(user, message)`，`message` 是 pyqbot 的原始消息。放行决定与真正开始处理之间有一个很小的窗口，所以实现者必须在开始有代价的操作之前，在自己的事务里调用 `access.chat_allowed()` 再确认一次。

日志：不记 openid 与消息正文，提到用户时用编号和名字；`httpx2` 的日志压到 WARNING，因为它在 INFO 级别会记下带 openid 的请求地址。

### 里程碑 3 定下的细节

接口：OpenAI 用 Responses API，Gemini 用 Interactions API，都是流式，都关掉服务端存储（`store=False`），历史每次由本地完整带上。SDK 是 `openai` 3.55.1 与 `google-genai` 3.6.1。

模块：

| 模块 | 职责 |
| --- | --- |
| `llm/__init__.py` | 与服务商无关的对话模型接口：请求、消息、流式事件、`ModelError`。不 import 任何 SDK |
| `llm/openai_responses.py`、`llm/gemini_interactions.py` | 两个适配器，SDK 的类型只出现在这里 |
| `llm/providers.py` | 按配置创建模型，同一家服务商共用一个客户端 |
| `conversation.py` | 一轮对话的核心逻辑，不依赖 pyqbot 与 SDK |
| `journal.py` | 消息流水与用量的数据层，所有查询都按用户过滤 |
| `prompt.py` | 拼系统提示词、组装请求 |
| `markdown_guard.py` | 发出前处理模型的输出，对流式的分片边界安全 |

一轮对话：

1. 同一个用户的消息串行处理，不同用户互不阻塞。
2. 一个事务里：用 `access.chat_allowed()` 再确认一次，写入用户消息，取出这个用户最近若干轮。
3. 模型还没开始输出时发「正在输入」；出现非空白的正文后才开始流式消息。
4. 结束后在一个事务里写入：用户实际看到的回复、送达状态、每次模型调用的用量。
5. 这次只处理文字，没有文字的消息回一句「暂时只支持文字」。

上下文是系统提示词加最近 `history_turns` 轮的原文。系统提示词由三部分组成：配置里的人设、一段固定的格式说明（告诉模型 QQ 能渲染什么）、当前时间。

事件接口留了扩展的余地：调用方必须忽略不认识的事件，以后加思考摘要、工具调用前的说明、搜索进展时各加一个事件类型即可；消息内容是若干「部分」，现在只有文字。

出错时：

- 模型调用失败、超时或只给出空白：只要还没有任何内容交给 QQ，并且配置了备用模型，就换备用模型重试一次，调用前再确认一次授权。否则给用户一句固定的说明。
- 流式回复被平台拒绝：把全文改用纯文本的普通消息再发一次，仍然失败就发固定说明。
- 发送出错、说不准是否送达：立即停止读模型，不改发，免得用户收到重复内容。
- 机器人关停时：限时收拢在途的发送，把已确认送达的部分和已知用量写进流水。这是尽力而为，事件循环提前结束时仍会丢。
- 超时按每次模型调用计，换备用模型时重新计时。（时限已改成空闲与总共两段，见「对话的输出上限与时限」。）

Markdown 的处理：把形如链接、目标却不是 http(s) 地址的那对圆括号换成全角括号，代码块和行内代码里的内容不动。没有用反斜杠转义，因为 QQ 会把 `\(…\)` 当成行内公式。全角括号能否通过平台审核还没有实测。

流水里每条回复有两个状态。`finish` 是模型一侧的结局：

| 取值 | 含义 |
| --- | --- |
| `completed` | 正常写完 |
| `max_tokens` | 达到输出上限 |
| `incomplete` | 其它原因没写完，如内容过滤 |
| `error` | 调用失败或流中途出错 |
| `timeout` | 超过空闲时限或总时限 |
| `empty` | 正常结束，但只有空白 |
| `aborted` | 发送出错后主动停止 |
| `cancelled` | 处理被取消 |
| `skipped` | 根本没有调用对话模型：决策之后发现用户已不能使用 |

`delivery` 是送达状态，`content` 记的总是已确认送达的回答，不含固定说明：

| 取值 | 含义 |
| --- | --- |
| `streamed` | 流式完整送达 |
| `interrupted` | 模型中途出错或超时；已送达的部分后面接了中断说明 |
| `unclosed` | 正文都已确认，结束分片被拒或说不准 |
| `plain` | 流式被拒，改用纯文本送达 |
| `rejected` | 流式和纯文本都被拒，固定说明已送达 |
| `failed` | 模型没给出回答，固定说明已送达 |
| `notice_lost` | 上面两种情况下，固定说明没能确认送达 |
| `noticed` | 没有送达任何回答，但附件的说明已确认送达（例如说完「附件没能下载」之后被取消）；算作结束了一轮 |
| `uncertain` | 发送回答时出错，说不准送达了多少 |
| `withheld` | 换备用模型前发现用户已不能使用，就此停止 |
| `cancelled` | 处理被取消（关停） |

用量：每次模型调用记一条，含用户、模型的内部名字、当时的服务商与实际的模型名、输入与输出的 token 数。服务商没有返回时记空，不估算；失败的调用也记一条。`/usage` 按用户列出今天和累计的次数与 token 数。

配置（完整的写法见 `config.example.toml`）：

- `[[models]]`：`name`（内部名字）、`provider`（`openai` / `gemini`）、`model`、`default`、可选的 `fallback` 与 `reasoning`。至少一项，恰好一个默认。`reasoning` 原样传给服务商，本地不维护取值表。
- `[chat]`：`persona`、`history_turns`（默认 10）、`max_output_tokens`（默认 8192）、`timeout_seconds`（默认 120）。后两项已按「对话的输出上限与时限」修改：`max_output_tokens` 默认不设，时限分成 `idle_timeout_seconds`（默认 300）与 `timeout_seconds`（默认 1800）。
- `[providers.openai]`、`[providers.gemini]`：可选的 `base_url` 与 `proxy`。代理支持 http、https、socks5、socks5h，地址不进 `repr`、日志与报错。
- `[qq]`：可选的 `base_url` 与 `proxy`。代理的校验与写法同 `[providers.*].proxy`，原样传给 `pyqbot.Bot(proxy=...)`，作用于开放平台的接口请求、网关的 WebSocket 与经 `bot.http_client` 的附件下载；不设时系统级的代理变量照常生效。地址不进本项目的 `repr`、日志与报错，pyqbot 也保证账号密码不出现在它的 `repr`、日志与异常里（有测试）。
- 启动时交叉校验：配置里用到哪家服务商，对应的密钥就必须在环境变量里。

环境变量的影响：端点只有两个来源，配置里的 `base_url` 或官方默认值；`OPENAI_BASE_URL`、`GOOGLE_GEMINI_BASE_URL` 这类变量不采用，改走 Vertex、改接口版本的变量也都压住了。`OPENAI_CUSTOM_HEADERS`（SDK 会把它的内容作为附加请求头，还可能顶替鉴权头）没有对应的参数可以关掉，所以程序在创建 OpenAI 客户端之前把它从本进程的环境里去掉，并记一条日志。唯一照常生效的是系统级的代理变量：没配 `proxy` 时由它们决定。

两个要留意的地方：`base_url` 不能带查询串或片段，SDK 和 pyqbot 都是在它后面直接拼路径；Gemini SDK 的配置对象（`HttpOptions`）的 `repr` 里有明文的 API key，那是 SDK 自己放进请求头的，诊断时不要打印它。代理地址交给 SDK 之前包了一层，不会出现在这些 `repr` 里。

SDK 的实际情况，与文档或预期不同的地方：

- Gemini 的 SDK 请求的是 `/v1/interactions`，不是 `v1beta`。
- Gemini 的 SDK 默认会自动续写，一次调用可能拆成多个 HTTP 请求，每次只报告当次的用量，适配器做了累加。关掉服务端存储后每次续写都会重发原始输入，输入会重复计费。
- 两家 SDK 默认都会自动重试，已调低（OpenAI 重试 1 次，Gemini 共 2 次），更多的重试交给备用模型。
- OpenAI 的输出消息带 `phase`，文档说回放历史时要原样带回。现在只存纯文字，没有回传；做过程展示时要处理。

已知的限制：流式回复中途被平台拒绝、改发纯文本成功时，用户会先看到半截消息再看到完整的，流水只记了后者。做过程展示时一轮本来就有多条消息，届时一并设计发送记录。

实测用例在 `tests/live/`，默认不运行：`uv run --env-file .env pytest -m live -s tests/live`，对两家各发一句话，只打印事件种类、字数与用量。

实测记录（2026-11-18，两家各一次，都正常结束）：

| 模型 | 文字增量 | 用量（输入 / 输出） |
| --- | --- | --- |
| `gpt-6.2-sol` | 24 片，共 38 字 | 25 / 30 |
| `gemini-4-hydrogen` | 2 片，共 57 字 | 68 / 336 |

两点观察：Gemini 的增量比 OpenAI 粗得多，一句话只分了两片；Gemini 一句话用了 336 个输出 token，其中大部分是思考（它的默认思考级别是 `high`，用量里输出含思考），日常聊天值得在 `[[models]]` 里把 `reasoning` 调低。

### 里程碑 4 定下的细节

模块：

| 模块 | 职责 |
| --- | --- |
| `llm/decisions.py` | 与服务商无关的决策接口：一次调用问多道题，题型有选择题和是非题。不 import 任何 SDK |
| `llm/openai_decisions.py`、`llm/gemini_decisions.py` | 两个适配器 |
| `routing.py` | 选模型的核心：组装题目、选择规则、失败时的退路、生成决策记录。不碰 SDK 和数据库 |

流程：写入用户消息、取出上下文的事务之后，先发「正在输入」，再做决策，然后调用选出的模型。决策是联网操作，不在数据库事务里。

配置：

- `[decisions]`：不写这个表就不做决策，始终用默认模型。字段是 `provider`（必填）、`model`（默认 `gpt-6-luna` / `gemini-decision-1`）、`instructions`（题面）、`timeout_seconds`（默认 3）、`history_turns`（默认 3）、`switch_margin`（默认 0.2）。
- `[[models]]` 的 `description`：一句话说明这个模型适合回答什么样的消息，就是选择题里这个选项的描述。配置了 `[decisions]` 且模型多于一个时必填。
- 决策模型与同一家的对话模型共用客户端，`[providers.*]` 的接口地址与代理同样生效。
- 这些默认值都还没有实测依据。

选择规则：

- 题目的输入是 JSON：最近几轮对话加当前这条消息，只含这个用户自己的内容。每条历史最多 1000 字，当前消息最多 4000 字，超出的部分截断。
- 取概率最高的模型。它和这个用户上一轮实际回答的模型不同时，只有高出至少 `switch_margin` 才换，否则沿用上一轮的。
- 「上一轮实际回答的模型」取最近一条有文字送达的回复；只发了固定说明的失败轮次不算。
- 只有一个模型时不调用决策。
- 任何失败（超时、网络、HTTP 错误、拒答、安全拦截、坏响应）都不挡住回复：沿用上一轮的模型，没有上一轮就用默认模型。
- 选出的模型调用失败时，换它自己配置的 `fallback`。
- 决策最长要等 `timeout_seconds`，所以决策返回后、调用对话模型之前会再确认一次授权；这时已不能使用的，不调用对话模型，也不再发任何东西，已经发生的决策照常记账。
- 配置了 `[decisions]` 时最多 255 个模型，这是两家选择题选项数的共同上限。

坏响应的判定：两家 SDK 都不校验响应，还会做宽松的转换（漏掉题型时自动补上，布尔值的概率转成 1.0 / 0.0），所以适配器直接按原始 JSON 校验。缺题、题型不对、概率不是 0 到 1 之间的数字、各选项的概率之和与 1 相差超过 0.02（`PROBABILITY_SUM_TOLERANCE`），都算坏响应，走上面的退路。

用量的数字不可信时记空：不是整数、是负数，或单次调用超过 10 亿（`MAX_TOKENS_PER_CALL`）的 token 数，一律当作服务商没有报告，免得写库出错连带回滚整轮的记录。对话和决策两条路径都是如此；Gemini 的输出与思考用量先逐项检查再相加，无效的那一项按未报告处理，用量的问题不会让回答失败。`/usage` 用 SQLite 的 `total()` 汇总，即使库里有绕过检查的异常大数也不会溢出。

决策返回后的授权复查与真正启动对话模型之间仍有一个极小的窗口：管理员的 `/disable` 恰好在这一瞬间提交时，模型仍会启动。它与「停用发生在模型启动后的一瞬间」无法区分，消除它要让管理命令等待进行中的对话，所以接受。

记录：

- `decisions` 表每次决策调用一行：属于哪条用户消息、题目名、服务商与模型、各选项的概率、最终选了谁、是否因 `switch_margin` 沿用了上一轮、耗时、失败时的错误分类。不记题目的输入文本。
- 用量表加了 `purpose` 列（`chat` / `decision`）。`/usage` 的数字包含决策调用，并在后面注明其中有多少是决策。

两家的差别，由适配器抹平：

| | OpenAI | Gemini |
| --- | --- | --- |
| 调用 | `client.decisions.create(...)` | `client.aio.decisions.create(..., api_version="v1beta")` |
| 题目 | 带 `name` 的数组；是非题叫 `predicate` | 以题目名为键的对象；是非题叫 `noul` |
| 选项 | `choices: [{value, description}]` | `criteria: {取值: 描述}` |
| 拒答与拦截 | 单道题返回 `refusal`，其它题照常有答案 | 安全拦截返回 HTTP 400，或响应里带 `prompt_feedback.block_reason` |

Gemini 的 Decisions 在 `v1beta` 下，而对话用的 Interactions 在 `v1` 下，所以决策调用单独指定了接口版本。两家的 SDK 都不校验响应，适配器逐项检查：缺题、题型不对、概率不在 0 到 1 之间都算坏响应。

以后加「属于哪条话题线」这道题时，在同一次请求里再放一道选择题即可，接口和适配器不用动；决策记录本来就是按题目名一道题一行。

实测记录（2026-11-18，两家各连发 5 次同一道选模型的题）：

| 模型 | 耗时（最小 / 中位数 / 最大） | 概率 | 概率之和 | 输入 token |
| --- | --- | --- | --- | --- |
| `gpt-6-luna` | 205 / 227 / 1328 毫秒 | solve 1.000，support 0.000 | 1.0000 | 284 |
| `gemini-decision-1` | 225 / 332 / 440 毫秒 | solve 0.987，support 0.013 | 1.0000 | 245 |

- 题目是先倾诉工作压力、最后一句问 Python 排序，两家都按最后一句选了「解决问题」，五次结果完全一致。
- OpenAI 的第一次是 1.3 秒，之后都在 0.2 秒左右，应是首次建立连接的开销；机器人里客户端常驻复用，平时应接近后者，但空闲久了连接断开后的第一条消息仍会慢一些。默认的 3 秒时限两家都绰绰有余。
- 两家的概率之和都是 1，`PROBABILITY_SUM_TOLERANCE` 的 0.02 不会误伤正常结果。
- 两家都没有输出 token，与文档一致。

### 里程碑 5a 定下的细节

模块：

| 模块 | 职责 |
| --- | --- |
| `media.py` | 附件的种类与状态、按文件头识别格式、文字版、本地存放、下载、过期清理 |
| `context.py` | 判断模型能否接收某个附件、按本轮附件筛候选、按模型能力组装请求 |
| `describe.py` | 后台给图片写一句话描述 |

一条带附件的消息的流程：

1. 接线层把 pyqbot 的附件转成本项目的数据。被引用消息里的图片也算（最多往下看 3 层），卡片和转发的聊天记录记为「不支持」。每条消息最多处理 16 个附件。
2. 确认授权后才下载，而且只下有模型用得上的种类。下载经 pyqbot 的 `bot.http_client`，有大小上限和时限；整个进程最多同时下载 4 个。
   - **目的地**：不自动跟随重定向，自己逐跳处理（最多 3 次），每一跳都检查：只认 http(s)、不带用户信息、主机不是 IP 字面量、主机属于 QQ 的下载域名白名单（`qq.com`、`qq.com.cn`、`ugcimg.cn`、`qpic.cn`、`gtimg.cn`，与形态日志共用）。重定向的正文不读。这份白名单是按 2026-11-18 的实测样本和官方文档里的示例整理的，平台的下载主机与域名随时可能变化：
     - 内置的列表在 `bot.PLATFORM_HOSTS`；配置的 `[attachments].extra_download_hosts` 可以追加域名后缀（不替换内置的），下载与形态日志共用合并后的列表。
     - 下载因主机的问题被拒时（不在白名单、是 IP、不是合法的域名，含重定向的每一跳），给管理员发一条提醒：合法域名写主机名，其余只写类别，并注明是哪个用户；不含完整链接、路径、端口和文件名。同一个域名 24 小时内只提醒一次。
   - **不带凭证**：下载请求只有地址，不继承共享客户端的默认请求头、Cookie、查询参数，也不带鉴权头。
   - **边写边数**：按块写进这个用户目录下的临时文件，内存里只留识别格式用的文件头，超过上限就停；识别通过后改名成正式文件。
   - **不收 Cookie**：pyqbot 靠请求头里的 token 鉴权，不用 Cookie，所以启动时给共享客户端装了拒收所有 Cookie 的策略（`refuse_cookies()`），附件服务器设的 Cookie 不会被带到 QQ 的接口请求里。
   - **落盘不用线程**：建临时文件、写盘（每次最多 256 KiB）、关闭、改名、删除都直接在事件循环里同步做，只有网络读取是异步的。这样取消只会发生在网络读取上，每一步文件操作要么做完、要么没开始，描述符只关一次。早先用线程做文件操作时，评审接连找出被取消的写盘线程把数据写进另一个用户的文件、排队中的操作被撤掉导致槽位不归还等问题，所以换成了这种写法；代价是磁盘异常慢时会短暂阻塞事件循环，附件放在本机的 `data/`，可以接受。
   - **已知的限制**：白名单只看主机名，不做 DNS 解析，白名单内的域名若被解析到内网地址（DNS 重绑定）拦不住。要彻底解决需要在连接层校验对端地址，暂时不做。pyqbot 的建议：以后给下载单独配一个校验对端地址的 transport 或客户端（不再与接口请求共用 `bot.http_client`）；走 `socks5h` 代理时域名由代理解析，本地校验不到对端地址。
3. 按文件头判断实际格式：PNG、JPEG、GIF、WebP、HEIC、HEIF、PDF、WAV。平台声明的类型只作初判；认不出的当作不支持，不保存。
4. 存到 `data_dir/attachments/<用户编号>/<随机名>.<扩展名>`，目录 0700、文件 0600。读文件时一律先按「用户编号 + 消息」查附件表，路径解析后必须仍在这个用户的目录里。
5. 写流水（用户消息另存引用索引 `msg_idx`），按本轮附件筛候选模型，必要时先发一条说明，再选模型、组装请求。
6. 回复之后，在后台给本轮的图片写描述。

模型的输入能力（`[[models]].inputs`）：

- 取值是 `image`、`audio`、`file` 的子集，不写就是只收文字。
- OpenAI 的模型不能写 `audio`：Responses API 不接受音频输入（SDK 与文档一致），所以语音对 OpenAI 的模型一律用 QQ 的识别文本。这和最初「模型支持音频就原样给」的设想不同。
- 两家对格式与大小的限制写在 `llm.INPUT_LIMITS`：OpenAI 收 PNG、JPEG、WebP 和 PDF，内联合计 50 MB；Gemini 收 PNG、JPEG、WebP、HEIC、HEIF、WAV 和 PDF，整个请求 20 MB（留 1 MB 给文字）。
- GIF 一律不给模型：OpenAI 只收非动图，本地判断不了是不是动图。

选模型时的能力筛选：

- 必须照顾的是本轮的图片和 PDF：取能接收其中最多的那些模型为候选；一个也接收不了时，候选是全部模型。「能接收」按整轮的内联预算算（`fit()`）：按附件顺序依次放进这家服务商的预算，放不下的不算；候选评分、备用模型、给用户的说明与组装请求都以它为准。
- 每次调用决策、主模型、备用模型之前（发说明、读文件这些等待都结束之后），以及后台每写一张图的描述之前，都在事务里复查一次授权。
- 语音不强制要求音频能力，但候选里有能接收本轮全部语音的模型时，只在它们之中选。
- 候选只剩一个时不调用决策；上一轮的模型不在候选里时，`switch_margin` 不适用。
- 备用模型要能接收选中模型能接收的那些图片和 PDF，否则不换它。
- 没有候选能处理时：图片退回文字版并告诉用户这次看不了；PDF 回「暂不支持」；本轮只剩看不了的内容时只发说明、不调用模型。

内存：整个进程同时最多 3 个会读原件的模型请求（`MULTIMODAL_REQUESTS`），覆盖从读文件、编码到模型回复结束；一次请求里同一份内容会有两三份拷贝，3 个同时在途约占四五百 MiB，给 2G 的机器留出余量。不带附件的请求不受限。

上下文：本轮按选中模型的能力给原件或文字版；还没有回复的用户消息（例如上次关停时留下的）并入本轮，参加候选筛选；给用户的说明以最终的请求为准（实际给了原件的才算），组装时按实际读到的字节扣预算，最终的请求里没有可答内容时只发说明、不调用模型；历史里最近 `[attachments].history_turns` 轮的图片在模型能接收、文件还在时给原件，其余一律文字版；语音和文件在历史里只给文字版。文字版放在方括号里，如「[图片：描述]」「[语音] 识别文本」「[文件：名字，PDF，1.2 MB]」，系统提示词里告诉模型方括号里是附件的说明。

一轮的定义改成「连续的若干条用户消息加上之后的回复」，没有回复的用户消息并进下一轮，为 5b 的攒批做准备。一条回复只有在用户实际收到东西时才算结束了一轮（`journal.ends_turn()`）：正文不为空，或确认送达了固定说明；正文为空的取消、跳过、送达不明等回复行不算，它们回复的消息仍属于下一轮的输入。历史先找到最近一个边界再限量，所以连来很多条只收到说明的消息也不会挤掉上一轮完整的问答。

图片描述（`[describe]`）：同时最多 2 个任务，描述压成一行、最长 300 字；失败只记日志；用量记进用量表，`purpose` 为 `describe`；关停时被取消的保持「待写」，重启后不补。

清理：启动时一次，之后每小时一次。先把超过保存期限的附件行标为 `expired` 并删文件；再删孤儿文件——附件表没有引用、且存在超过一小时的文件，覆盖各种取消路径下没来得及删的文件。`MediaStore.remove_user()` 留给以后的「遗忘」和删除用户。

关停：

- 程序自己接管 SIGINT 与 SIGTERM（`docker stop` 发的是 SIGTERM）：第一次收到就开始有序关停，之后再收到只记一条「正在关停，请稍候」，不打断收尾。Windows 上不接管。
- 顺序（当时的写法，已被后文取代，现行的见 5b 的「关停顺序」）：`Bot.close()` 取消前台的处理函数 → 等对话自己跟踪的在途轮次收尾并记账（`Conversation.drain()`，因为 pyqbot 只等处理函数 5 秒）→ 向清理、图片描述、下载发出停止请求 → 限时等它们收尾 → 关模型客户端与数据库。
- 等待部分对再次取消有抵抗力，总时限 15 秒，超时记一条警告继续关停；那时仍没写完的记账会丢。

迁移 V4：按 SQLite 的做法重建用量表，`purpose` 加上 `describe`；`messages` 加 `msg_idx`；新表 `attachments`。

配置：`[[models]].inputs`、`[attachments]`（`max_size_mb` 20、`download_timeout_seconds` 30、`retention_days` 30、`history_turns` 3）、`[describe]`（`provider`、`model` 必填）。这些默认值都还没有实测依据。

### 第二次 QQ 实测后的修正

- **表情一律忽略**：`faces.clean()` 直接删掉 `<faceType=…>` 标记，不再换成「[表情]」。只由表情组成的消息（`faces_only = 1`，包括只有标记的小黄脸）照常记进流水、正文存空串，但在 SQL 里就被排除：不进本轮、不进历史、不进决策输入、不占 32 条的名额、不触发回复；一批的最后一条是表情时，回复挂在最后一条非表情的消息上。
- **PDF 前后一致**：
  - PDF 也在后台写摘要，与图片描述共用 `[describe]` 的模型与流程（并发、授权复查、受保护的记账、关停收尾）；只有这家服务商收 PDF、且大小在内联上限内时才写。摘要最多 600 字，存进附件表的 `description`。
  - 附件表的 `given` 列记录这一轮**实际**以原件放进请求的附件，与回复写在同一个事务里：这一轮按 `ends_turn()` 结束了（用户收到了回答或说明，包括正文送达后才被取消的），就按结束这一轮的那次请求重记这一轮所有附件——在那次请求里给了原件的设 1，其余设 0（换了备用模型以备用模型为准）；没有结束这一轮的都设 0。历史里「原图／原声／原文在当时那一轮已经给过你」只在 `given = 1` 时才写，后面接描述、识别文字或摘要；没有记录的照旧用当时的文字版。主模型收了原件但出错、又没有可换的备用模型时，也算给过。
  - 系统提示词告诉模型：历史里写着原件当时给过你的，不要否认看过。
- **语音按内容选模型**：去掉了「本轮有语音时只在能听的模型里选」的规则，语音不影响候选。决策用 Gemini 时把本轮的语音原声（WAV）连同题目一起交给它（`DECISION_INPUT_LIMITS`：OpenAI 的决策什么媒体都不收，Gemini 只收 WAV，19 MiB 以内）；用 OpenAI 时只看题目里的识别文字。选中能听的模型给原声，选中听不了的给识别文字。没有识别文字、但原声已下载的语音，和图片、PDF 一样算必须照顾的附件：候选（与备用模型）要能听它，免得同批的文字让听不了的模型把它「答掉」。带语音的决策从读原声到结束都占一个多模态名额。
- 迁移 V6（Python 函数）：附件表加 `description`、`given`；从旧的文字版里回填已写好的图片描述；V5 误记为「只有表情」的带附件消息改回普通消息，并去掉 V5 生成的「[表情]」字样；V4 时期带原始标记的表情包重新识别为「只有表情」并清空正文。

### 里程碑 5c 定下的细节

取代 5b 按固定时长攒批的做法（用户实测反馈：文字等 2.5 秒来不及打下一条，图片等 12 秒也常常不够）。QQ 平台没有「用户正在输入」的事件，机器人看不到用户是否在打字，所以只能按消息到达来决定。

- **文字和语音立即处理**；`[turns].text_debounce_seconds`（默认 0）可以设一个短防抖来接住快速的连发。
- **单独的图片或文件不触发回复**，等下一条文字或语音，一起作为一轮。从最后一张附件到达算起，过了 `attachment_wait_seconds`（默认 60，最大 1800，因为发问或回答是对原附件消息的被动回复、平台的有效期是 60 分钟；0 表示一直等）还没有下文，按 `attachment_timeout_action` 处理：`ask`（默认）发一句「收到 2 张图片，想让我帮你看什么？」，不调用模型，也不写进流水（否则会结束这一轮）；`answer` 直接回答；`none` 什么都不做。同一组附件只做一次。
- **插话（steer）只在一轮回答进行中考虑**：
  - 回答还没开始显示（还没有任何东西交给 QQ，包括附件说明与固定说明）时来了新的文字或语音：用一道是非题决策（题目名 `steer`，`routing.STEER_INSTRUCTIONS`）判断它是在补充当前的问题，还是一个新问题。补充（概率不低于 0.5），或判断失败、没有配置 `[decisions]`：打断当前的生成，带上新消息重来，每轮最多 `max_restarts` 次（默认 3）。新问题：等当前这一轮答完再答。
  - **回答已经开始显示时也判断**（用户 2026-11-19 QQ 实测后决定：长回答显示期间补的一句要等它写完才答，实测等了约 3 分钟）。判为补充、回答的流式消息已经开始、模型还在写：停下这段回答，在已送达的部分后接一句「收到补充，这段回答先停在这里」并正常结束流式消息，按已送达的部分写回复行（结局 `steered`，送达状态 `interrupted`），这一轮照常结束（话题归属、摘要照常）；新消息紧接着作为下一轮，回复挂在它上面（它有自己的被动回复次数）。QQ 的流式消息只能追加、不能撤回，已显示的部分留着。停下不算重来，不占 `max_restarts`，也不受重来名额的限制。
  - 显示中判为新问题，或判断失败、没有配置 `[decisions]`：不停，排到下一轮。代价不对等：还没显示时重来几乎没有代价，显示到一半停下会丢掉一段可能有用的回答，没配决策时每条插话都会打断回答。
  - 只显示了固定说明（附件说明等）、回答的流式消息还没开始，或已经在改发纯文本、发固定说明，或模型已经写完只剩发送收尾：不停，排到下一轮。
  - 判断期间回答开始显示了、结论是补充：按显示中的规则尝试停下这段回答（以前是打断不成功、排到下一轮）。
  - `max_restarts` 为 0 时完全不考虑插话；已达到重来上限，或这一轮里已有一条判为新问题之后，不再判断，新消息排到下一轮。
  - 停下的方式与时限相同：标记后取消读流的任务，只有没有别的取消在进行时才动手，所以与时限至多一个生效；关停或发送出错后停读的取消优先，结局分别记 `cancelled`、`aborted`，都不接说明。停下之后关闭响应流卡住时（时限的看门任务这时已不再管），最多等 3 秒（`GRACE_SECONDS`）就不再等它，免得这一轮收不了尾、补充开不了轮（评审修正）。判为补充却停不下的（见上），这一轮里之后的消息也不再判断。
- 回答停在围栏代码块里时，接任何说明（中断、没写完、停下）之前先补上闭合围栏的那一行，免得说明被渲染进代码块；闭合行算回答的一部分，与接「来源」之前的处理相同（随显示中插话一起修正，此前只有「来源」会先闭合）。
  - 回答进行中到达的单独附件不触发判断：重来时一并带上，否则等下一条文字。
- 重来的名额按这一轮实际带上的待回复消息算（含重启后遗留的），一轮最多 32 条：只有触发打断的那条消息连同它之前到达的消息都装得进重来的请求时才打断，装不下就不打断、排到下一轮，免得重来时挤掉最早的消息或漏掉那条补充。判断插话时看到的也是这一轮实际带上的消息。
- 开轮之前先等这批消息都收完、复查完；接收时没通过复查的文字不会把等待中的附件带着开轮。整条队列里有文字就算有下文，开轮时仍按到达顺序一次最多带 32 条。
- 被打断的生成不写回复行、不改 `given`，这一轮的用户消息仍是待回复的，由重来的那一轮带上。被打断的模型调用与插话判断照常记用量与决策记录（插话判断挂在新消息的最后一条上，`chosen` 为 `supplement` 或 `new`）。
- 「正在输入」在一轮开始时发；重来时距上次实际发出不到一个脉冲就不再发（脉冲见 7b 的「正在输入」）。
- 配置表从 `[batching]` 改名为 `[turns]`。

### 里程碑 6a 定下的细节

用户 2026-11-19 确认：

- **只在配置了 `[decisions]` 时启用。** 不配就和现在一样：不分话题，上下文是最近 `[chat].history_turns` 轮。
- **候选话题**：这个用户最近活跃的 `[topics].candidates` 条（默认 20），外加「新话题」。更久以前的话题会被判成新话题，以后再加关键词或向量召回。一条候选也没有时不问，直接开新话题。
- **一次决策问两道题**：选模型与选话题放在同一次 Decisions 调用里，共用 `[decisions].timeout_seconds`。插话判断仍然单独做。话题选项的描述是标题加摘要的开头。
- **新话题的空窗期**：后台还没写出标题时，用首条消息的前 40 字当临时标题。
- **话题题失败**（超时、拒答、拦截、坏响应）：沿用这个用户最近活跃的话题；一条都没有就开新话题。
- **按引用定位**：用户引用了自己的旧消息或机器人回复他的消息时，按存下的 `msg_idx` 只在这个用户自己的流水里找；找到且那条消息有话题，就直接用那个话题，话题题不问（模型题照问）。机器人回复的 `msg_idx` 是回答送达后存下的引用索引（见下文「按引用定位到机器人的回复」）；拿不到索引的回复定位不了，照常交给决策。
- **上下文组装**（按时间排列、去重）：
  - 话题目录：最近活跃的 `[topics].directory` 条（默认 20）的标题，不含当前话题，让模型知道别的话题存在；
  - 不分话题的最近 `[topics].recent_turns` 轮原文（默认 3），兜住「它」「刚才那个」这类指代；
  - 选中话题的摘要，加上它最近 `[chat].history_turns` 轮原文（不分话题时这个数就是最近几轮，两种情况含义一致）；
  - 第二可能的已有话题概率不低于 `[topics].second_threshold`（默认 0.25）时，再带上它的摘要；
  - 6a 之前的消息不回填话题，只经「不分话题的最近几轮」出现。
- **话题归属是派生数据**：存在单独的表里，流水仍然只追加，以后可以重算。一轮结束时（`ends_turn()`）与回复写在同一个事务里：这一轮的用户消息与回复都归到选中的话题，新话题在这时建行；被插话打断的那次不写。
- **后台写标题与摘要**：`[memory]` 表，写法同 `[describe]`（`provider`、`model`、可选的 `reasoning`、时限、输出上限、提示词）。每轮结束后在后台更新这一轮话题的标题与摘要：输入是旧摘要加上次摘要之后的各轮文字版，输出新的标题与摘要。同一个用户依次处理，排着的合并成一次。调用前在事务里复查授权；用量记账，用途是 `memory`；日志不记标题与摘要的内容。不配 `[memory]` 时只有临时标题、没有摘要。
- **推理强度**：`[memory]` 与 `[describe]` 都在后台运行，不占用户等待的时间，可以把 `reasoning` 调高（gpt-6-luna 接受 `none`、`low`、`medium`、`high`、`xhigh`、`max`，默认 `medium`，2026-11-19 查自官方模型页）；代价是费用更高、新话题的空窗期更长。用户等待路径上的 gpt-6-luna 只有 Decisions，而 Decisions API 没有推理强度的参数。

第一步（不含后台写标题与摘要）实现时定下的细节：

- 模块：`topics.py` 是话题表与归属的数据层（候选、按引用定位、建行与归属、留给下一步的 `set_summary()`）；话题里各轮的原文由 `journal.topic_history()` 取；选话题在 `routing.py`（`TopicQuery`、`choose_topic()`），与选模型同一个 `Selection`；合并历史在 `context.merge_history()`，记忆一段在 `prompt.Memory`。
- 启用：`Router(..., topics=settings.topics)`，没有 `[decisions]` 或没有决策模型时 `Router.topics` 为空，`Conversation` 据此判断是否分话题，不另设开关。启用后即使只有一个模型，也会为话题题调用决策。
- 迁移 V9：`messages.ref_msg_idx`（被引用消息的引用索引，按 `(user_id, msg_idx)` 建了索引）；新表 `topics`（`provisional_title`、`title`、`summary`、`summarized_through`、`created_at`、`active_at`、`last_message_id`）与 `topic_messages`（消息 → 话题，带 `user_id`）。「最近活跃」按 `last_message_id`（归进来的最后一轮的回复编号）排序，不按时刻：时钟可能回拨，同一秒里也会有好几轮。
- 引用的来源（已实测，见 pyqbot 的 `docs/errata.md`）：先取 pyqbot 的 `message.ref_msg_idx`（`message_scene.ext` 里的 `ref_msg_idx=`），没有时由本项目回退到 `msg_elements` 第一项的 `msg_idx`（pyqbot 不做这个回退）；超过 512 个字符的当作没有。实测四次都对上：引用机器人的普通消息时 `ref_msg_idx` 等于发送结果的 `ext_info.ref_idx`，引用流式消息时等于 `StreamMessage.ref_idx`，引用用户自己的消息时等于那条消息的 `msg_idx`；`msg_elements` 只有被引用的那一项，它的 `msg_idx` 与 `ref_msg_idx` 相同，所以回退只是兜底。一轮里有几条消息带引用时，从最新的一条看起，第一个找得到话题的为准。
- **按引用定位到机器人的回复**（改用 pyqbot 的 `StreamMessage.ref_idx` 之后）：回答送达后，把送达回答的那条消息的引用索引存进它在流水里那一行的 `messages.msg_idx`。流式回答取 `StreamMessage.ref_idx`（pyqbot 实测：每个分片的响应，含结束分片，都带同一个 `ext_info.ref_idx`；仍在每个成功的分片与结束分片之后都看一次，第一个不为空的为准）；流式被拒、改发纯文本的取发送结果的 `ext_info.ref_idx`；拿不到就留空，超过 512 个字符的也当作没有。只有回答的那条消息存：固定说明（模型失败、平台拒发后的说明）与过程消息都不存。`conversation.ReplyChannel` 的 `stream()`、`finish_stream()`、`send()` 改为返回发出的那条消息的引用索引（替身返回 `None` 即可），`conversation.py` 仍不依赖 pyqbot。`topics.quoted_topic()` 去掉了「只认用户消息」的条件，仍只在这个用户自己的流水里找，所以机器人回复别人的消息的索引解析不到（有测试）。
- 话题题：选项取值是话题编号（十进制）与 `new`，描述是「标题：摘要的前 120 字」（压成一行，没有摘要时只有标题）；题面是 `routing.TOPIC_INSTRUCTIONS`。两家的官方文档都没有对选项描述设实际的长度上限（OpenAI 的字段上限是 1 MiB；Gemini 没写，受 262,144 token 的总上下文约束），120 字只为控制费用。题目的输入与选模型共用（最近 `[decisions].history_turns` 轮加当前消息）。
- 「第二可能的话题」是除选中的以外概率最高的已有话题（不含「新话题」）；选中「新话题」时就是概率最高的已有话题。它的摘要为空时（6a 第一步一律为空）什么都不带。
- 决策记录：话题题一行，题目名 `topic`，`probabilities` 的键是话题编号与 `new`，`chosen` 同理；话题题失败时 `chosen` 是退回的话题。同一次调用的两道题共用一行决策用量。被取消时问了的题各记一行 `cancelled`。
- 上下文：决策之后在一个事务里复查授权、取出选中话题的上下文，不能使用就停下（`withheld`）；历史是「不分话题的最近几轮」与「选中话题最近几轮」按消息去重、按对话位置排列，「往前数第几轮」按合并后的各轮重算（只收到说明、没有正文的回复不在历史里，它前后的用户消息会被算成同一轮）。系统提示词在当前时间之前加一段：历史只是相关片段（`prompt.TOPIC_GUIDE`）、当前话题的摘要、相关话题的摘要、目录（标题列表，不含当前话题）。
- 归属：一轮按 `ends_turn()` 结束了才写，含只收到附件说明（`noticed`）的轮次；选「新话题」或话题已不属于这个用户（防御）时建行，临时标题取这一轮各条用户消息文字版（正文加附件标记，同决策题目里的写法）用空格连起来的前 40 字，全是空白时写「（无文字）」。归属里混进别人的消息编号时只归这个用户自己的。
- 日志只记话题编号与概率，不记标题与摘要。
- 坏响应改为逐题（评审修正）：适配器只在整次确实失败时抛错（HTTP 错误、超时、整体结构不对、缺题、多题、重名）；某一道题的答案不合法（题型不对、缺选项、概率不合法）只把那一道标成 `llm.decisions.Malformed`，与拒答一样是逐题的结果，其余照常返回。每一道都坏时仍按整次的坏响应抛出，所以只问一道题时（插话判断、只问模型或只问话题）行为与之前相同。`Router` 按逐题结果分别记账、分别走退路，只有整次失败时两道题才记同一个错误。这修正了里程碑 4「坏响应整次作废」的说法。

第二步（后台写标题与摘要）实现时定下的细节：

- 模块 `memory.py`（`Summarizer`），写法照 `describe.py`：后台任务、真正调用之前在事务里复查授权、受保护的记账、`stop()` / `aclose()` 收尾。接在 `__main__.py` 的关停顺序里，与 `Describer` 并列（第 6、7 步）。关停只取消一次（评审修正）：`aclose()` 在已经 `stop()` 过时只等待、不再取消，免得打断模型响应流被第一次取消后的异步关闭；`Describer.aclose()` 同样改了。
- 配置 `[memory]`：`provider`、`model` 必填；`reasoning` 默认不传；`timeout_seconds` 默认 120（最大 600）；`max_output_tokens` 默认不设；`instructions` 默认题面写在 `config.DEFAULT_MEMORY_INSTRUCTIONS` 与示例里。只在配置了 `[decisions]` 时生效；有 `[memory]` 没有 `[decisions]` 时不报错，忽略它并在启动时记一条警告（同 `[topics]`），也不要求它的服务商的密钥。模型与同一家的对话模型共用客户端（`ChatModels.memorizer`）。
- **后台任务默认不设输出上限**（用户 2026-11-19 决定：后台用 gpt-6-luna 的任务几乎不花钱）：`[describe]` 的 `max_output_tokens`、`file_max_output_tokens` 与 `[memory]` 的 `max_output_tokens` 都改成可选，不写就不向服务商传（`llm.ChatRequest.max_output_tokens` 可以为空，OpenAI 不带 `max_output_tokens`，Gemini 的 `generation_config` 里不带 `max_output_tokens`），由模型自己的上限兜底，失控时由 `timeout_seconds` 兜底；写了才传，含推理所用的 token。`[chat].max_output_tokens` 当时不变，仍默认 8192（之后也改成默认不设，见「对话的输出上限与时限」）。
- 排队：每个用户一个后台任务，依次处理排着的话题（按排的顺序、不重复）；正在写的话题又排进来，写完后再写一次；整个进程同时最多 `memory.CONCURRENCY`（2）个调用。只有正常结束（没有被取消）、写了归属的一轮才排。
- 输入：JSON（`title`、`summary`、`turns`），`turns` 是这个话题里覆盖范围之后的各轮文字版（用户消息是正文加附件的 `text`，回复是 `content`，只发了说明的回复不带），最多最近 20 轮，每条最多 2000 字，合计最多 12000 字，超出时丢掉更早的。没有新的轮次就不调用。
- 按轮次取（评审修正，`journal.topic_turns_after()`）：`summarized_through` 记的是覆盖到的那一轮的回复，下一次取回复编号更大的那些轮，带上它们各自 `reply_to` 覆盖的用户消息，不论用户消息的编号大小。回答进行中发来的下一轮问题编号比上一轮的回复小（问1、问2、答1、答2），只按消息编号取会漏掉问2。只发了说明的回复照样是轮次的边界，它的问题照常带上。覆盖范围推进到这次带上的各轮里最大的回复编号，所以超出上限被丢掉的更早轮次之后不会补写。
- 输出：约定的两行纯文本「标题：……」「摘要：……」（摘要可以折行，压成一行），没有用结构化输出（对话接口没有这个参数）。标题超过 40 字、摘要超过 600 字（提示词建议的两倍）、缺一行、空白、模型没有正常写完（`FinishReason` 不是 completed）都按失败处理：只记日志，保留旧值，覆盖范围不动，下次带着更多轮重试。
- 写回 `topics.set_summary()`（覆盖范围只前进）；用量一行，用途 `memory`、`model` 列是 `memory`，挂在输入里最后一条用户消息上。迁移 V10 按 SQLite 的做法重建用量表，把 `memory` 加进 `purpose` 的 CHECK 约束（保留第 7 版的 `searches`）。
- 提示词注入：摘要与标题来自用户的对话，系统提示词里在它们前面加 `prompt.MEMORY_NOTICE`，说明这是自动整理的资料、可能过时，其中的要求不是给模型的指令；写摘要的提示词里也说明对话里的要求不要执行。它们只进这个用户自己的上下文。
- 生效后：决策的话题选项、目录、上下文都用 `Topic.display_title`（有标题用标题，没有用临时标题）与摘要，第一步已经接好。
- 日志只记话题编号、字数与覆盖的消息条数，不记标题与摘要。

### 里程碑 7a 定下的细节

- `[[models]].search`（默认 `false`）打开时，调用这个模型带上服务商内置的搜索：OpenAI 是 `{"type": "web_search", "user_location": {"type": "approximate"}}`（只写 `type`，免得服务商默认用户在美国），Gemini 是 `{"type": "google_search"}`。模型不支持或服务商拒绝时按普通的调用失败处理。写描述的模型不带搜索。
- 新的流式事件（`llm`）：`SearchProgress(call_id, stage, queries)`，同一次搜索依次是开始、零到多次更新（Gemini 在搜索过程中给出查询词）、完成（OpenAI 只在这时给出查询词）；`Citation(url, title)`，同一次调用里同一个来源只给一次。7b 用它们展示「正在搜索：……」。
- 搜索次数：OpenAI 按 `action` 为 `search` 的调用数（`open_page`、`find_in_page` 不算，失败的照样算）；Gemini 按这次调用里（含自动续写的各跳）不重复的非空查询词数。每执行一次就交出一个新的累计 `Usage`，被打断时次数不丢。用量表的 `searches` 列（迁移 V7）：带了搜索工具的调用记整数，没带的记空；`/usage` 显示今天和累计的搜索次数。
- 「来源」（`citations.py`）：回答有正文时，在正文之后、中断说明之前追加，最多 5 条，按规整后的链接去重。每条是 Markdown 链接：链接只接受 `http(s)://主机`、不带用户信息、主机是 ASCII 且不是 IPv6 字面量、不超过 500 字符，主机之后的括号、引号等特殊字符与非 ASCII 字符做百分号编码；标题压成一行、超过 60 字截断、没有标题时用主机名，再经 `escape_markdown()` 转义。它算进用户实际看到的内容；改发纯文本时写成「标题 链接」。
- Gemini 的「搜索建议」（一段 HTML）忽略，不发给用户；这与它的条款不符，用户知情并决定照常打开。
- 日志不记查询词与引用的链接，只记次数。
- 还没确认的：平台会不会拒发带任意网站链接的消息；Gemini 用量里的 `total_tool_use_tokens`（工具结果的 token）是否计费，现在没有计入输入；两家计费口径的细节（OpenAI 的 `open_page` 是否收费、Gemini 的查询去重范围）。

### 里程碑 7b 定下的细节

- `[[models]].show_process`（默认 `false`）打开时，这个模型另发一条流式消息展示过程。
- **不请求、不展示思考摘要**（用户 2026-11-19 决定）：实测两家的摘要都很稀疏、标题都是英文，提示词也改不了它的语言（见「搜索与过程展示的模型实测」）。适配器保留请求摘要的能力（`summaries` 参数与事件 `ThoughtSummary`，只供实测使用），收到了也不展示、不存档。
- 过程的来源：OpenAI 消息项 `phase` 为 `commentary` 的文字（新事件 `Commentary`，**一律不进回答**，不论是否展示）、7a 的搜索进展。文字增量里不带 `phase`，按 `output_item.added` 记下的消息项编号分流。Gemini 没有这种标记，它的文字一律算回答。
- 过程消息的格式（`process.py`）：**纯文本**（流式消息的 `content_type=text`），每步一行、行间不空行，不做 Markdown 转义（用户 2026-11-19 QQ 实测后决定；最初是每步一段 Markdown 引用，但流式消息结束之前客户端把 `>` 原样显示，过程消息又要一直开到回答开始）。每步最多 40 字、最多 12 步；两次更新至少隔 2 秒，期间的变化合并。没有过程内容时不发。
- 搜索写成进度式的一行（同上，用户决定）：开始时新起一行「正在搜索🔍」，得知查询词后在同一行接一个空格和查询词（多个用「、」连），如「正在搜索🔍 上海 今天 天气、上海 明天 天气」；不写「搜索完成」。流式消息只能追加，所以只有这一行仍是最后发出的内容时才接在后面，否则新起一行「正在搜索🔍 查询词」。这一行发出之前就已知道查询词的（开始与完成落在同一次更新里），直接写成完整的一行；还没发出就完成、又没有查询词的（打开网页等）整行去掉。每次搜索各占一行，即使与上一行相同也不合并（用户 2026-11-19 补充：不要几次搜索挤在一行里）；说明仍然是与上一行完全相同时不重复写。
- 回答开始显示（或要发说明、改发纯文本）时结束过程消息，之后的说明与搜索只存档不展示。**过程消息之后一直留着，不撤回**（用户 2026-11-19 决定）：pyqbot 实测 QQ 的流式消息撤回不了，见「查证过的外部事实」的「QQ 平台」。最初做过「回答送达后、发出不到 105 秒时撤回」与配置项 `[process].recall`，已随这个决定删掉（`[process]` 表出现时按未知的表报错）。
- 过程消息不算「回答已开始显示」，所以插话照常可以打断；被打断时给它写一行「收到补充，重新开始」并结束，它和重来后的过程消息一样留着，全文由最后答完的那一次一起存档。
- 被动回复次数的预算：每条被回复的消息由对话一侧统一计数（「正在输入」、普通消息、每条流式消息算一次），开过程消息前要给回答留出 2 次，并且回复不超过 4 次、连「正在输入」不超过 5 次（按官方说法与 pyqbot 的实测取保守值）；不够就不发过程消息。
- 过程全文存进回复行的 `process` 列（迁移 V8），不用于组装请求。
- 提示词（`prompt.py`）：打开 `show_process` 的模型加一句「最终回答要能独立成立，不要指向过程」；OpenAI 且开了搜索的模型再加一句「搜索前用一句话说要查什么，查完说一句发现了什么」。
- OpenAI 的推理摘要可能要求组织验证：带摘要的请求被 4xx（401、429 除外）拒绝时不带摘要重试一次，重试被接受才在本次运行期间对这个模型停用摘要。现在不请求摘要，这条只在实测时用到。
- 自己重放历史时没有带回 OpenAI 的 `phase`（历史里只有最终回答）。
- OpenAI 的 `phase` 在 `output_item.added` 时就已给出（2026-11-19 实测：三个消息项分别是 `commentary`、`commentary`、`final_answer`，`added` 与 `done` 一致），所以按 `added` 分流即可，不需要暂存。万一某个消息项在 `added` 时没有 `phase`，它的文字按回答处理。
- **「正在输入」是一个个短脉冲**（用户 2026-11-19 决定）：每次只请求 8 秒（`TYPING_PULSE_SECONDS`），在有进展时再请求一次——一轮开始时、真正开始调用对话模型时（含插话重来、换备用模型之后的那次）、还没有任何内容交给 QQ 期间模型流里出现新的阶段时（一次搜索开始、一段调用工具前的说明开始）。没有进展时（如 OpenAI 隐藏的长时间推理）上一次到期就自然停下，不让用户以为一直在打字。
  - 前提全部满足才发：过程消息、回答、附件说明都还没交给 QQ；距上一次实际发出至少 8 秒（时刻记在 `TurnControl.typed_at`，插话重来时接着用）；这条消息发「正在输入」不到 3 次（`process.MAX_TYPINGS`）；发完仍给回答，以及这一轮还可能发的过程消息（含备用模型的）留足被动回复的余量。
  - 过程消息与回答的第一片等在途的「正在输入」发完再发，免得「正在输入」晚于内容到达。一轮结束或被打断时取消还在途的，限时等它们收尾。
- 需要实测：引用段落的渲染；8 秒的「正在输入」脉冲用起来是否自然。同一条用户消息先后回两条流式消息已由 pyqbot 实测确认可行，流式消息撤回不了（见「查证过的外部事实」的「QQ 平台」）。

### 对话的输出上限与时限

用户 2026-11-19 决定，向 ChatGPT app 看齐：它在 Thinking 模式下不在模型之外另设单条回答的输出上限（总上下文 256K = 输入 128K + 最多输出 128K，正好是模型自己的上限），长回答写几分钟也照样等。原来的 `max_output_tokens = 8192`（含推理）会让高推理强度的难题推理到一半就被截断，`timeout_seconds = 120`（从开始调用到写完）也容易被高推理加搜索加长回答超过。

- **输出上限默认不设**：`[chat].max_output_tokens` 改成可选，不写就不向服务商传（OpenAI 不带 `max_output_tokens`，Gemini 的 `generation_config` 里不带），由模型自己的上限兜底；写了照常传，校验范围不变（1 到 131072），含推理所用的 token。做法与 6a 的「后台任务默认不设输出上限」相同。Gemini 不传时实际是 65,536（见「查证过的外部事实」的「模型」）。
- Gemini 的 `generation_config` 什么都不设时（没有上限、没有推理强度、不要思考摘要）整个字段不带，不再发空对象 `{}`；后台任务同样适用。
- **时限分两段**，代替「`timeout_seconds` 秒内写完」：
  - 空闲时限 `[chat].idle_timeout_seconds`（默认 300，1 到 3600）：模型流这么久没有任何动静就放弃。「动静」以适配器从 SDK 收到的任何事件为准，而不只是本项目认识的那几种：适配器每收到一个 SDK 流式事件（含不认识的）就先交出一个 `llm.Heartbeat`，调用方照「忽略不认识的事件」的约定处理它，只有对话拿它重新计时。OpenAI 推理时可能很久只有本项目不关心的事件。
  - 总时限 `[chat].timeout_seconds`（沿用键名，默认改成 1800，上限仍是 3600）：一次调用从发出请求到写完最多这么久。QQ 被动回复的有效期是从用户那条消息算起的 60 分钟，前面还有决策、下载附件，换备用模型又要重新计时，所以留出余量。
  - 换备用模型时两个时限都重新计时。超时之后的处理（给用户的说明、记账、`Ending.TIMEOUT`）沿用原来的超时路径，只是触发条件变了；日志写明是空闲时限还是总时限。
- 实现（`conversation._Deadlines`）：读流的任务旁边起一个看门的任务，按注入的单调时钟（`Conversation` 的 `timer` 与 `sleep`，测试换成可控的）算两个到期时刻，到期就取消读流的任务；读流的任务按 `asyncio.timeout()` 的办法（`cancelling()` / `uncancel()`）区分这里的超时与别处的取消（关停、发送出错后停读）。流已经给出 `Finished`、只是关闭响应流时到期的，不算超时。
- **整轮赶在被动回复窗口之前**（评审补充）：每次调用独立计时不变，但一轮另有一个送达截止点，是回复所挂的那条用户消息记进流水的时刻（`messages.created_at`，`Conversation` 注入的墙上时钟）加 `REPLY_DEADLINE_SECONDS`（55 分钟：被动回复约 60 分钟有效，留 5 分钟给超时后的说明、结束流式消息和时钟误差）。否则配了备用模型时，主、备各用满 1800 秒（只有心跳、没有正文）就会用完同一条消息的 60 分钟，备用模型最后写出的回答或两次超时后的说明都会因原消息过期被拒。
  - 每次调用的总时限取 `timeout_seconds` 与离截止点的剩余时间中较小的，但不短于 `MIN_CALL_SECONDS`（60 秒）：第一次调用总会给一次机会，宁可略微越过留出的余量。截短了的总时限超时时，日志注明「已按被动回复的截止点截短」。
  - 换备用模型之前离截止点不到 `MIN_CALL_SECONDS` 就不再换（高推理加搜索一分钟内很难写出有用的回答），直接走原来的超时说明，日志记剩余秒数。
  - 流水里取不到那条消息的时刻时（不应发生）不设截止点。
- 看门任务到期时，如果读流的任务已经在被别处取消（插话、关停、发送出错后停读，`task.cancelling()` 大于开始时的值），就不再取消它：它正在收尾（SDK 异步关闭响应流），再取消一次会打断清理；那次取消的发起方自己限时等它（评审修正）。正常写完之后关闭响应流时仍在计时，关闭卡住时由时限兜底（已经给出 `Finished` 的不算超时）。
- 两个时限的大小不做交叉校验：空闲时限不小于总时限时，等于只有总时限。
- 后台任务（`[describe]`、`[memory]`）仍是单段的 `timeout_seconds`，不变。
- 空闲时限的实测（2026-11-19，`gpt-6.2-sol`，`reasoning = "high"`，问题固定、不含用户数据）：推理期间 SDK 事件持续到达，沉默的长度远小于推理的时长。

  | 问题 | 总耗时 | 首个正文 | SDK 事件 | 最长沉默 | 输出 token |
  | --- | --- | --- | --- | --- | --- |
  | 12 球称重（纯推理） | 21 秒 | 第 14 秒 | 657 | 8.1 秒 | 1,378 |
  | 今明两天天气比较（搜索加推理） | 15 秒 | 第 12 秒 | 110 | 1.8 秒 | 558 |
  | 1 到 2026 里任意两数之和都不是平方数，最多选几个（难题） | 368 秒 | 第 357 秒 | 929 | 12.7 秒 | 18,868 |

  结论：默认 300 秒的空闲时限有很大余量；难题推理了 6 分钟，原来「120 秒内写完」的时限会把它截断，30 分钟的总时限够用。

### 给管理员的提醒（`alerts.py`）

可复用的提醒模块，第一个用途是上面的下载域名提醒，里程碑 9 的「机器人掉线」「额度用尽」等也用它：

- `alerts.notify(键, 文案)`：同步调用，立即返回是否安排了发送；在后台给 `ADMIN_OPENID` 发一条主动消息。
- 同一个键 24 小时内只发一次（记在内存里，重启后可能再发一次）；全局每小时最多 10 条，免得耗光平台的主动消息额度；同一类提醒还可以另设更小的每小时上限（`AlertGroup`，下载域名一类是 3 条），免得一类提醒挤掉别的。被上限挡下的不占冷却；发出但失败的照样占冷却（多半是额度用尽）。每次发送最多 10 秒，超时就放弃。
- 发送失败只记日志，不影响触发它的流程；关停时在关闭 QQ 客户端之前等在发的提醒，之后触发的直接丢弃。
- 键和文案里不能放完整链接、路径、查询串或 openid。

### 里程碑 5b 定下的细节

模块：`faces.py`（表情标记的解析与表情包的判定，纯函数）、`batching.py`（计时规则与 `Batcher`）。

对话处理拆成两部分：

- `Conversation.receive()`：每条消息到达时就做——清洗表情标记、复查授权、下载附件、在事务里再复查并写进流水。不拿用户的串行锁，同一个用户的几条消息可以同时下载，但按到达顺序入库。
- `Conversation.respond()`：每批一次，拿用户锁。从流水里取这一轮的输入（编号不大于这一批最后一条、还没被回复覆盖的用户消息），回复挂在最后一条上；附件说明只就这一批的消息发一次。选模型、生成、收尾、记账都沿用 5a。
- 接线层的处理函数收下消息就返回，回答在 `Batcher` 按用户开的任务里进行。

表情标记：

- 认得的形式是 `<faceType=数字,名字="取值",…>`，换成「[表情]」；`ext` 能解出 JSON 且 `text` 是合适的短字符串（不超过 16 字、不含括号类字符）时换成「[表情：{text}]」。`ext` 过长、不是严格的 base64、解不出 JSON 等情况一律退回「[表情]」；认不出的形式原样保留。原始标记不进流水，也不进上下文。
- 表情包的判定：至少有一个认得的标记，去掉标记后没有别的文字，附件都是不被引用的图片且张数不超过标记数。表情包的图片不下载。
- 收消息时把「这条消息是不是只由真实的表情标记组成」记进流水（`messages.faces_only`），可答性判断只看这一列，不从「[表情]」的显示文字反推，所以用户手打的「[表情]」照常回答。
- 组装模型输入时（对话请求与决策输入），所有文字都过一遍 `faces.clean()`：用户消息、助手的历史回复、附件的文字版与文件名。流水里保留原文，升级前存进去的原始标记也因此不会进模型。
- 只有标记、没有图片的消息（很可能是单独的小黄脸）也按表情包处理，不回复。

攒批（`[batching]`）：

- 每条消息归为三种：有文字或语音、只有图片或文件、单独的表情包。
- 一批的结束时刻 = 最后一条非表情包消息的到达时刻 + 它那种的等待（`text_wait_seconds` 2.5 秒或 `attachment_wait_seconds` 12 秒），但不超过「第一条非表情包消息 + `max_wait_seconds`（20 秒）」。只有表情包时不成一批。
- 等待期间来了新消息就重新计算，所以结束时刻可能推后，也可能提前（只有图片的一批来了文字就提前）。
- 到点就截止，之后到达的消息算下一批；生成期间到达的消息同样算下一批，等这一轮结束后再处理。
- 都设为 0 就不攒批。

轮次的边界改按回复的 `reply_to`：一轮还在生成时，下一批的消息已经入库，它们的行号比这一轮的回复小，但这一轮并没有看到它们。所以「已经被回复覆盖的消息」是编号不大于某条结束了一轮的回复的 `reply_to` 的那些；历史里每条回复排在它回答的消息之后，而不是按行号排。迁移 V5 为此加了 `(user_id, reply_to)` 上的索引。

收消息改成先入库、后下载：在事务里复查授权、写入用户消息与附件占位（先记为下载失败），再去下载并改写占位。这样 Gate 放行之后，消息无论如何都会进流水；下载途中关停，附件按「没能下载」处理。写入流水的顺序就是到达的顺序。

一批最多 32 条（与本轮输入能取的上限共用一个常量），多出来的留给下一批。批次按每条消息的到达时刻划分：上一轮生成得久，期间到达、彼此相隔超过等待时间的消息仍分成不同的批次，依次回答。

关停顺序（`__main__._shut_down()`，改用 pyqbot 的 `Bot.stop()` 之后）：

1. `Batcher.stop()`（同步）放弃计时中的批次、取消正在回答的轮次；之后收下的消息只入库、不回答。它排在 `Bot.stop()` 之前，免得等处理函数的那几秒里刚收下的消息又开一轮（发「正在输入」、调用决策）随即被取消。
2. `Bot.stop()`，限时 `BOT_STOP_SECONDS`（5 秒）：断开网关、不再收新事件，等前台的处理函数自然结束（Gate 的决定、写流水、下载附件）；不取消它们，QQ 的 HTTP 客户端照常可用。到期只结束等待、不取消处理函数，还在下载附件的留给第 5 步。
3. 等 `Batcher` 与 `Conversation` 收尾（结束分片、记账）。
4. 给管理员的提醒停止并收尾。
5. `Bot.close()`：取消仍没结束的处理函数（消息在下载之前已经入库，被取消的下载按「没能下载」记），最多等 5 秒，再关 QQ 的 HTTP 客户端。
6. 等接线层「Gate 放行 → 入库」的交接完成（被取消的处理函数仍会把放行的消息写进流水）。
7. 向后台任务发出停止请求，限时等它们收尾 → 关模型客户端与数据库。

被放弃的消息已经在流水里，重启后是待回复的消息，等用户发下一条时一并回答。所有等待共用 15 秒的总时限，其中给第 5、6 步留 8 秒。

已知的取舍：

- 很久以前单独发的表情包一直是待回复的，会以「[表情]」并进下一轮的输入，即使隔了几个小时。
- 「攒批的等待与决策调用同时进行」没有做，决策在一批结束之后才调用。
- 之前遗留的待回复消息加上这一批超过 32 条时，最早的遗留消息会被这一轮的回复覆盖，之后取不回来。
## 接入与授权

pyqbot 已有的能力（实测结论见 pyqbot 的 `docs/errata.md`）：

- `generate_share_link(callback_data=...)` 生成邀请链接，`callback_data` 最长 32 个字符。
- 用户经链接添加后，`FRIEND_ADD` 的 `scene_param` 就是 `callback_data`。这时 `scene` 实测是 1000，不是官方文档写的 2003 / 2004，所以只认 `scene_param`。

链接不是门禁：用户还能通过搜索、群、资料页添加机器人。授权是机器人自己存的一张名单，默认拒绝，对应 `AGENTS.md` 的第一条不变量。

已实现，细节见「实现进度」的里程碑 2：

- `callback_data` 用随机的邀请码，在本地记录有效期与可用次数，默认一次性。链接可以被转发。
- 兜底通道：同一个邀请码能在聊天里发给机器人兑换，整段邀请原样发回来也行。
- 管理员用环境变量 `ADMIN_OPENID` 标识，机器人看不到 QQ 号。

## 一轮对话

```text
攒批 → 非文本转文字 → 决策 → 组装上下文 → 模型流式回复 → 后台更新摘要与档案
```

- **攒批**：把短时间内的多条输入合成一次提问。带文字或语音的消息稍等片刻再处理；只有图片或文件的消息多等一会儿，没有后续就直接回应它。同一个用户始终串行。
- **文字版**：每个非文本输入存一份文字版（语音转写、图片描述、文件摘要）。当前这轮，选中的模型支持该模态就给原件，否则给文字版。同一话题最近几轮里的图片和文件原样再带上，更早的只带文字版。
- **决策**：一次 Decisions 调用问两道选择题，见「记忆」。
- **回复**：用 pyqbot 的 `reply_stream()` 流式回复，只有单聊支持，且只能是被动回复。

## 记忆

每个用户存三样东西：

- **消息流水**：所有消息原样追加，是唯一的事实来源。
- **话题线**：自动划分的隐式 session，每条有标题、一段摘要和最近活跃时间。
- **用户档案**：几百字的稳定事实，如称呼、偏好、重要的人和事。

每轮的决策调用问两道题：

- **用哪类模型**：选项是配置里的模型列表，每项带一句类别描述。
- **属于哪条话题线**：选项是候选话题线的标题与一句话摘要，外加「新话题」。

Decisions 返回每个选项的概率，上下文按概率组装：

| 内容 | 何时带上 | 形式 |
| --- | --- | --- |
| 用户档案、话题目录（只有标题） | 每次 | 短文本，让模型知道别的话题存在 |
| 全局最近几轮 | 每次 | 原文，兜住「它」「刚才那个」这类指代 |
| 概率最高的话题线 | 每次 | 摘要加该话题最近若干轮原文 |
| 概率次高、超过阈值的话题线 | 拿不准时 | 只带摘要 |

这样一轮的上下文约 5k–8k token。几个候选模型的窗口都在 100 万 token 上下，限制不在窗口而在费用，所以不把整段历史都带上。

Decisions 只能选、不能写。新话题的标题、话题摘要和档案更新交给后台的小模型，在回复之后做，不占用户等待的时间。

用户引用旧消息时，pyqbot 给出被引用消息的索引（`message.ref_msg_idx`），`msg_elements` 里带回被引用的内容，可以直接定位话题，不必靠猜（见里程碑 6a 的「按引用定位」）。

### 留给以后的口子

用户要求留出拓展空间。建议守住三条：

- **流水只追加，其余都是可重建的派生数据。** 话题归属、摘要、档案、文字版都能从流水重新算出来，以后换提示词、阈值或算法时可以对历史重跑。唯一的例外是用户要求遗忘：对应的流水要彻底删除，再重建受影响的摘要和档案。
- **每轮存一条决策记录**：候选、各选项的概率、最终选择、带了哪些上下文、耗时与 token。效果不好时靠它查原因，延迟实测的数据也从这里来。
- **三个接口**：决策、对话模型、语音转写，SDK 隔在接口后面。「生成候选话题」与「在候选里选」分成两步，以后可以给前一步加关键词或向量召回。
- **一次回复是若干段内容，不是一个字符串。** 现在只有文字，以后可以加语音或图片形式的回复。
- **工具不一定在本地执行。** 联网搜索由服务商在它那边执行，工具调用的流程不能假设每个工具都有本地的处理函数。

### 已知的薄弱处

都还没有定做法，实现到相应部分时先和用户确认：

1. **候选话题从哪来**：选择题最多 255 个选项，实际只会列最近几十条，很久以前的话题会被判成「新话题」。已定，见里程碑 6a。
2. **新话题的空窗期**：后台还没写出标题和摘要时，下一条消息认不出这条话题。已定先用首条消息的开头当临时标题，见里程碑 6a。
3. **决策调用失败或被拦**：超时、安全拦截、拒答都可能发生，情感类内容最容易触发。选模型这道题已在里程碑 4 处理（硬超时，失败就沿用上一轮的模型）；话题那道题的退路见里程碑 6a。
4. **流水里记什么**：平台可能拒发或流式中途失败，要记用户实际看到的内容，而不是模型生成的内容。
5. **模型来回切换**：两个模型交替回答会像换了个人。已在里程碑 3、4 处理：各模型共用人设，切换要求概率有明显差距（`switch_margin`），跨服务商的历史只存纯文本。
6. **连发消息**：攒批的等待可以和决策调用同时进行；期间来了新消息就取消重来，生成过程中来的排到下一轮。
7. **重复推送**：平台可能重复推送同一条消息，pyqbot 不去重。已在里程碑 2 处理，见「实现进度」。

## 展示处理过程

目标是像 ChatGPT 那样：处理时能看到进展，回答出来后过程不碍事。

已定：

- **过程与回答分成两条消息。** 过程用一条流式消息；回答开始时结束它，另起一条流式消息写回答。pyqbot 实测同一条用户消息可以先后被动回复两条流式消息，两条都正常显示、正常结束。
- **过程消息回答之后留着，不撤回**（用户 2026-11-19 决定）。原定「2 分钟内撤回、相当于折叠」，但 pyqbot 实测 QQ 的流式消息撤回不了。

QQ 侧的限制（官方文档快照与 pyqbot 的实测）：

- 消息的 Markdown 没有折叠语法，HTML 标签（如 `<details>`）不生效。
- 流式消息的 `replace` 只能接着已下发的内容往后写，不能删改用户已经看到的部分。过程和回答放在同一条流式消息里时，过程去不掉。
- 流式消息的请求体里没有键盘字段，不能带按钮。
- 普通消息的撤回只在发出 2 分钟内有效，撤回后聊天里会留下一条撤回提示；**流式消息撤回不了**（pyqbot 实测，见「查证过的外部事实」的「QQ 平台」）。
- 流式消息每来一片，手机会轻微震动一次。

建议，未定：

- **过程只写步骤级的短句**（在查什么、发现了什么），每步一行，按步骤更新而不是逐字更新。（格式已定为纯文本，见 7b 的细节。）
- **没有过程就不发过程消息。** 模型直接开始回答时只发「正在输入」。
- **按模型类别配置是否展示**，情感陪伴类默认不展示。
- **回答要能独立成立**，不依赖过程里说过的话。过程的全文存进决策记录，不进后续的上下文。
- 回答开始之后再出现的思考或搜索不再展示，只记录。

过程的内容有三个来源，两家服务商给的形式不同，见「查证过的外部事实」的「思考摘要与过程标记」：思考摘要、调用工具前的说明、搜索的查询词。让模型在调用工具前先说明的提示词（如「我先查一下……」）只适合 OpenAI：它用 `phase` 字段把说明和最终回答分开；Gemini 没有这种标记，官方也不建议强制模型在调用工具前输出文字。

## 提醒事项

建议，未定：

- 自己存一张提醒表，加一个「睡到最近一条到期」的 asyncio 任务，启动时补发已过期的。asyncio 自带定时但重启就丢；APScheduler 4 仍是 alpha，3.x 要持久化就得带上 SQLAlchemy。
- 时间解析交给主模型，把「设置提醒」做成工具，对所有模型类别开放；回复里复述解析出的时间，方便用户纠正。
- 到点发出的是主动消息：用户在资料卡关掉「允许主动发送」就会失败，要在用户下次发言时补上。

提醒有两种，区别在于到点时要不要再调用一次模型：

- **到点发一句话**：「8 点提醒我吃药」，到点发出事先定好的内容。第一版做这种。
- **到点执行一个请求**：「明早 8 点告诉我今天的天气」，内容在设定时还不存在，到点要让模型带着工具跑一轮再发出结果。已定要做，但以后再做。它只能作为主动消息发出，不能流式。

提醒表里先留好区分这两种的字段。

## 其它待定

- **配额的具体规则**：每个用户的每日上限、全局预算。工具执行时的用户身份取自当前会话，不取模型给的参数。
- **时间感**：上下文里标注当前时间，以及距上次对话过了多久。
- **数据去留**：用户删除好友后数据保留多久，附件的磁盘清理。
- **情感类的风险处置**：涉及自伤等内容时走固定的模型与回应方式，不交给路由决定。

对里程碑 5、6 的影响：

- 附件的 `content_type` 和扩展名都不可信，下载后要按文件内容判断格式。
- 语音有两条路：直接用 QQ 的识别文本（不花钱），或下载 WAV 交给模型或转写接口。

- 表情包要单独识别，不能每个都回复。它附带的文字（经用户同意，从本地流水里查看了那一条）是一个表情标记：`<faceType=6,faceId="0",ext="eyJ0ZXh0IjoiIn0=">`，其中 `ext` 是 base64 编码的 JSON，这次解出来是 `{"text":""}`。所以识别规则是：文字里的 `<faceType=…>` 标记换成「[表情]」（`ext` 里的 `text` 不为空时用它）；去掉标记后没有别的文字、只剩表情图片的消息就是表情包。QQ 的小黄脸等系统表情很可能也用同样的标记（`faceType` 不同），未实测。现在的版本会把这段标记原样发给模型。
- 按引用定位话题时要把消息与被引用的内容对上，需要另存每条消息的引用索引（`msg_idx` / `ref_idx`），当时流水里没有（后来里程碑 5a、6a 加上了，见那里）。
- 文件「合集」（一次发多个文件）以一条普通文字消息到达：`message_type=0`，没有附件，文字是「闪传」卡片的标题（如「……等 2 项文件」），所以没有触发形态日志，而是走了对话流程，模型回复说看得到标题、打不开文件。要支持它，得先弄清闪传的内容能不能通过接口取到。优先级低。
- 机器人目前没有公开，经分享链接添加用户这一步暂时没法实测。

## 需要实测

实测前按 `AGENTS.md` 先取得用户同意。

- 附件地址的有效期：过多久就下载不到了。
- QQ 的小黄脸等系统表情以什么形式到达，是否也是 `<faceType=…>` 标记、带不带图片附件。
- 单聊消息里的昵称字段有没有值。官方示例里是空串，pyqbot 的样本里有值，但可能是脱敏后的占位。
- 单条消息的长度上限，长回复要不要拆条。
- QQ 单条流式消息最长能写多少字、能持续多久（对话不再设输出上限、总时限放宽到 30 分钟之后，长回答更常见）。第三次 QQ 实测里约 6000 字的回答在客户端被平台拆成了两条，所有分片都被接受、没有报错。2026-11-19 已请 pyqbot 实测：按字数、字节还是时长拆，拆在哪里（会不会切开代码块或表格），响应里有没有信号（`remain_msg_len` 等），拆出的一条能不能引用、占不占被动回复次数，有没有硬上限。有了结论再决定主动分条的做法：在接近上限时按段落边界（不在代码块、表格里）结束这条，另起一条流式消息，每条占一次被动回复。
- 已是好友的人点邀请链接、机器人离线时有人添加，这两种情况会不会收到 `FRIEND_ADD`。
- 回答里带任意网站的引用链接时，平台会不会拒发。
- 「正在输入」每次请求 8 秒、有进展再请求，在手机上看起来是否自然。

出处是 pyqbot 的 `docs/errata.md` 与官方文档快照：

- 单聊主动消息的官方限额是每个用户每天 1000 条。用户切换资料卡里的开关时，平台推的是 `type` 18 的互动事件。

2026-11-20 pyqbot 的实测（它的 `tests/live/test_live_quote.py`，结论记在它的 `docs/errata.md`，提交 84d1604）：

- **流式消息撤回不了**：在发出后两分钟内，用 `stream_msg_id` 撤回报 40061001「请求参数无效」，用 `ref_idx` 报 40011002「不支持的调用」。所以过程消息留着（见「展示处理过程」）。
- **同一条用户消息可以先后被动回复两条流式消息**，两条都正常显示、正常结束：过程消息加回答的做法成立。
- 流式消息的每个分片响应（含结束分片）都带同一个 `id`（`stream_msg_id`）与同一个 `ext_info.ref_idx`。
- **引用**：`message.ref_msg_idx` 四次都对上——引用机器人的普通消息时等于发送结果的 `ext_info.ref_idx`，引用流式消息时等于 `StreamMessage.ref_idx`，引用用户自己的消息时等于那条消息的 `msg_idx`。`msg_elements` 只有一项，就是被引用的那条：`msg_elements[0].msg_idx == ref_msg_idx`，`content` 是完整正文，`message_type` 总是 103，没有 `author`。
- **等待气泡**：用户每发一条单聊消息，客户端底部先出现一个三个点在跳的空气泡；机器人回复后它变成回复，不回复时约 1 分钟后才消失。用户决定接受、保持现状：表情照旧忽略，单独的附件照旧等下文或 60 秒后问一句。
