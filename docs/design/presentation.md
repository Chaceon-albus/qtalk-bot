# 展示与交互

回答怎样排版，哪些地方用按钮与指令面板，图片能不能随回答一起发出。过程消息与「正在输入」见 [search-and-process.md](search-and-process.md)，确认按钮现有的机制见[「记忆」里里程碑 6b 的实现](memory.md#里程碑-6b-的实现2026-11-20)。

起因（2026-11-20）：用户喜欢 ChatGPT 的 Intelligent UI 那种富展示（模型从一套固定的原生组件里挑，客户端边生成边渲染；OpenAI 没有公开接口），想知道本项目能向它靠拢多少。结论是能靠拢的主要是 Markdown 本身，交互只有按钮一种，凡是「点一下、原地变化」的（表单、计算器、标签页、小游戏）都做不了。

## QQ 侧能做到什么

出处是 pyqbot 的 `docs/guide.md`、`docs/errata.md` 与官方文档快照（`docs/upstream/qqbot-api-v2/`），以固定的那个 commit 为准。

- **Markdown**：官方「Markdown 消息」列的标题、文字样式（粗体、斜体、删除线）、链接、图片、有序与无序列表（可以嵌套）、块引用、分割线都能用；文档没列的代码块、表格（含对齐）、LaTeX、任务列表、脚注实测也能用，流式与普通消息的最终渲染一致（errata「Markdown：实际支持的语法比文档多」）。HTML 标签不生效，没有折叠。嵌套列表的子项要缩进 4 个空格，列表前面是普通文字时要先空一行（官方文档的「列表嵌套」）。
- **图片可以写在 Markdown 正文中间**：`![文字 #宽px #高px](地址)`，地址要能在公网访问，平台自己下载转存；流式消息里也能用。宽高必须写，并按原图的比例：不写时只显示「[文字]」，写错会变形。平台抓不到图时接口不报错，客户端显示「图片加载失败」。素材库（先上传、再引用 `qqbot-media://` 地址）每个机器人最多 100 张，但引用它的消息发完之后就可以删掉素材，已发的消息不受影响。细节见下面的[「QQ 一侧的实测」](#qq-一侧的实测2026-11-20)。
- **按钮只能随普通的 Markdown 消息发**，流式消息的请求体里没有键盘字段。三种按钮：回调（点了推一个互动事件）、指令（把一段文字填进输入框，`enter` 时直接以用户的身份发出，只有单聊）、跳转（https 链接）。回调按钮可以分组（同组点了一个，其余变灰）、带二次确认弹窗、选样式（线框、蓝底、红字）。
- **消息发出后不能修改**：单聊只有发送、流式发送、撤回三个接口。普通消息发出 2 分钟内可以撤回（聊天里留一条撤回提示），流式消息撤回不了。所以按钮发出后去不掉，「用过就消失」至多做到失效或变灰，见下面的[「按钮用过之后」](#按钮用过之后)。
- 点了回调按钮后的 `visited_label` 只是临时显示，收到下一条消息后按钮又显示回原来的文字（errata「回应互动」）。
- **指令面板**（输入 `/` 时弹出）可以只关联指定的用户（errata「指令面板」实测的就是只关联一个用户的单聊面板）；**底部的自定义菜单**对所有用户相同。

## 已定

### 格式说明只列能力

系统提示词里的格式说明（`prompt.FORMAT_GUIDE`）只告诉模型 QQ 能渲染哪些元素、平台有哪些限制，用不用、用哪些由模型自己决定；不规定什么场合用什么形式，也不要求闲聊只用纯文字（用户 2026-11-20 决定）。已实现：列出上面「Markdown」一条里的元素与嵌套列表的写法，HTML、链接、图片三条限制照旧。

### 先记下、还没实现的优化

用户 2026-11-20 决定要做，细节实现时再定：

1. **初次见面**：欢迎语下面只放一个按钮「你能做什么」，点了回一段固定的使用示例（不调用模型），用过之后就不再能用。不做底部的自定义菜单。
2. **单独发图或文件后的那句询问**（`texts.attachments_waiting()`）：加几个快捷按钮（如「描述一下」「提取文字」「翻译」「总结要点」）。用户点了其中一个，或接着发了消息之后，这组按钮就不再能用。
3. **确认类按钮**（忘掉话题、提醒的设置与取消）：用样式区分主次（删除用红字），同组点了一个之后另一个变灰，需要时加平台自带的二次确认弹窗。
4. **管理员的指令面板**：只对管理员生效的 `/` 面板，列出管理命令与说明。
5. **等待阶段**（「正在输入」与过程消息）不改。

### 按钮用过之后

平台没有修改或移除已发消息上的按钮的接口，所以第 1、2 条里的「消失」分两层做：

- 程序一侧一定做到失效：按钮带一次性的令牌，用过、过期或有了下文之后再点，不再起作用（沿用确认按钮的令牌机制；欢迎语的按钮可能隔很久才点，状态要存进数据库，不能只放内存）。
- 界面上能不能变灰或消失要实测：回调按钮的 `group_id`（文档说同组点了一个其余变灰，没说被点的那个，也没说只有一个按钮时怎样）；撤回只在发出 2 分钟内有效，还会留一条撤回提示，不合适。
- 因此这两处要用回调按钮，不能用「点了直接替用户发一句话」的指令按钮：后者发出后程序管不了，过多久点都会再发一遍。

## 图片随回答发出

用户的想法（2026-11-20）：模型的回答里有示意图之类的图片地址时，机器人把图拖下来随回答一起发出。与「模型输出里的图片语法」这个安全细节一起考虑（用户同意）。

**做法已定**（用户 2026-11-20 决定，两次实测之后）：机器人下载图片，传到素材库，在正文中间引用素材库的地址，这条消息发完就删掉素材。还没有实现。**下载时抓哪些地址还没有定**：倾向用主机白名单，名单里放哪些图站要先调研两家模型一般给哪些。

图片地址从哪来：

- **模型自己写的 `![说明](地址)`**：两家都能写，位置由模型决定。实测里两家只在搜索过的回答里给图，给出的地址都对得上真实的图片，见下面的[「模型一侧的实测」](#模型一侧的实测2026-11-20)。
- **OpenAI 搜索工具的图片结果**（2026-11-20 查自[官方指南](https://developers.openai.com/api/docs/guides/tools-web-search)的「Image search results」）：`search_content_types` 里加 `"image"`，`include` 里加 `web_search_call.results`，结果在 `web_search_call` 输出项里，每条有 `image_url`、`thumbnail_url`、`source_website_url`、`caption`。地址是真的，但与回答的正文分开给，放在哪由程序决定；文档的示例注明已发布的 SDK 还没有这几个参数。Gemini 的搜索没有图片结果（[官方指南](https://aistudio.google.com/docs/google-search)只有文字与 `url_citation`）。

为什么要由机器人下载，而不是把地址原样交给平台去抓：

- 平台的图片语法要写宽高，模型不知道图片的尺寸；下载后才能按真实的比例写。
- 模型写的地址可能打不开或不是图片，先下载才能把坏的去掉，不让用户看到裂图。
- 平台的服务器抓不到维基共享资源的图（实测显示「图片加载失败」），而模型给的图大多在那里；机器人这边可以走自己的网络或代理。
- 本地留一份，之后的轮次才能像用户发的图一样带给模型或写描述。

下载之后怎么发（QQ 一侧实测之后的结论，用户已确认用素材库）：

| 做法 | 实测之后 |
| --- | --- |
| 写回原地址、补上宽高，由平台再抓一次 | 不行：维基的图平台抓不到，流式消息又不报错，用户只会看到「图片加载失败」 |
| 传到素材库，正文里引用素材库的地址 | 可行，建议用它：图在正文中间；流式消息结束后立刻删掉素材，已发的消息里图还在，所以不占 100 张的额度 |
| 作为单独的图片消息发（现在画图用的就是它） | 备用：素材库上传失败时可以退到它，或干脆去掉这张图 |

照素材库的做法，程序要做的事：

- 流式输出到图片语法时先扣住，等这一段写完整。
- 下载、按文件头认格式、读出宽高。宽高必须写、要按原图的比例，过大的按比例缩小（写得很大时显示会变形，上限是多少没有测）。
- 传到素材库，把语法改写成 `![说明 #宽px #高px](素材库的地址)` 再交给流式消息。
- 这条流式消息结束之后删掉素材。不能提前删：引用已经删掉的素材时接口不报错，用户看到的是「图片加载失败」。
- 任何一步失败就去掉这张图、留下说明文字，不让回答卡住。

安全上要一起做的：

- 现在模型输出里的图片语法只靠提示词禁止，程序没有拦（`markdown_guard.py` 只处理链接的括号）；平台会去抓其中的地址。
- 机器人自己下载时要防着请求内网：只收 https，解析出的地址是内网、回环、链路本地等一律拒绝，重定向之后重新检查，限制大小与时长，按文件头认格式（`media.detect_format()`）。附件下载现在靠的是 QQ 域名的白名单，这里用不上。
- 泄露：开着搜索时，网页里的注入内容可以让模型把对话里的信息拼进图片地址，谁去抓这个地址，信息就到了对方手里。可选的做法，取哪种没有定：
  - 只抓搜索工具自己给出的地址：最稳，但那就不收模型自己写的地址。
  - 主机白名单（做法同 `[attachments].extra_download_hosts`）：只抓少数知名图站的图，其余的不抓。实测的 8 张里 7 张在维基共享资源、1 张在 NASA，默认的名单不用长。
  - 去掉查询串再抓、限制地址长度：挡不住把信息写进路径的。实测的 8 张里 3 张带查询串（2 张是维基的统计参数，1 张是 NASA 的缩放参数），直接不抓带查询串的会丢掉这 3 张。

### 模型一侧的实测（2026-11-20）

用户同意后做了一次。把格式说明里「不要插图片」那条换成「可以用 `![说明](图片的完整 https 地址)` 把网上真实存在的图片插在正文里合适的位置；只用你确实知道存在的图片地址，不要编造」，系统提示词只有人设、格式说明与当前时间，没有画图函数。两家都按本地配置开着搜索，各问 10 个固定的问题（不含用户数据）：5 个明说要图（光合作用、TCP 三次握手、心脏结构、勾股定理的证明、埃菲尔铁塔），5 个没说但适合配图（水循环、有丝分裂、行星大小、二叉搜索树的插入、板块构造）。再由脚本逐个下载回答里的图片地址，按文件头判断是不是图片。20 次调用都正常结束，共搜索 20 次。

| 模型 | 明说要图的 5 问 | 没说要图的 5 问 | 给出的图片地址 |
| --- | --- | --- | --- |
| `gpt-6.2-sol`（`reasoning = "high"`） | 3 个回答带图，各 1 张 | 都没有图 | 3 张都下载到了真的图片 |
| `gemini-4-hydrogen`（`reasoning = "medium"`） | 4 个回答带图，各 1 张 | 1 个回答带图 | 5 张里 4 张是真的图片，1 张被图站限流（HTTP 429） |

- **没有编造的地址**：8 张图全部出在搜索过的回答里；没搜索的 10 个回答都没有给图。被限流的那一张是维基共享资源上的原图，同一个文件的缩略图地址在另一家的回答里下载成功，所以文件是存在的。
- **要了图却没有给图的 3 个回答**（`gpt-6.2-sol` 的 TCP 三次握手与勾股定理，这两问它没有搜索；`gemini-4-hydrogen` 的勾股定理）都改用代码块里的字符画和 LaTeX 来讲，没有硬凑一个地址。
- **不主动配图**：没说要图的 10 个回答里只有 1 个带图。
- **位置与说明**：图都放在正文靠前或中间、紧跟引出它的那句话，说明文字是中文、写得具体；都没有写宽高。`gpt-6.2-sol` 每张图下面自己加了一行图源与授权（如「图源：维基共享资源，CC BY-SA 3.0」）。
- **图站**：7 张在维基共享资源（6 张是 `thumb.wikimedia.org` 的缩略图，SVG 的示意图已转成 PNG；1 张是 `upload.wikimedia.org` 的原图），1 张在 NASA。格式是 PNG 与 JPEG，51 KB 到 313 KB。
- **对做法的影响**：
  - 模型自己写地址这条路走得通，至少对百科类的内容是这样。
  - 维基的站点在境内访问不了，平台的服务器抓不到（QQ 一侧的实测里显示「图片加载失败」），所以要由机器人下载再传给 QQ。
  - 图站会限流，下载要一张张来、失败就去掉图，不能让回答卡住。
- **局限**：只有一次、20 个回答、8 张图，问题都是百科里常见的内容；冷门内容与其它图站没有测。脚本与原始回答没有放进仓库。

### QQ 一侧的实测（2026-11-20）

用户同意后做了一次，用例是 pyqbot 的 `tests/live/test_live_markdown_images.py`，结论记在它的 `docs/errata.md`「Markdown 图片：不写宽高不显示，抓不到时显示「图片加载失败」，接口不报错」与「素材库：流式消息里可以引用，发出后删掉素材不影响已发的消息」（pyqbot 提交 acc6abf、3cbcd66，比本仓库固定的那个 commit 新）。单聊，测试用户发编号，机器人回一条正文中间带图的消息，15 种都做了：

| 情况 | 接口 | 用户看到的 |
| --- | --- | --- |
| 流式，维基共享资源的图 | 各分片都被接受 | 图片加载失败 |
| 流式，地址是 404、是网页、主机解析不了 | 各分片都被接受 | 图片加载失败 |
| 普通消息，地址是 404 | 被接受 | 图片加载失败 |
| 普通消息，地址是 404，打开强制校验 | 被拒，`err_code` 40034141「图片转存失败，请重试」 | 没有消息 |
| 流式，不写宽高（公网的图、素材库的图各一次） | 各分片都被接受 | 不显示图片，只显示「[说明]」 |
| 流式，540×258 的图写成 300×300 | 各分片都被接受 | 图片被拉伸 |
| 流式，同一张图写成 2160×1032（比例没变） | 各分片都被接受 | 图片被压扁 |
| 流式，素材库的图，结束后立刻删掉素材 | 上传、各分片、删除都被接受 | 发出编号后就退出聊天，等发完、删完再进入，图片显示正常 |
| 流式，引用已经删掉的素材 | 各分片都被接受，没有报错 | 图片加载失败（两次都是） |
| 流式，百度的图、NASA 的图（地址带查询串）；普通消息加素材库的图 | 都被接受 | 没有记下观察（显示失败的几种都记了） |

还不知道的：百度与 NASA 那两种的图有没有显示出来；图是在流式过程中出现还是结束后才出现；宽高写到多大开始变形；流式消息还没结束就删掉素材会怎样。

## 没有定

调研里提过、用户还没有表态的：

- 给模型一个「给出选项」的函数，回答之后由程序发一组按钮（做法同忘掉话题的确认：函数只登记，回答写完再发）。
- 出错与没写完时的「继续」「重试」按钮。
- `/users`、`/invites` 列表下的停用、撤销按钮；`/usage` 改成表格。
- 图表（服务商内置的代码执行出图，或本地渲染）。

## 还要实测的

- 回调按钮的 `group_id`、二次确认弹窗（`modal`）、红字样式在单聊里的实际表现（pyqbot 都还没有实测）。
- 指令按钮 `enter` 在单聊里点了之后实际发出的文字（pyqbot 的实测用例里有这个按钮，errata 只记了样式）。
- 按钮文字的长度上限（pyqbot 的 docstring 写 10 个字符）。
- 嵌套列表缩进 2 个空格时会不会被压平（官方只说要 4 个空格；管理员的 `/usage` 现在用的是 2 个空格）。
- 「QQ 一侧的实测」末尾列的几项还不知道的。
