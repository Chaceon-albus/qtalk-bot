# 对话

一轮对话从收到消息到回复送达的全过程（里程碑 3、5b、5c）：流程、两家的对话接口、出错时的处理、流水与送达状态、用量、输出上限与时限、长回答分条、收消息与开轮、表情、插话、关停顺序。选模型见 [model-routing.md](model-routing.md)，附件见 [attachments.md](attachments.md)，过程消息与「正在输入」见 [search-and-process.md](search-and-process.md)。

## 一轮对话的流程

```text
收消息（入库、下载）→ 开轮 → 附件说明 → 决策 → 组装上下文 → 模型流式回复 → 记账 → 后台写描述、摘要与档案
```

- **收消息与开轮**：每条消息到达时就入库；文字和语音立即开始一轮，单独的图片或文件等下一条文字或语音，一起作为一轮。见[「收消息与开轮」](#收消息与开轮)。
- **文字版**：每个非文本输入存一份文字版（语音转写、图片描述、文件摘要）。当前这轮，选中的模型支持该模态就给原件，否则给文字版；历史里只有最近几轮的图片给原件，其余只带文字版。见 [attachments.md](attachments.md)。
- **决策**：一次 Decisions 调用同时选模型与话题（启用了用户档案时再加一道档案题），见 [model-routing.md](model-routing.md) 与[「记忆」](memory.md)。
- **回复**：用 pyqbot 的 `reply_stream()` 流式回复，只有单聊支持，且只能是被动回复。

回答一轮：

1. 同一个用户的轮次串行处理，不同用户互不阻塞。
2. 一个事务里：用 `access.chat_allowed()` 再确认一次，取出这一轮的输入与这个用户最近若干轮。
3. 模型还没开始输出时发「正在输入」：每次只请求一个短脉冲，有进展时再请求；插话重来时距上次实际发出不到一个脉冲就不再发，见[「正在输入」](search-and-process.md#正在输入)。出现非空白的正文后才开始流式消息。
4. 结束后在一个事务里写入：用户实际看到的回复、送达状态、每次模型调用的用量。

只有不支持的内容（视频、卡片、转发的聊天记录等）、没有文字的消息，确认授权后回一句「暂不支持」，不进流水。图片、语音、PDF 的处理见 [attachments.md](attachments.md)。

上下文是系统提示词加最近 `[chat].history_turns` 轮的原文；分话题时历史由不分话题的最近几轮与选中话题的最近几轮合成，见[「记忆」的「上下文组装」](memory.md#上下文组装)。系统提示词的基本部分是配置里的人设、一段固定的格式说明（告诉模型 QQ 能渲染什么）、附件标记的说明、当前时间；展示过程、话题、提醒、画图各自另加一段，见 `prompt.py` 与对应的文件。格式说明只列能力、用不用由模型决定，见[「展示与交互」](presentation.md#格式说明只列能力)。

## 模块

| 模块 | 职责 |
| --- | --- |
| `llm/__init__.py` | 与服务商无关的对话模型接口：请求、消息、流式事件、`ModelError`。不 import 任何 SDK |
| `llm/openai_responses.py`、`llm/gemini_interactions.py` | 两个适配器，SDK 的类型只出现在这里 |
| `llm/providers.py` | 按配置创建模型，同一家服务商共用一个客户端 |
| `conversation.py` | 一轮对话的核心逻辑：收消息（`receive()`）与回答一轮（`respond()`），不依赖 pyqbot 与 SDK |
| `batching.py` | 什么时候开始一轮、插话时重来还是停下、排队时回一句收到（`Batcher`） |
| `faces.py` | 表情标记的解析与「只由表情组成」的判定，纯函数 |
| `splitting.py` | 长回答分条的规则，不依赖 asyncio |
| `journal.py` | 消息流水与用量的数据层，所有查询都按用户过滤 |
| `prompt.py` | 拼系统提示词、组装请求 |
| `markdown_guard.py` | 发出前处理模型的输出，对流式的分片边界安全 |

## 两家的对话接口

OpenAI 用 Responses API，Gemini 用 Interactions API，都是流式，都关掉服务端存储（`store=False`），历史每次由本地完整带上。SDK 是 `openai` 3.55.1 与 `google-genai` 3.6.1。

事件接口：调用方必须忽略不认识的事件，加事件类型时不必改已有的调用方。现有的事件除文字增量、用量、结束外，还有搜索进展与引用（见[「内置搜索与来源」](search-and-process.md#内置搜索与来源)）、调用工具前的说明与思考摘要（见[「过程的来源」](search-and-process.md#过程的来源)）、函数调用，以及空闲时限用的心跳（见[「对话的输出上限与时限」](#对话的输出上限与时限)）。消息内容是若干「部分」：文字、图片、音频、文件。

SDK 的实际情况，与文档或预期不同的地方：

- Gemini 的 SDK 请求的是 `/v1/interactions`，不是 `v1beta`。
- Gemini 的 SDK 默认会自动续写，一次调用可能拆成多个 HTTP 请求，每次只报告当次的用量，适配器做了累加。关掉服务端存储后每次续写都会重发原始输入，输入会重复计费。
- 两家 SDK 默认都会自动重试，已调低（OpenAI 重试 1 次，Gemini 共 2 次），更多的重试交给备用模型。
- OpenAI 的输出消息带 `phase`，文档说回放历史时要原样带回。同一次调用里函数调用的多跳之间，上一跳的输出项（含带 `phase` 的消息）原样带回；跨轮的历史只存最终回答的纯文字，不带 `phase`。`phase` 为 `commentary` 的文字不进回答，见[「过程的来源」](search-and-process.md#过程的来源)。

## 出错时

- 模型调用失败、超时或只给出空白：只要还没有任何内容交给 QQ，并且配置了备用模型（备用模型还要能处理这一轮的附件，见 [attachments.md](attachments.md)），就换备用模型重试一次，调用前再确认一次授权。否则给用户一句固定的说明。时限见[「对话的输出上限与时限」](#对话的输出上限与时限)。
- 流式回复被平台拒绝：把全文改用纯文本的普通消息再发一次，仍然失败就发固定说明。
- 发送出错、说不准是否送达：立即停止读模型，不改发，免得用户收到重复内容。
- 机器人关停时：限时收拢在途的发送，把已确认送达的部分和已知用量写进流水。这是尽力而为，事件循环提前结束时仍会丢。
- 回答停在围栏代码块里时，接任何说明（中断、没写完、插话停下）之前先补上闭合围栏的那一行，免得说明被渲染进代码块；闭合行算回答的一部分，与接「来源」之前的处理相同。

## Markdown 的处理

把形如链接、目标却不是 http(s) 地址的那对圆括号换成全角括号，代码块和行内代码里的内容不动。没有用反斜杠转义，因为 QQ 会把 `\(…\)` 当成行内公式。全角括号能否通过平台审核还没有实测。

## 流水与送达状态

流水里每条回复有两个状态。`finish` 是模型一侧的结局：

| 取值 | 含义 |
| --- | --- |
| `completed` | 正常写完 |
| `max_tokens` | 达到输出上限 |
| `incomplete` | 其它原因没写完，如内容过滤 |
| `error` | 调用失败或流中途出错 |
| `timeout` | 超过空闲时限或总时限 |
| `empty` | 正常结束，但只有空白 |
| `aborted` | 发送出错后主动停止 |
| `steered` | 回答显示到一半时用户插话、被判为补充，主动停下（见[「插话」](#插话)） |
| `cancelled` | 处理被取消 |
| `skipped` | 根本没有调用对话模型：决策之后发现用户已不能使用，或组装出的请求里没有可答的内容、只发了说明 |

`delivery` 是送达状态，`content` 记的总是已确认送达的回答，不含固定说明：

| 取值 | 含义 |
| --- | --- |
| `streamed` | 流式完整送达 |
| `interrupted` | 模型中途出错或超时，或因插话停下；已送达的部分后面接了相应的说明 |
| `unclosed` | 正文都已确认，结束分片被拒或说不准 |
| `plain` | 流式被拒，改用纯文本送达 |
| `rejected` | 流式和纯文本都被拒，固定说明已送达 |
| `failed` | 模型没给出回答，固定说明已送达 |
| `notice_lost` | 上面两种情况下，固定说明没能确认送达 |
| `noticed` | 没有送达任何回答，但附件的说明已确认送达（例如说完「附件没能下载」之后被取消）；算作结束了一轮 |
| `uncertain` | 发送回答时出错，说不准送达了多少 |
| `withheld` | 复查授权（决策之后、换备用模型之前、执行画图函数之前）时发现用户已不能使用对话，就此停止，不再发任何东西 |
| `cancelled` | 处理被取消（关停） |
| `images` | 没有送达文字回答，但这一轮画的图至少有一张已确认送达，见[「生成图片」](image-generation.md) |
| `card` | 模型没写回答文字，这一轮只发了提醒或遗忘的确认卡片与提醒列表，见[「提醒事项」](reminders.md) |

## 用量

每次模型调用记一条，含用户、模型的内部名字、当时的服务商与实际的模型名、输入与输出的 token 数。服务商没有返回时记空，不估算；失败的调用也记一条。`/usage` 的显示见[「接入与授权」的管理员命令](access.md)。

缓存命中的输入 token（迁移 V12 的 `cached_input_tokens` 列，含在输入 token 里）：OpenAI 取 `usage.input_tokens_details.cached_tokens`，Gemini 取 `usage.total_cached_tokens`（SDK 说明它是提示里被缓存的部分），两家 Decisions 与出图有就取；多跳时逐跳累加。一跳的缓存数超过这一跳的输入、或这一跳没报告输入时，这一跳的缓存数当作没报告。旧行为空。

## 配置与环境变量

完整的写法见 `config.example.toml`。

- `[[models]]`：`name`（内部名字）、`provider`（`openai` / `gemini`）、`model`、`default`、可选的 `fallback` 与 `reasoning`。至少一项，恰好一个默认。`reasoning` 原样传给服务商，本地不维护取值表。其它项（`inputs`、`search`、`show_process`、`image_generation`）见附件、搜索与过程、生成图片各自的文件。
- `[chat]`：`persona`、`history_turns`（默认 10）、可选的 `max_output_tokens`（默认不设）、`idle_timeout_seconds`（默认 300）、`timeout_seconds`（默认 1800）。后三项见[「对话的输出上限与时限」](#对话的输出上限与时限)。
- `[turns]`：`text_debounce_seconds`（默认 0）、`attachment_wait_seconds`（默认 60）、`attachment_timeout_action`（默认 `ask`）、`max_restarts`（默认 3），见[「收消息与开轮」](#收消息与开轮)与[「插话」](#插话)。
- `[providers.openai]`、`[providers.gemini]`：可选的 `base_url` 与 `proxy`。代理支持 http、https、socks5、socks5h，地址不进 `repr`、日志与报错。
- `[qq]`：可选的 `base_url` 与 `proxy`。代理的校验与写法同 `[providers.*].proxy`，原样传给 `pyqbot.Bot(proxy=...)`，作用于开放平台的接口请求、网关的 WebSocket 与经 `bot.http_client` 的附件下载；不设时系统级的代理变量照常生效。地址不进本项目的 `repr`、日志与报错，pyqbot 也保证账号密码不出现在它的 `repr`、日志与异常里（有测试）。
- 启动时交叉校验：配置里用到哪家服务商，对应的密钥就必须在环境变量里。

环境变量的影响：端点只有两个来源，配置里的 `base_url` 或官方默认值；`OPENAI_BASE_URL`、`GOOGLE_GEMINI_BASE_URL` 这类变量不采用，改走 Vertex、改接口版本的变量也都压住了。`OPENAI_CUSTOM_HEADERS`（SDK 会把它的内容作为附加请求头，还可能顶替鉴权头）没有对应的参数可以关掉，所以程序在创建 OpenAI 客户端之前把它从本进程的环境里去掉，并记一条日志。唯一照常生效的是系统级的代理变量：没配 `proxy` 时由它们决定。

两个要留意的地方：`base_url` 不能带查询串或片段，SDK 和 pyqbot 都是在它后面直接拼路径；Gemini SDK 的配置对象（`HttpOptions`）的 `repr` 里有明文的 API key，那是 SDK 自己放进请求头的，诊断时不要打印它。代理地址交给 SDK 之前包了一层，不会出现在这些 `repr` 里。

## 对话的输出上限与时限

向 ChatGPT app 看齐：它在 Thinking 模式下不在模型之外另设单条回答的输出上限（总上下文 256K = 输入 128K + 最多输出 128K，正好是模型自己的上限），长回答写几分钟也照样等。固定的输出上限（如含推理的 8192）会让高推理强度的难题推理到一半就被截断；「从开始调用到写完」的单段时限（如 120 秒）也容易被高推理加搜索加长回答超过。

- **输出上限默认不设**：`[chat].max_output_tokens` 是可选的，不写就不向服务商传（OpenAI 不带 `max_output_tokens`，Gemini 的 `generation_config` 里不带），由模型自己的上限兜底；写了照常传，校验范围 1 到 131072，含推理所用的 token。做法与[「后台任务的输出上限」](memory.md#后台任务的输出上限)相同。Gemini 不传时实际是 65,536（见[「查证过的外部事实」的「模型」](external-facts.md#模型)）。
- Gemini 的 `generation_config` 什么都不设时（没有上限、没有推理强度、不要思考摘要）整个字段不带，不发空对象 `{}`；后台任务同样适用。
- **时限分两段**：
  - 空闲时限 `[chat].idle_timeout_seconds`（默认 300，1 到 3600）：模型流这么久没有任何动静就放弃。「动静」以适配器从 SDK 收到的任何事件为准，而不只是本项目认识的那几种：适配器每收到一个 SDK 流式事件（含不认识的）就先交出一个 `llm.Heartbeat`，调用方照「忽略不认识的事件」的约定处理它，只有对话拿它重新计时。OpenAI 推理时可能很久只有本项目不关心的事件。
  - 总时限 `[chat].timeout_seconds`（默认 1800，上限 3600）：一次调用从发出请求到写完最多这么久。QQ 被动回复的有效期是从用户那条消息算起的 60 分钟，前面还有决策、下载附件，换备用模型又要重新计时，所以留出余量。
  - 时限按每次模型调用计，换备用模型时两个时限都重新计时。两种超时之后的处理相同（给用户的说明、记账、`Ending.TIMEOUT`），日志写明是空闲时限还是总时限。
- 实现（`conversation._Deadlines`）：读流的任务旁边起一个看门的任务，按注入的单调时钟（`Conversation` 的 `timer` 与 `sleep`，测试换成可控的）算两个到期时刻，到期就取消读流的任务；读流的任务按 `asyncio.timeout()` 的办法（`cancelling()` / `uncancel()`）区分这里的超时与别处的取消（关停、发送出错后停读）。流已经给出 `Finished`、只是关闭响应流时到期的，不算超时。
- **整轮赶在被动回复窗口之前**：每次调用独立计时，但一轮另有一个送达截止点，是回复所挂的那条用户消息记进流水的时刻（`messages.created_at`，`Conversation` 注入的墙上时钟）加 `REPLY_DEADLINE_SECONDS`（55 分钟：被动回复约 60 分钟有效，留 5 分钟给超时后的说明、结束流式消息和时钟误差）。否则配了备用模型时，主、备各用满 1800 秒（只有心跳、没有正文）就会用完同一条消息的 60 分钟，备用模型最后写出的回答或两次超时后的说明都会因原消息过期被拒。
  - 每次调用的总时限取 `timeout_seconds` 与离截止点的剩余时间中较小的，但不短于 `MIN_CALL_SECONDS`（60 秒）：第一次调用总会给一次机会，宁可略微越过留出的余量。截短了的总时限超时时，日志注明「已按被动回复的截止点截短」。
  - 换备用模型之前离截止点不到 `MIN_CALL_SECONDS` 就不再换（高推理加搜索一分钟内很难写出有用的回答），直接走超时的说明，日志记剩余秒数。
  - 流水里取不到那条消息的时刻时（不应发生）不设截止点。
- 看门任务到期时，如果读流的任务已经在被别处取消（插话、关停、发送出错后停读，`task.cancelling()` 大于开始时的值），就不再取消它：它正在收尾（SDK 异步关闭响应流），再取消一次会打断清理；那次取消的发起方自己限时等它。正常写完之后关闭响应流时仍在计时，关闭卡住时由时限兜底（已经给出 `Finished` 的不算超时）。
- 两个时限的大小不做交叉校验：空闲时限不小于总时限时，等于只有总时限。
- 后台任务（`[describe]`、`[memory]`）仍是单段的 `timeout_seconds`。
- 空闲时限的实测见[「实测记录」](#实测记录)：默认 300 秒有很大余量，30 分钟的总时限够用。

## 长回答分条（`splitting.py`）

平台按 Markdown 原文的 UTF-8 字节数在约 15000 字节处硬切，切口不看 Markdown 结构（pyqbot 实测，见[「QQ 平台」](external-facts.md#qq-平台)）；第三次 QQ 实测里约 6000 字的回答被平台拆成两条，衔接生硬。所以在合适的位置提前结束这一条、另起一条：

- 按回答的流式消息实际交出的文字（回答、补上的围栏、「来源」、固定说明）累计 UTF-8 字节数，规则写在不依赖 asyncio 的 `splitting.StreamSplitter` 里，`_Outbox` 只负责执行。输入怎样切分，分条结果都一样（有测试）。
- 过了 `SPLIT_SOFT_BYTES`（12000）之后开始的行只在整行到齐后交出，这样随时能在行边界上切；之后遇到合适的边界就结束这一条：不在代码块里的空行之后（下一行有缩进的除外：它仍属于上面的列表项，切开的话新的一条以空格开头，会变成缩进代码块），或表格开始之前（尽量不切表格）。只有空白的行同样计入硬上限。空行留在上一条末尾，新的一条开头没有空行。
- 再交出下一整行就会超过 `SPLIT_HARD_BYTES`（14000，比实测里表格横跨边界时的 14387 留了余量）而一直没有合适的边界时，就在当前的行边界切：在代码块里时给这一条补上闭合围栏，下一条以原来的开头行重开（列表项里的代码块连列表标记一起重开，新的一条会多显示一个列表符号）；到了硬上限还在表格里，只能切在表格行之间。
- 软上限之前开始的行整行留在这一条里，所以与平台的上限之间留了 3000 字节（约 1000 个中文字）的余量；比这更长的一段，或单独一行就超过硬上限的，仍会被平台拆开（单行超长时记警告）。
- 先等前一条的结束分片返回，再开下一条（同一条消息上两条流式消息不能同时开着，见[「QQ 平台」](external-facts.md#qq-平台)）；结束分片失败时记 `unclosed`，照样开下一条。新的一条第一片被拒时按「送达一部分后流式被拒」处理，全文改发纯文本（前面几条的内容会重复一遍）。改发纯文本时不分条。
- 每多开一条算一次被动回复，开之前要给兜底留出余量，不够就不再分条、让平台去拆，见[「被动回复次数的预算」](search-and-process.md#被动回复次数的预算)。
- 流水里存的仍是模型原文，不含为分条补上与重开的围栏行。插话停下时说明接在当前这一条上；固定说明只按硬上限切。日志「送达 streamed（分 2 条）」。
- 已知限制：回复行的 `msg_idx` 只存第一条的引用索引，用户引用第二条及以后的气泡时按引用定不到话题，退回由决策选话题。

## 收消息与开轮

### 收消息与回答分开

- `Conversation.receive()`：每条消息到达时就做——去掉表情标记、在事务里复查授权并写进流水、下载附件。不拿用户的串行锁，同一个用户的几条消息可以同时下载，但按到达顺序入库。
- `Conversation.respond()`：每轮一次，拿用户锁。从流水里取这一轮的输入（编号不大于回复所挂的那条、还没被回复覆盖的用户消息，含之前遗留的待回复消息），回复挂在这一轮最后一条不只由表情组成的消息上；附件说明只就这一轮的消息发一次。选模型、生成、收尾、记账都在这里。
- 接线层的处理函数收下消息就返回，回答在 `Batcher` 按用户开的任务里进行。

先入库、后下载：在事务里复查授权、写入用户消息与附件占位（先记为下载失败），再去下载并改写占位。这样 Gate 放行之后，消息无论如何都会进流水（Gate 放行时已经提交了去重记录，平台重推会被丢弃）；下载途中关停，附件按「没能下载」处理。写入流水的顺序就是到达的顺序。

### 什么时候开始一轮

不按固定时长攒批：等文字 2.5 秒来不及打下一条，等图片 12 秒也常常不够。QQ 平台没有「用户正在输入」的事件，机器人看不到用户是否在打字，所以只能按消息到达来决定。

- **文字和语音立即处理**；`[turns].text_debounce_seconds`（默认 0）可以设一个短防抖来接住快速的连发，期间每来一条重新计时。
- **单独的图片或文件不触发回复**，等下一条文字或语音，一起作为一轮。从最后一张附件到达算起，过了 `attachment_wait_seconds`（默认 60，最大 1800，因为发问或回答是对原附件消息的被动回复、平台的有效期是 60 分钟；0 表示一直等）还没有下文，按 `attachment_timeout_action` 处理：`ask`（默认）发一句「收到 2 张图片，想让我帮你看什么？」，不调用模型，也不写进流水（否则会结束这一轮，用户接着发来的问题就看不到这些附件了）；`answer` 直接回答；`none` 什么都不做。同一组附件只做一次。
- 开轮之前先等这批消息都收完、复查完；接收时没通过复查的文字不会把等待中的附件带着开轮。整条队列里有文字就算有下文，开轮时按到达顺序带上等待中的消息。
- 一轮最多 32 条（与本轮输入能取的上限共用一个常量），多出来的留给下一轮。回答进行中到达、排到下一轮的消息，等这一轮结束后一起作为下一轮。
- 只由表情组成的消息不参加这些规则，见[「表情」](#表情)。

### 轮次的边界

轮次的边界按回复的 `reply_to`：一轮还在生成时，下一轮的消息已经入库，它们的行号比这一轮的回复小，但这一轮并没有看到它们。所以「已经被回复覆盖的消息」是编号不大于某条结束了一轮的回复的 `reply_to` 的那些；历史里每条回复排在它回答的消息之后，而不是按行号排。迁移 V5 为此加了 `(user_id, reply_to)` 上的索引。

## 表情

表情一律忽略：表情标记从文字里去掉，只由表情组成的消息只记进流水，不进模型的输入、不影响轮次（`faces.py`）。

- **表情标记**：认得的形式是 `<faceType=数字` 开头，后面是若干个 `,名字="取值"`（取值里没有引号与尖括号），以 `>` 结尾，整个标记不超过 65536 字（`MAX_MARKER`，只为挡住病态的输入）；属性的顺序与多出来的属性都不影响。实测的样本是 `<faceType=6,faceId="0",ext="eyJ0ZXh0IjoiIn0=">`。`faces.clean()` 把认得的标记直接删掉，不换成任何文字，`ext` 也不解码；认不出的形式原样保留，任何输入都不抛异常。原始标记不进流水与上下文，标记的内容不进日志。
- **只由表情组成**（`faces.is_sticker()`，表情包、单独的小黄脸）：至少有一个认得的标记，去掉标记后没有别的文字，附件都是不被引用的图片且张数不超过标记数。只有标记、没有图片的消息（很可能是单独的小黄脸）也算。文字加表情、去掉标记后还有别的内容的，是普通的消息。
- 这样的消息图片不下载，照常记进流水（正文存空串，`messages.faces_only = 1`），但在 SQL 里就被排除：不进本轮、不进历史、不进决策输入、不占 32 条的名额、不触发回复。一轮的最后一条是表情时，回复挂在最后一条非表情的消息上；都是表情时不回答。可答性判断只看 `faces_only` 这一列。
- 组装模型输入时（对话请求与决策输入），所有文字都再过一遍 `faces.clean()`：用户消息、助手的历史回复、附件的文字版与文件名。升级前存进流水的原始标记也因此不会进模型。
- 旧数据的处理见[迁移 V6](attachments.md)。

## 插话

插话（steer）只在一轮回答进行中考虑：

- 回答还没开始显示（还没有任何东西交给 QQ，包括附件说明与固定说明）时来了新的文字或语音：用一道是非题决策（题目名 `steer`，`routing.STEER_INSTRUCTIONS`）判断它是在补充当前的问题，还是一个新问题。补充（概率不低于 0.5），或判断失败、没有配置 `[decisions]`：打断当前的生成，带上新消息重来，每轮最多 `[turns].max_restarts` 次（默认 3）。新问题：等当前这一轮答完再答。
- **回答已经开始显示时也判断**：长回答显示期间补的一句，等它写完才答要等很久（实测等了约 3 分钟）。判为补充、回答的流式消息已经开始、模型还在写：停下这段回答，在已送达的部分后接一句「收到补充，这段回答先停在这里」并正常结束流式消息，按已送达的部分写回复行（结局 `steered`，送达状态 `interrupted`），这一轮照常结束（话题归属、摘要照常）；新消息紧接着作为下一轮，回复挂在它上面（它有自己的被动回复次数）。QQ 的流式消息只能追加、不能撤回，已显示的部分留着。停下不算重来，不占 `max_restarts`，也不受重来名额的限制。
- 显示中判为新问题，或判断失败、没有配置 `[decisions]`：不停，排到下一轮。代价不对等：还没显示时重来几乎没有代价，显示到一半停下会丢掉一段可能有用的回答，没配决策时每条插话都会打断回答。
- 只显示了固定说明（附件说明等）、回答的流式消息还没开始，或已经在改发纯文本、发固定说明，或模型已经写完只剩发送收尾：不停，排到下一轮。
- 判断期间回答开始显示了、结论是补充：按显示中的规则尝试停下这段回答。
- `max_restarts` 为 0 时完全不考虑插话；已达到重来上限，或这一轮里已有一条判为新问题之后，不再判断，新消息排到下一轮。
- 停下的方式与时限相同：标记后取消读流的任务，只有没有别的取消在进行时才动手，所以与时限至多一个生效；关停或发送出错后停读的取消优先，结局分别记 `cancelled`、`aborted`，都不接说明。停下之后关闭响应流卡住时（时限的看门任务这时已不再管），最多等 3 秒（`GRACE_SECONDS`）就不再等它，免得这一轮收不了尾、补充开不了轮。判为补充却停不下的（见上），这一轮里之后的消息也不再判断。
- 只显示了过程消息不算回答已开始显示，照常可以重来，见[「过程消息的开始与结束」](search-and-process.md#过程消息的开始与结束)。
- 回答进行中到达的单独附件不触发判断：重来时一并带上，否则等下一条文字。
- 重来的名额按这一轮实际带上的待回复消息算（含重启后遗留的），一轮最多 32 条：只有触发打断的那条消息连同它之前到达的消息都装得进重来的请求时才打断，装不下就不打断、排到下一轮，免得重来时挤掉最早的消息或漏掉那条补充。判断插话时看到的也是这一轮实际带上的消息。
- 被打断的生成不写回复行、不改 `given`，这一轮的用户消息仍是待回复的，由重来的那一轮带上。被打断的模型调用与插话判断照常记用量与决策记录（插话判断挂在新消息的最后一条上，`chosen` 为 `supplement` 或 `new`）。

## 排队时的那句回复

回答进行中来的文字或语音最后排到下一轮时（判为新问题、显示中判断失败或停不下、装不下、已不再判断），立刻单独被动回复一句「收到，等上一个问题答完就看这条。」，否则用户没有任何反馈。

- 这句回在正在回答的那条消息上（这一轮回复挂的那条），计进它的被动回复次数，而不是回给新消息：流式消息还没结束时，机器人回复这个用户的另一条消息会让平台提前结束它（pyqbot 实测，40034019，见[「QQ 平台」](external-facts.md#qq-平台)），正在显示的回答就断了；对同一条消息插一条普通回复则不受影响。客户端里它仍显示在用户那条新消息之后。回答进行中给这个用户的其它回复（「暂不支持」、管理员命令等）同样这样处理，见[「已知的薄弱处」](open-questions.md#已知的薄弱处)。
- 一轮只回一次，回给其中最早排队的那条；一轮装不下、留到再下一轮的消息不重复回。重来、停下了正在显示的回答时不回（已有各自的说明；停下之后这一轮里再来的也不回，下一轮紧接着就开始）。
- 发之前复查授权、确认发完仍给回答留着被动回复的余量，否则不发；不进流水、不进上下文、不调用模型。
- 下一轮选定要带上的消息之前，先等这句回复发完，再按那时的队列选，等待期间来的消息也算进那一轮：它回在上一轮的那条消息上，晚于下一轮的流式消息到达会让平台把那条提前结束，也会排在那一轮的「正在输入」与回答之后。最多等 `ACK_WAIT_SECONDS`（45 秒，pyqbot 一次请求的时限是 30 秒），到时取消它，而不是只等一小会儿就放它在后台接着发：那样它仍可能晚于下一轮的流式消息到达。
- 不放进回答里：回答还在流式写，中途插一句会打断正文（可能正在代码块里），放在末尾又太晚，而且会进流水和之后的上下文。

## 关停顺序

`__main__._shut_down()`：

0. 停掉维护任务（心跳、定时备份、磁盘检查、网关检查、到点发提醒、素材库的清理、指令面板的同步）：先发各自的停止请求（正在复制的备份借此放弃、删掉临时文件），再取消任务。放在最前面：数据库只有一个线程，正在做的备份会让排在后面的 Gate 事务与流水写入一直等，耗掉第 6 步的时限，已经放行的消息就可能丢掉；心跳与网关检查不该把之后 `Bot.stop()` 造成的断开写进心跳或拿来告警；到点发提醒经 QQ 的 HTTP 客户端发主动消息，要在第 5 步关闭客户端之前停下（被取消的发送按「可能没送到」记下）。等它们退出放在第 8 步；素材库的清理与指令面板的同步（见 [presentation.md](presentation.md)）除外，它们在第 4 步等。
1. `Batcher.stop()`（同步）放弃等待中的附件、防抖的计时与正在进行的插话判断，取消正在回答的轮次；之后收下的消息只入库、不回答。它排在 `Bot.stop()` 之前，免得等处理函数的那几秒里刚收下的消息又开一轮（发「正在输入」、调用决策）随即被取消。
2. `Bot.stop()`，限时 `BOT_STOP_SECONDS`（5 秒）：断开网关、不再收新事件，等前台的处理函数自然结束（Gate 的决定、写流水、下载附件）；不取消它们，QQ 的 HTTP 客户端照常可用。到期只结束等待、不取消处理函数，还在下载附件的留给第 5 步。
3. 等 `Batcher` 与 `Conversation` 收尾（插话判断的记账、结束分片、写流水与用量）。这一步要在关闭 QQ 客户端之前：回答在 `Batcher` 自己的任务里，pyqbot 不等它们，客户端先关的话结束分片发不出去，用户会一直看到「生成中」。
4. 给管理员的提醒停止并收尾：同步地不再接受新的提醒、取消还在发的，再限时等它们退出；之后再触发的直接丢弃，只记日志。然后等素材库的清理与指令面板的同步退出：它们经 QQ 的 HTTP 客户端发请求，等它们退出之后才能关客户端。
5. `Bot.close()`：取消仍没结束的处理函数（消息在下载之前已经入库，被取消的下载按「没能下载」记），最多等 5 秒，再关 QQ 的 HTTP 客户端。
6. 等接线层「Gate 放行 → 入库」的交接完成（被取消的处理函数仍会把放行的消息写进流水）。
7. 向后台发出停止请求：附件清理、图片描述、话题摘要、下载。这些是同步的、无条件执行，前面用完了时间也照样发出。
8. 限时等后台收尾：清理任务、第 0 步停掉的维护任务、描述与话题摘要的任务和它们受保护的写入、下载，最后关掉回答里的图片下载用的 HTTP 客户端（另给它留 1 秒，总时限用完时也照样关）。之后关模型客户端与数据库。

被放弃的消息已经在流水里，重启后是待回复的消息，等用户发下一条时一并回答。每一步的等待都受保护，再次取消（如连按两次 Ctrl+C）不会打断；所有等待共用 15 秒的总时限（`SHUTDOWN_GRACE_SECONDS`），其中给第 5、6 步留 8 秒，时间用完就跳过剩下的等待（停止请求仍会发出）。信号的接管见 [attachments.md](attachments.md)，容器的停机宽限与线程里的文件操作取消不了的边界见[「部署」](deployment.md)。

## 已知的取舍

- 流式回复中途被平台拒绝、改发纯文本成功时，用户会先看到半截消息再看到完整的，流水只记了后者。
- 防抖或等附件的等待与决策调用不并行，决策在开轮之后才调用。
- 之前遗留的待回复消息加上这一轮超过 32 条时，最早的遗留消息会被这一轮的回复覆盖，之后取不回来。

## 发送记录（已定，还没做）

流水里还有两样用户看到过、却没有记下的东西：流式被拒、改发纯文本之前已经显示的半截，以及分条后第二条及以后的引用索引（见[「长回答分条」](#长回答分条splittingpy)的已知限制）。为此加一张发送记录：

- 一轮里每条被动回复各记一行：过程消息、回答的每一条（分条后各算一条）、改发的纯文本、固定说明、确认卡片与列表、图片。记它属于哪条回复、种类、在这一轮里的顺序、引用索引与送达状态；文字类的消息存用户实际看到的正文。
- 按引用定位改查发送记录：用户引用这一轮的任何一条气泡（含过程消息、第二条以后的分条、卡片）都能找到这一轮的回复与话题，回复行上的 `msg_idx` 不再需要。
- 发送记录随回复一起删（忘掉话题时）。
- 要动的文件与「展示与交互」的优化相同，等那边做完再做；做完后紧接着把迁移合并回 V1，见[「存储与配置」](storage-and-config.md#存储)。其余细节实现时定。
