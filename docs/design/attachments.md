# 附件与多模态

图片、语音、PDF 等附件从下载、识别格式、存放到交给模型的全过程，以及按附件筛选候选模型的规则。表情与表情包的处理见 [conversation.md](conversation.md) 的里程碑 5b。

## 里程碑 5a 定下的细节

模块：

| 模块 | 职责 |
| --- | --- |
| `media.py` | 附件的种类与状态、按文件头识别格式、文字版、本地存放、下载、过期清理 |
| `context.py` | 判断模型能否接收某个附件、按本轮附件筛候选、按模型能力组装请求 |
| `describe.py` | 后台给图片写一句话描述 |

一条带附件的消息的流程：

1. 接线层把 pyqbot 的附件转成本项目的数据。被引用消息里的图片也算（最多往下看 3 层），卡片和转发的聊天记录记为「不支持」。每条消息最多处理 16 个附件。
2. 确认授权后才下载，而且只下有模型用得上的种类。下载经 pyqbot 的 `bot.http_client`，有大小上限和时限；整个进程最多同时下载 4 个。
   - **目的地**：不自动跟随重定向，自己逐跳处理（最多 3 次），每一跳都检查：只认 http(s)、不带用户信息、主机不是 IP 字面量、主机属于 QQ 的下载域名白名单（`qq.com`、`qq.com.cn`、`ugcimg.cn`、`qpic.cn`、`gtimg.cn`，与形态日志共用）。重定向的正文不读。这份白名单是按 2026-11-18 的实测样本和官方文档里的示例整理的，平台的下载主机与域名随时可能变化：
     - 内置的列表在 `bot.PLATFORM_HOSTS`；配置的 `[attachments].extra_download_hosts` 可以追加域名后缀（不替换内置的），下载与形态日志共用合并后的列表。
     - 下载因主机的问题被拒时（不在白名单、是 IP、不是合法的域名，含重定向的每一跳），给管理员发一条提醒：合法域名写主机名，其余只写类别，并注明是哪个用户；不含完整链接、路径、端口和文件名。同一个域名 24 小时内只提醒一次。
   - **不带凭证**：下载请求只有地址，不继承共享客户端的默认请求头、Cookie、查询参数，也不带鉴权头。
   - **边写边数**：按块写进这个用户目录下的临时文件，内存里只留识别格式用的文件头，超过上限就停；识别通过后改名成正式文件。
   - **不收 Cookie**：pyqbot 靠请求头里的 token 鉴权，不用 Cookie，所以启动时给共享客户端装了拒收所有 Cookie 的策略（`refuse_cookies()`），附件服务器设的 Cookie 不会被带到 QQ 的接口请求里。
   - **落盘不用线程**：建临时文件、写盘（每次最多 256 KiB）、关闭、改名、删除都直接在事件循环里同步做，只有网络读取是异步的。这样取消只会发生在网络读取上，每一步文件操作要么做完、要么没开始，描述符只关一次。早先用线程做文件操作时，评审接连找出被取消的写盘线程把数据写进另一个用户的文件、排队中的操作被撤掉导致槽位不归还等问题，所以换成了这种写法；代价是磁盘异常慢时会短暂阻塞事件循环，附件放在本机的 `data/`，可以接受。
   - **已知的限制**：白名单只看主机名，不做 DNS 解析，白名单内的域名若被解析到内网地址（DNS 重绑定）拦不住。要彻底解决需要在连接层校验对端地址，暂时不做。pyqbot 的建议：以后给下载单独配一个校验对端地址的 transport 或客户端（不再与接口请求共用 `bot.http_client`）；走 `socks5h` 代理时域名由代理解析，本地校验不到对端地址。
3. 按文件头判断实际格式：PNG、JPEG、GIF、WebP、HEIC、HEIF、PDF、WAV。平台声明的类型只作初判；认不出的当作不支持，不保存。
4. 存到 `data_dir/attachments/<用户目录名>/<随机名>.<扩展名>`，目录 0700、文件 0600。读文件时一律先按「用户编号 + 消息」查附件表，路径解析后必须仍在这个用户的目录里。用户目录原来用用户编号，2026-11-20 改成随机名，见[「用户目录的命名」](#用户目录的命名2026-11-20)。
5. 写流水（用户消息另存引用索引 `msg_idx`），按本轮附件筛候选模型，必要时先发一条说明，再选模型、组装请求。
6. 回复之后，在后台给本轮的图片写描述。

模型的输入能力（`[[models]].inputs`）：

- 取值是 `image`、`audio`、`file` 的子集，不写就是只收文字。
- OpenAI 的模型不能写 `audio`：Responses API 不接受音频输入（SDK 与文档一致），所以语音对 OpenAI 的模型一律用 QQ 的识别文本。这和最初「模型支持音频就原样给」的设想不同。
- 两家对格式与大小的限制写在 `llm.INPUT_LIMITS`：OpenAI 收 PNG、JPEG、WebP 和 PDF，内联合计 50 MB；Gemini 收 PNG、JPEG、WebP、HEIC、HEIF、WAV 和 PDF，整个请求 20 MB（留 1 MB 给文字）。
- GIF 一律不给模型：OpenAI 只收非动图，本地判断不了是不是动图。

选模型时的能力筛选：

- 必须照顾的是本轮的图片和 PDF：取能接收其中最多的那些模型为候选；一个也接收不了时，候选是全部模型。「能接收」按整轮的内联预算算（`fit()`）：按附件顺序依次放进这家服务商的预算，放不下的不算；候选评分、备用模型、给用户的说明与组装请求都以它为准。
- 每次调用决策、主模型、备用模型之前（发说明、读文件这些等待都结束之后），以及后台每写一张图的描述之前，都在事务里复查一次授权。
- 语音不强制要求音频能力，但候选里有能接收本轮全部语音的模型时，只在它们之中选。
- 候选只剩一个时不调用决策；上一轮的模型不在候选里时，`switch_margin` 不适用。
- 备用模型要能接收选中模型能接收的那些图片和 PDF，否则不换它。
- 没有候选能处理时：图片退回文字版并告诉用户这次看不了；PDF 回「暂不支持」；本轮只剩看不了的内容时只发说明、不调用模型。

内存：整个进程同时最多 3 个会读原件的模型请求（`MULTIMODAL_REQUESTS`），覆盖从读文件、编码到模型回复结束；一次请求里同一份内容会有两三份拷贝，3 个同时在途约占四五百 MiB，给 2G 的机器留出余量。不带附件的请求不受限。

上下文：本轮按选中模型的能力给原件或文字版；还没有回复的用户消息（例如上次关停时留下的）并入本轮，参加候选筛选；给用户的说明以最终的请求为准（实际给了原件的才算），组装时按实际读到的字节扣预算，最终的请求里没有可答内容时只发说明、不调用模型；历史里最近 `[attachments].history_turns` 轮的图片在模型能接收、文件还在时给原件，其余一律文字版；语音和文件在历史里只给文字版。文字版放在方括号里，如「[图片：描述]」「[语音] 识别文本」「[文件：名字，PDF，1.2 MB]」，系统提示词里告诉模型方括号里是附件的说明。

一轮的定义改成「连续的若干条用户消息加上之后的回复」，没有回复的用户消息并进下一轮，为 5b 的攒批做准备。一条回复只有在用户实际收到东西时才算结束了一轮（`journal.ends_turn()`）：正文不为空，或确认送达了固定说明；正文为空的取消、跳过、送达不明等回复行不算，它们回复的消息仍属于下一轮的输入。历史先找到最近一个边界再限量，所以连来很多条只收到说明的消息也不会挤掉上一轮完整的问答。

图片描述（`[describe]`）：同时最多 2 个任务，描述压成一行、最长 300 字；失败只记日志；用量记进用量表，`purpose` 为 `describe`；关停时被取消的保持「待写」，重启后不补。

清理：启动时一次，之后每小时一次。先把超过保存期限的附件行标为 `expired` 并删文件；再删孤儿文件——附件表没有引用、且存在超过一小时的文件，覆盖各种取消路径下没来得及删的文件。`MediaStore.remove_user()` 留给以后的「遗忘」和删除用户。

关停：

- 程序自己接管 SIGINT 与 SIGTERM（`docker stop` 发的是 SIGTERM）：第一次收到就开始有序关停，之后再收到只记一条「正在关停，请稍候」，不打断收尾。Windows 上不接管。
- 顺序（当时的写法，已被后文取代，现行的见 [5b 的「关停顺序」](conversation.md#里程碑-5b-定下的细节)）：`Bot.close()` 取消前台的处理函数 → 等对话自己跟踪的在途轮次收尾并记账（`Conversation.drain()`，因为 pyqbot 只等处理函数 5 秒）→ 向清理、图片描述、下载发出停止请求 → 限时等它们收尾 → 关模型客户端与数据库。
- 等待部分对再次取消有抵抗力，总时限 15 秒，超时记一条警告继续关停；那时仍没写完的记账会丢。

迁移 V4：按 SQLite 的做法重建用量表，`purpose` 加上 `describe`；`messages` 加 `msg_idx`；新表 `attachments`。

配置：`[[models]].inputs`、`[attachments]`（`max_size_mb` 20、`download_timeout_seconds` 30、`retention_days` 30、`history_turns` 3）、`[describe]`（`provider`、`model` 必填）。这些默认值都还没有实测依据。

实测记录（2026-11-18，图片、PDF、音频都在代码里生成）：

| 模型 | 输入 | 结果 | 用量（输入 / 输出） |
| --- | --- | --- | --- |
| `gpt-6.2-sol` | 32×32 的 PNG | 正常结束，13 字 | 31 / 16 |
| `gpt-6.2-sol` | 一页的 PDF | 正常结束，2 字 | 63 / 5 |
| `gemini-4-hydrogen` | 同一张 PNG | 正常结束，28 字 | 1140 / 260 |
| `gemini-4-hydrogen` | 1 秒的 WAV | 正常结束，16 字 | 81 / 262 |
| `gemini-4-hydrogen` | 同一个 PDF | 正常结束，2 字 | 629 / 61 |

- 两家都接受了适配器发出的图片、PDF 与音频的写法（包括 OpenAI 的 PDF 用 data URL 的写法）。
- 这一版实测只检查了「有回答、正常结束」，没有检查回答的内容。PDF 里写的是 42，两家都回了 2 个字，大概率答对了，但没有核对。
- 同一张小图，Gemini 计了约 1100 个输入 token，OpenAI 只有约 30 个，两家对图片的计费方式差别很大。

## 第二次 QQ 实测后的修正

- **表情一律忽略**：`faces.clean()` 直接删掉 `<faceType=…>` 标记，不再换成「[表情]」。只由表情组成的消息（`faces_only = 1`，包括只有标记的小黄脸）照常记进流水、正文存空串，但在 SQL 里就被排除：不进本轮、不进历史、不进决策输入、不占 32 条的名额、不触发回复；一批的最后一条是表情时，回复挂在最后一条非表情的消息上。
- **PDF 前后一致**：
  - PDF 也在后台写摘要，与图片描述共用 `[describe]` 的模型与流程（并发、授权复查、受保护的记账、关停收尾）；只有这家服务商收 PDF、且大小在内联上限内时才写。摘要最多 600 字，存进附件表的 `description`。
  - 附件表的 `given` 列记录这一轮**实际**以原件放进请求的附件，与回复写在同一个事务里：这一轮按 `ends_turn()` 结束了（用户收到了回答或说明，包括正文送达后才被取消的），就按结束这一轮的那次请求重记这一轮所有附件——在那次请求里给了原件的设 1，其余设 0（换了备用模型以备用模型为准）；没有结束这一轮的都设 0。历史里「原图／原声／原文在当时那一轮已经给过你」只在 `given = 1` 时才写，后面接描述、识别文字或摘要；没有记录的照旧用当时的文字版。主模型收了原件但出错、又没有可换的备用模型时，也算给过。
  - 系统提示词告诉模型：历史里写着原件当时给过你的，不要否认看过。
- **语音按内容选模型**：去掉了「本轮有语音时只在能听的模型里选」的规则，语音不影响候选。决策用 Gemini 时把本轮的语音原声（WAV）连同题目一起交给它（`DECISION_INPUT_LIMITS`：OpenAI 的决策什么媒体都不收，Gemini 只收 WAV，19 MiB 以内）；用 OpenAI 时只看题目里的识别文字。选中能听的模型给原声，选中听不了的给识别文字。没有识别文字、但原声已下载的语音，和图片、PDF 一样算必须照顾的附件：候选（与备用模型）要能听它，免得同批的文字让听不了的模型把它「答掉」。带语音的决策从读原声到结束都占一个多模态名额。
- 迁移 V6（Python 函数）：附件表加 `description`、`given`；从旧的文字版里回填已写好的图片描述；V5 误记为「只有表情」的带附件消息改回普通消息，并去掉 V5 生成的「[表情]」字样；V4 时期带原始标记的表情包重新识别为「只有表情」并清空正文。

## 用户目录的命名（2026-11-20）

用户不想用数字目录名：编号一旦被复用，新用户可能继承旧用户的附件目录。程序里还没有删除用户，但有一条今天就能走到的路：从备份恢复数据库后，编号的计数器跟着回退，盘上的目录却还在，下一个新用户会拿到同一个编号、同一个目录。方案由 Fable 5.2 提出，用户选了随机名（2026-11-20 决定）：

- **目录名**：`users` 表新加 `media_dir` 列（`TEXT NOT NULL UNIQUE`），建用户时取 `secrets.token_hex(16)`（32 位十六进制），与附件文件名、邀请码的做法一致。目录名不带任何信息，永不复用。openid 是隐私，不进路径。
- **编号**：`users.id` 改成 `AUTOINCREMENT`，删除后不再复用。
- **新用户的目录检查**：生成 `media_dir` 时，如果 `attachments/<名字>` 已经存在（随机名下理论上不会发生），换一个名字重新生成，最多 5 次，不删除任何东西（评审后改：原来写的「建好后删掉已有的目录」会和这个用户刚开始写的附件撞上）。
- **附件表只存文件名**：`attachments.path` 只存文件名，目录由这个用户的 `media_dir` 决定；`MediaStore` 拒绝含路径分隔符或 `..` 的文件名，一行附件无论如何指不到别人的目录。
- **迁移 V16**（Python 函数，一个事务）：
  - 按 V14 的写法重建 `users`，加 `AUTOINCREMENT` 与 `media_dir`，按原编号复制，每行生成目录名。
  - `attachments.path` 去掉 `<编号>/` 前缀，先校验每一行的前缀确实是它自己的 `user_id/`，不符就让迁移失败、拒绝启动，不猜。
  - 迁移前的自动备份见[「部署」的「备份」](deployment.md#备份)。
- **搬目录**：V16 在同一个事务里把迁移时已有的每个用户登记进 `media_relocations`（`user_id → media_dir`）。启动时，在数据库打开之后、清理任务启动与开始收消息之前，只对这张表里的用户幂等地把旧的数字目录搬到新名字，搬完一个删掉一行；新用户永远不进这张表（否则从旧备份恢复后，新用户可能拿到一位已不在库里的用户的编号，接手他的数字目录）：
  - 只有旧目录时整体改名；
  - 两个都在（上次搬到一半）时逐个文件移过去，再删掉空的旧目录；
  - 新旧目录里有同名文件时，内容完全相同就删掉旧的那份；内容不同（或同名的不是普通文件）就一个都不动。
  - 改名或合并之后先 fsync 受影响的目录，确认落盘才删待搬记录。
  - 没搬完（同名冲突、旧目录或新目录是符号链接或不是目录、附件根目录不安全、出错）就拒绝启动，日志写明用户编号、原因与新旧目录名，待搬记录保留，处理好之后重启接着搬（第二轮评审后改：原来部分情况只记警告、照常运行，原件留在数字目录里，用户遗忘话题时删不到它）。
  - 数据库先提交、后搬文件：有待搬的行时先做一次 WAL 检查点，确认迁移已经落盘再改名（`synchronous=NORMAL` 下断电可能丢掉刚提交的事务）。任何一步崩溃，下次启动都会重做。
- **无主目录**（用户决定：过宽限期后删除）：后台清理时，附件根目录下名字是 32 位十六进制或全数字、又不属于任何用户的目录，其中最新的修改时间（目录本身与里面的文件取最新）早于附件的保留期（`[attachments]` 的过期天数），就整个删掉。其它名字的目录与符号链接不碰；`media_relocations` 里还有的用户，他的数字目录算有主（没搬完的不能删）；递归遍历出错或判断不了的目录跳过，候选目录本身或里面某一层是挂载点（`st_dev` 与附件根目录不同）的也跳过，不删任何东西。这一条收掉从备份恢复后留下的目录、以后删除用户没删干净的目录，以及迁移前留下的数字目录。必须在搬目录完成后才运行。
- **管理员排查**：列出用户的管理命令里显示每个用户的目录名（不是秘密）。
- **已知的边界**：从 V16 之前的备份恢复时，迁移会重跑并生成新的目录名，已经搬过的随机目录对不上，这部分附件原件找不回，历史里退回文字版（与附件过期后的表现相同），之后按无主目录删除。写进部署说明。

实现时定下的细节（2026-11-20）：

- `users.media_dir` 另加 `CHECK`（32 位小写十六进制），多一道防线；迁移 V16 用 `media.valid_filename` 校验去掉前缀后的文件名，以 `.` 开头、含反斜杠或 NUL 的也让迁移失败。
- `ensure_user` 改成先查后插：`AUTOINCREMENT` 下被 `ON CONFLICT DO NOTHING` 忽略的插入也会占掉一个编号，管理员每条消息都会走到这里，编号会一直跳。
- 新用户的目录检查：存储层 `access.new_media_dir(conn, dir_taken)` 跳过已被别的用户用过的名字和 `dir_taken` 说已被占用的名字，5 次都不行就抛 `MediaDirUnavailableError`，整个事务回滚、邀请次数不扣。`dir_taken` 由接线层注入（`MediaStore.dir_taken`，先看附件根目录：不存在时照常往下判断，是符号链接、不是目录或无权访问就一律按已占用；再用 `lstat` 看候选名：只有「不存在」返回假，无权访问、悬空的符号链接、普通文件都按已占用），存储层不碰文件系统。附件根目录无权访问时建不了新用户，这是故意的。换下来的旧管理员重新兑换邀请时沿用原来那一行、目录名不变。
- `MediaStore` 的方法一律由调用方传入目录名；目录名不合法时，读与删当作不存在，写抛 `UnsafeDirectoryError`。文件名拒绝以 `.` 开头、含 `/`、`\`、`..` 或 NUL 的，并要求解析后直接位于用户目录里；临时文件只能经 `commit` 与 `discard_temp` 处理。
- 搬目录（`media.relocate_user_dirs`）在数据库打开之后、构造 `Bot` 之前，逐个用户放进线程里做；检查点没做成、无权访问（用 `lstat` 区分「不存在」与「无法访问」）、fsync 失败或没搬完时抛 `RelocationError`，按「数据库有误」退出，文案有用户编号、原因与新旧目录名（目录名不是秘密，运维者靠它找到目录），不含完整路径与文件名。
- 无主目录的最新修改时间取目录本身与里面全部内容（递归、不跟随符号链接）中最新的；删掉的目录数单独记一条日志。
- `/users` 每行末尾显示「附件目录 <目录名>」。
