# 附件与多模态

图片、语音、PDF 等附件从下载、识别格式、存放到交给模型的全过程，以及按附件筛选候选模型的规则（里程碑 5a）。表情与表情包的处理见 [conversation.md](conversation.md#表情)。

## 模块与流程

| 模块 | 职责 |
| --- | --- |
| `media.py` | 附件的种类与状态、按文件头识别格式、文字版、本地存放、下载、过期清理 |
| `context.py` | 判断模型能否接收某个附件、按本轮附件筛候选、按模型能力组装请求 |
| `describe.py` | 后台给图片写简短的描述、给 PDF 写摘要 |

一条带附件的消息：

1. 接线层把 pyqbot 的附件转成本项目的数据。被引用消息里的图片也算（最多往下看 3 层），卡片和转发的聊天记录记为「不支持」。每条消息最多处理 16 个附件。
2. 收消息时先在事务里复查授权、写入用户消息（另存引用索引 `msg_idx`）与附件占位（先记为下载失败），再去下载并改写占位，见 [conversation.md](conversation.md#收消息与回答分开)。只下有模型用得上的种类。
3. 按文件头判断实际格式，存进这个用户的目录。
4. 开轮时按本轮附件筛候选模型（没有可答内容时只发说明），再选模型、组装请求，按实际的请求发附件的说明。
5. 回复之后，在后台给本轮的图片写描述、给 PDF 写摘要。

## 下载与白名单

下载经 pyqbot 的 `bot.http_client`（`[qq].proxy` 因此对下载同样生效），有大小上限和时限；平台声明的大小已经超过上限就不下载。整个进程最多同时下载 4 个。

- **目的地**：不自动跟随重定向，自己逐跳处理（最多 3 次），每一跳都检查：只认 http(s)、不带用户信息、主机不是 IP 字面量、主机属于 QQ 的下载域名白名单（`qq.com`、`qq.com.cn`、`ugcimg.cn`、`qpic.cn`、`gtimg.cn`，与形态日志共用）。重定向的正文不读。这份白名单是按 2026-11-18 的实测样本和官方文档里的示例整理的，平台的下载主机与域名随时可能变化：
  - 内置的列表在 `bot.PLATFORM_HOSTS`；配置的 `[attachments].extra_download_hosts` 可以追加域名后缀（不替换内置的），下载与形态日志共用合并后的列表。
  - 下载因主机的问题被拒时（不在白名单、是 IP、不是合法的域名，含重定向的每一跳），给管理员发一条提醒：合法域名写主机名，其余只写类别，并注明是哪个用户；不含完整链接、路径、端口和文件名。同一个域名 24 小时内只提醒一次。提醒模块见[「部署与运维」](deployment.md)。
- **不带凭证**：下载请求只有地址，不继承共享客户端的默认请求头、Cookie、查询参数，也不带鉴权头。
- **不收 Cookie**：pyqbot 靠请求头里的 token 鉴权，不用 Cookie，所以启动时给共享客户端装了拒收所有 Cookie 的策略（`refuse_cookies()`），附件服务器设的 Cookie 不会被带到 QQ 的接口请求里。
- **边写边数**：按块写进这个用户目录下的临时文件，内存里只留识别格式用的文件头，超过上限就停；识别通过后改名成正式文件，否则删掉。单个附件下载或落盘失败只算这一件失败；日志只记异常类型或原因的分类，不记地址。
- **落盘不用线程**：建临时文件、写盘（每次最多 256 KiB）、关闭、改名、删除都直接在事件循环里同步做，只有网络读取是异步的。这样取消只会发生在网络读取上，每一步文件操作要么做完、要么没开始，描述符只关一次。用线程做文件操作时，被取消的写盘线程可能把数据写进另一个用户的文件，排队中的操作被撤掉会导致槽位不归还。代价是磁盘异常慢时会短暂阻塞事件循环，附件放在本机的 `data/`，可以接受。
- **已知的限制**：白名单只看主机名，不做 DNS 解析，白名单内的域名若被解析到内网地址（DNS 重绑定）拦不住。要彻底解决需要在连接层校验对端地址，暂时不做。可行的做法（pyqbot 的建议）：给下载单独配一个校验对端地址的 transport 或客户端（不再与接口请求共用 `bot.http_client`）；走 `socks5h` 代理时域名由代理解析，本地校验不到对端地址。

## 识别格式

按文件头判断实际格式：PNG、JPEG、GIF、WebP、HEIC、HEIF、PDF、WAV。平台声明的类型只作初判，实际的种类也以文件头为准（以文件发来的 PNG 是图片，标成图片的 PDF 是文件）；认不出的当作不支持，不保存。

## 存放与用户目录

存到 `data_dir/attachments/<用户目录名>/<随机名>.<扩展名>`，目录 0700、文件 0600。文件名由程序生成，不用原始文件名。读文件时一律先按「用户编号 + 消息」查附件表，路径解析后必须仍在这个用户的目录里。

用户目录名用随机名，不用用户编号：编号一旦被复用，新用户可能继承旧用户的附件目录。程序里还没有删除用户，但有一条今天就能走到的路：从备份恢复数据库后，编号的计数器跟着回退，盘上的目录却还在，下一个新用户会拿到同一个编号、同一个目录。

- **目录名**：`users.media_dir`（`TEXT NOT NULL UNIQUE`，另加 `CHECK` 要求 32 位小写十六进制，多一道防线），建用户时取 `secrets.token_hex(16)`，与附件文件名、邀请码的做法一致。目录名不带任何信息，永不复用。openid 是隐私，不进路径。
- **编号**：`users.id` 是 `AUTOINCREMENT`，删除后不再复用。`ensure_user` 因此先查后插：`AUTOINCREMENT` 下被 `ON CONFLICT DO NOTHING` 忽略的插入也会占掉一个编号，管理员每条消息都会走到这里，编号会一直跳。
- **新用户的目录检查**：存储层 `access.new_media_dir(conn, dir_taken)` 跳过已被别的用户用过的名字和 `dir_taken` 说已被占用的名字（随机名下理论上不会发生），换一个重新生成，最多 5 次，都不行就抛 `MediaDirUnavailableError`，整个事务回滚、邀请次数不扣。不删除任何东西：删掉已有的目录会和这个用户刚开始写的附件撞上。
  - `dir_taken` 由接线层注入（`MediaStore.dir_taken`），存储层不碰文件系统：先看附件根目录，不存在时照常往下判断，是符号链接、不是目录或无权访问就一律按已占用；再用 `lstat` 看候选名，只有「不存在」返回假，无权访问、悬空的符号链接、普通文件都按已占用。附件根目录无权访问时建不了新用户，这是故意的。
  - 换下来的旧管理员重新兑换邀请时沿用原来那一行、目录名不变。
- **附件表只存文件名**：`attachments.path` 只存文件名，目录由这个用户的 `media_dir` 决定，一行附件无论如何指不到别人的目录。
- **`MediaStore` 的边界**：方法一律由调用方传入目录名；目录名不合法时，读与删当作不存在，写抛 `UnsafeDirectoryError`。文件名拒绝以 `.` 开头、含 `/`、`\`、`..` 或 NUL 的，并要求解析后直接位于用户目录里；临时文件只能经 `commit` 与 `discard_temp` 处理。附件根目录或用户目录本身是符号链接时，读、写、删一律拒绝。
- **管理员排查**：`/users` 每行末尾显示「附件目录 <目录名>」（目录名不是秘密）。

### 无主目录

后台清理时，附件根目录下名字是 32 位十六进制、又不属于任何用户的目录，过了宽限期就整个删掉：

- 宽限期是附件的保留期（`[attachments].retention_days`）：目录的最新修改时间早于它才删。最新修改时间取目录本身与里面全部内容（递归、不跟随符号链接）中最新的。
- 其它名字的目录与符号链接不碰。
- 递归遍历出错或判断不了的目录跳过；候选目录本身或里面某一层是挂载点的也跳过，不删任何东西：Linux 上按 `/proc/self/mountinfo` 认（同一文件系统内的绑定挂载设备号相同，只比 `st_dev` 认不出），另外逐层比较 `st_dev`，读不到 mountinfo 时只剩后者。
- 这一条收掉从备份恢复后留下的目录与以后删除用户没删干净的目录。删掉的目录数单独记一条日志。

## 模型的输入能力

`[[models]].inputs`：

- 取值是 `image`、`audio`、`file` 的子集，不写就是只收文字。
- OpenAI 与 Claude 的模型不能写 `audio`：Responses API 不接受音频输入（SDK 与文档一致），Claude 的 Messages API 也没有音频的内容块（SDK 的类型里没有），所以语音对这两家的模型一律用 QQ 的识别文本，「模型支持音频就原样给」只对 Gemini 成立。
- 各家对格式与大小的限制写在 `llm.INPUT_LIMITS`：OpenAI 收 PNG、JPEG、WebP 和 PDF，内联合计 50 MiB；Gemini 收 PNG、JPEG、WebP、HEIC、HEIF、WAV 和 PDF，整个请求 20 MB（取 19 MiB，留 1 MB 给文字）；Claude 收 PNG、JPEG、WebP 和 PDF，单张图片按 base64 计取 10,000,000 字节，内联合计取与 OpenAI 相同的 50 MiB（接口的上限见[「查证过的外部事实」的「Claude」](external-facts.md#claude)；合计取保守值是为了让同时在途的请求不超出内存的估算）。
- 单张图片的上限写在 `InputLimits.max_image_bytes`（只有 Claude 有），判断单个附件放不放得下时用 `InputLimits.item_limit()`：内联合计的上限，图片再取它与单图上限中小的那个。候选筛选（`context.accepts()` 与 `fit()`）、实际读到原件时、给用户的「太大」说明（按单件上限折算）、写描述与摘要的模型（`describe.accepts()`）都按它判断；Claude 的适配器自己也兜底，超过单图上限或类型不在 `INPUT_LIMITS` 里时不发请求。
- GIF 一律不给模型：OpenAI 只收非动图，Claude 的动图只取第一帧（见[「查证过的外部事实」的「Claude」](external-facts.md#claude)），本地判断不了是不是动图。

## 候选筛选

- 必须照顾的是本轮的图片和 PDF，以及原声已下载、却没有识别文字的语音：取能接收其中最多的那些模型为候选；一个也接收不了时，候选是全部模型。「能接收」按整轮的内联预算算（`fit()`）：按附件顺序依次放进这家服务商的预算，放不下的不算；候选评分、备用模型、给用户的说明与组装请求都以它为准。没有识别文字的语音这样算，是免得同批的文字让听不了的模型把它「答掉」。
- **语音按内容选模型**：有识别文字的语音不影响候选。决策用 Gemini 时把本轮的语音原声（WAV）连同题目一起交给它（`DECISION_INPUT_LIMITS`：OpenAI 的决策什么媒体都不收，Gemini 只收 WAV，19 MiB 以内）；用 OpenAI 时只看题目里的识别文字。选中能听的模型给原声，选中听不了的给识别文字。带语音的决策从读原声到结束都占一个多模态名额。
- 候选只剩一个时不问选模型那道题；上一轮的模型不在候选里时，`switch_margin` 不适用。见[「选模型」](model-routing.md)。
- 备用模型要能接收选中模型能接收的那些必须照顾的附件，否则不换它。
- 没有候选能处理时：图片退回文字版并告诉用户这次看不了；PDF 回「暂不支持」；本轮只剩看不了的内容时只发说明、不调用模型。
- 每次调用决策、主模型、备用模型之前（发说明、读文件这些等待都结束之后），以及后台每写一张图的描述之前，都在事务里复查一次授权。

## 交给模型的方式

- **本轮**按选中模型的能力给原件或文字版；还没有回复的用户消息（例如上次关停时留下的）并入本轮，参加候选筛选。给用户的说明以最终的请求为准（实际给了原件的才算），组装时按实际读到的字节扣预算，最终的请求里没有可答内容时只发说明、不调用模型。
- **历史**里最近 `[attachments].history_turns` 轮的图片在模型能接收、文件还在时给原件，其余一律文字版；语音和文件在历史里只给文字版。分话题时按合成后的各轮算，见 [memory.md](memory.md)。原件按「当前这一轮优先、历史从新到旧」占用服务商的内联上限，放不下的退回文字版。
- **文字版**放在方括号里，如「[图片：描述]」「[语音] 识别文本」「[文件：名字，PDF，1.2 MB]」，系统提示词里告诉模型方括号里是附件的说明。
- **原件当时给过**：附件表的 `given` 列记录这一轮**实际**以原件放进请求的附件，与回复写在同一个事务里：这一轮按 `ends_turn()` 结束了（用户收到了回答或说明，包括正文送达后才被取消的），就按结束这一轮的那次请求重记这一轮所有附件——在那次请求里给了原件的设 1，其余设 0（换了备用模型以备用模型为准）；没有结束这一轮的都设 0。主模型收了原件但出错、又没有可换的备用模型时，也算给过。历史里「原图／原声／原文在当时那一轮已经给过你」只在 `given = 1` 时才写，后面接描述、识别文字或摘要；没有记录的照旧用当时的文字版。系统提示词告诉模型：历史里写着原件当时给过你的，不要否认看过。
- **一轮**是连续的若干条用户消息加上之后的回复，没有回复的用户消息并进下一轮。一条回复只有在用户实际收到东西时才算结束了一轮（`journal.ends_turn()`）：正文不为空，或确认送达了固定说明、附件的说明或模型画的图；正文为空的取消、跳过、送达不明等回复行不算，它们回复的消息仍属于下一轮的输入。历史先找到最近一个边界再限量，所以连来很多条只收到说明的消息也不会挤掉上一轮完整的问答。轮次边界按回复的 `reply_to` 判断，见[「轮次的边界」](conversation.md#轮次的边界)。
- **内存**：整个进程同时最多 3 个会读原件的模型请求（`MULTIMODAL_REQUESTS`），覆盖从读文件、编码到模型回复结束；一次请求里同一份内容会有两三份拷贝，3 个同时在途约占四五百 MiB，给 2G 的机器留出余量。不带附件的请求不受限。

## 图片描述与 PDF 摘要

由 `[describe]` 的模型在后台写，图片与 PDF 共用一套流程：

- 同时最多 2 个任务；失败只记日志；用量记进用量表，`purpose` 为 `describe`；关停时被取消的保持「待写」，重启后不补。
- 图片描述：提示词（`[describe].instructions`）要求客观描述、不超过 200 字，图里有文字时把关键的文字与数字摘录在「」里。原图只在最近 `[attachments] history_turns` 轮里带着，之后模型只剩这段描述，截图、文档照片这类以文字为主的图要靠它留住内容，所以给到 200 字。程序把描述压成一行、最长 300 字（`media.DESCRIPTION_CHARS`），高出提示词的上限，正常的描述不会被截断。
- PDF 也写摘要，免得历史里只剩「[文件：名字，PDF，0.8 MB]」时模型以为自己从没读过它；只有这家服务商收 PDF、且大小在内联上限内时才写。摘要最多 600 字。
- 描述与摘要存进附件表的 `description`，并换掉附件的文字版。

## 清理

启动时一次，之后每小时一次：

1. 把超过保存期限的附件行标为 `expired` 并删文件（模型画的图同样按保存期限清理）。
2. 删孤儿文件：附件表没有引用、且存在超过一小时的文件，覆盖各种取消路径下没来得及删的文件。
3. 删无主目录，见上面的[「无主目录」](#无主目录)。

`MediaStore.remove_user()` 能整个删掉一个用户的目录，留给以后的删除用户。

## 关停

程序自己接管 SIGINT 与 SIGTERM（`docker stop` 发的是 SIGTERM）：第一次收到就开始有序关停，之后再收到只记一条「正在关停，请稍候」，不打断收尾。Windows 上不接管。等待部分对再次取消有抵抗力，总时限 15 秒，超时记一条警告继续关停；那时仍没写完的记账会丢。关停的顺序见[「关停顺序」](conversation.md#关停顺序)。

## 表与配置

- **表** `attachments`：每个附件一行，挂在它所属的那条消息上（多是用户消息；模型画的图挂在回复上，见[「生成图片」](image-generation.md)）；`path` 只存文件名，`description` 是图片描述或 PDF 摘要本身（不带标签），`given` 记原件是否在结束那一轮的请求里实际交给过模型。用户消息的引用索引在 `messages.msg_idx`。列与约束以 `storage.py` 里的注释为准。
- **配置**：`[[models]].inputs`、`[attachments]`（`max_size_mb` 20、`download_timeout_seconds` 30、`retention_days` 30、`history_turns` 3、`extra_download_hosts`）、`[describe]`（`provider`、`model` 必填）。这些默认值都还没有实测依据。

## 实测记录（2026-11-18）

图片、PDF、音频都在代码里生成：

| 模型 | 输入 | 结果 | 用量（输入 / 输出） |
| --- | --- | --- | --- |
| `gpt-6.2-sol` | 32×32 的 PNG | 正常结束，13 字 | 31 / 16 |
| `gpt-6.2-sol` | 一页的 PDF | 正常结束，2 字 | 63 / 5 |
| `gemini-4-hydrogen` | 同一张 PNG | 正常结束，28 字 | 1140 / 260 |
| `gemini-4-hydrogen` | 1 秒的 WAV | 正常结束，16 字 | 81 / 262 |
| `gemini-4-hydrogen` | 同一个 PDF | 正常结束，2 字 | 629 / 61 |

- 两家都接受了适配器发出的图片、PDF 与音频的写法（包括 OpenAI 的 PDF 用 data URL 的写法）。
- 这一版实测只检查了「有回答、正常结束」，没有检查回答的内容。PDF 里写的是 42，两家都回了 2 个字，大概率答对了，但没有核对。
- 同一张小图，Gemini 计了约 1100 个输入 token，OpenAI 只有约 30 个，两家对图片的计费方式差别很大。
