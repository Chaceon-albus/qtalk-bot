连真实平台与真实模型做的实测：QQ 端到端实测的各次记录、搜索与过程展示的模型实测，以及还需要实测的事。只涉及一个模块的实测记在那个模块的文件里（如里程碑 3、4、5a）。

## QQ 端到端实测记录

2026-11-18 第一次连接真实平台，管理员一人操作，按消息选模型开启。

功能：

| 项目 | 结果 |
| --- | --- |
| `/help`、`/usage`、`/invite` | 正常；带邀请链接的消息没有被平台拒绝 |
| 对话 | 5 轮，全部 `completed / streamed`，单轮 5–19 秒 |
| 按消息选模型 | 有效：按话题在 `sol` 与 `hydrogen` 之间切换了 3 次；单次 208–782 毫秒，紧接上一条时最快，隔了一阵的第一条较慢 |

收到的消息的真实形态（只记元信息，见 `bot.py` 的形态日志）。表里的主机名只是这一次观察到的，平台随时可能换用别的主机或域名，不能当作固定值写进逻辑；代码里只依赖域名后缀的白名单，见下文。

| 种类 | `content_type` | 扩展名 | 地址的主机 | 其它 |
| --- | --- | --- | --- | --- |
| 图片 | `image/jpeg` | `png` | `multimedia.nt.qq.com.cn` | 带宽高；类型与扩展名不一致 |
| 语音 | `voice` | `amr` | `multimedia.nt.qq.com.cn` | `voice_wav_url` 在 `qqbot.ugcimg.cn`；带 `asr_refer_text`（QQ 自己的识别结果） |
| 文件 | `file` | `pdf` | `grouptalk.c2c.qq.com` | 单聊里能收到文件，但类型只写 `file` |
| 表情包 | `image/gif` | `png` | `multimedia.nt.qq.com.cn` | 以图片附件到达，同时带一段 46 字的文字，所以现在每个表情包都会触发一次回复 |
| 引用 | — | — | — | `message_type=103`，`msg_elements` 里带被引用消息的文字与附件 |

对里程碑 5、6 的影响：

- 附件的 `content_type` 和扩展名都不可信，下载后要按文件内容判断格式。
- 语音有两条路：直接用 QQ 的识别文本（不花钱），或下载 WAV 交给模型或转写接口。
- 这次三种附件在三个不同的主机上。具体主机会变，下载只能按域名后缀放行，并且要能在日志里看出「主机不在白名单里」的失败，以便及时补充白名单。
- 表情包要单独识别，不能每个都回复。它附带的文字（经用户同意，从本地流水里查看了那一条）是一个表情标记：`<faceType=6,faceId="0",ext="eyJ0ZXh0IjoiIn0=">`，其中 `ext` 是 base64 编码的 JSON，这次解出来是 `{"text":""}`。所以识别规则是：文字里的 `<faceType=…>` 标记换成「[表情]」（`ext` 里的 `text` 不为空时用它）；去掉标记后没有别的文字、只剩表情图片的消息就是表情包。QQ 的小黄脸等系统表情很可能也用同样的标记（`faceType` 不同），未实测。现在的版本会把这段标记原样发给模型。
- 按引用定位话题时要把消息与被引用的内容对上，需要另存每条消息的引用索引（`msg_idx` / `ref_idx`），当时流水里没有（后来[里程碑 5a](attachments.md#里程碑-5a-定下的细节)、[6a](memory.md#里程碑-6a-定下的细节) 加上了，见那里）。
- 文件「合集」（一次发多个文件）以一条普通文字消息到达：`message_type=0`，没有附件，文字是「闪传」卡片的标题（如「……等 2 项文件」），所以没有触发形态日志，而是走了对话流程，模型回复说看得到标题、打不开文件。要支持它，得先弄清闪传的内容能不能通过接口取到。优先级低。
- 机器人目前没有公开，经分享链接添加用户这一步暂时没法实测。

### 第三次（2026-11-19，话题线）

管理员一人操作，`gpt-6.2-sol`（推理强度 high、开搜索与过程展示）为默认模型，话题线与后台摘要（`gpt-6-luna`，推理强度 high）开着：

| 项目 | 结果 |
| --- | --- |
| 对话 | 7 轮，全部 `completed / streamed`，全程没有警告 |
| 话题 | 前三个问题各判为新话题（0.99）；之后一句含糊的追问判回话题 1（0.98）；引用旧回答的那轮没问话题题，按引用直接定到话题 1。每轮结束后 2–4 秒写好标题与摘要 |
| 过程消息 | 带搜索的几轮各 4–8 片、说明 2 段、搜索 2–3 次 |
| 长回答 | 两轮各约 6000 字、写了约 3 分钟，都正常写完 |
| 插话 | 长回答显示期间补的一句没有判断（当时的规则），等这段写完才作为下一轮回答，归到同一话题（0.98） |

用户反馈与后续：

- 过程消息的 Markdown 引用在流式消息结束之前显示成原样的 `>`；搜索的「正在搜索」「搜索完成」两行不好看 → 改成纯文本、搜索写成进度式的一行（见 [7b 的细节](search-and-process.md#里程碑-7b-定下的细节)）。
- 长回答在客户端被拆成两条，衔接生硬；pyqbot 不拆、接口也没报错，是平台自己拆的 → 已请 pyqbot 实测拆分的规则（见[「需要实测」](#需要实测)），之后在接近上限时按段落边界主动另起一条。
- 显示中的插话要等回答写完 → 改成显示中也判断（见 [5c 的细节](conversation.md#里程碑-5c-定下的细节)）。

### 第四次（2026-11-19，过程消息纯文本与显示中插话）

同样的配置，验证纯文本的过程消息与显示中插话：

| 项目 | 结果 |
| --- | --- |
| 对话 | 5 轮回复、1 次插话重来，没有其它警告 |
| 过程消息 | 纯文本、每次搜索一行，用户认可；但每一条的结束分片都被平台拒绝（`err_code` 40034019，5 次中 5 次），以前用 Markdown 发时没有 |
| 还没显示时插话 | 判为补充，取消生成、带上新消息重来 |
| 显示中插话 | 判为补充，停下回答（`steered / interrupted`），补充紧接着作为下一轮，归到同一话题（0.98） |
| 显示中的新问题 | 判为新问题，排到下一轮，答完后接着答 |

用户反馈与后续：

- 排到下一轮时用户没有任何反馈 → 给新消息单独回一句（见 [5c 的细节](conversation.md#里程碑-5c-定下的细节)）。
- 过程消息的结束分片被拒 → pyqbot 查清是时序问题：回答流在过程消息结束之前就开了（见[「QQ 平台」](external-facts.md#qq-平台)）；改为先等过程消息结束再开回答流（见 [7b 的细节](search-and-process.md#里程碑-7b-定下的细节)）。
- 长回答被平台拆开 → 主动分条（见[「长回答分条」](conversation.md#长回答分条splittingpy)）。

### 第五次（2026-11-19，主动分条与排队时的那句收到）

同样的配置，验证主动分条、排队时的那句收到、回答进行中的 Gate 回复，以及先等过程消息结束再开回答流：

| 项目 | 结果 |
| --- | --- |
| 对话 | 4 轮，全部 `completed / streamed`，除了关停时的 SIGTERM 没有其它警告 |

## 搜索与过程展示的模型实测（2026-11-19）

问的都是需要联网的天气问题：

| 项目 | `gpt-6.2-sol` | `gemini-4-hydrogen` |
| --- | --- | --- |
| 搜索（问今天的日期和上海天气） | 2 次搜索调用，其中 1 次是 `search`（计 1 次），另一次没有查询词；引用 1 条 | 2 次搜索调用、4 个查询词（计 4 次）；引用 6 条 |
| 过程（比较今明两天哪天适合跑步） | 推理强度不设时：思考摘要 0 段、说明 2 段、搜索 2 次；`reasoning = "high"` 时：思考摘要 1 段（标题是英文） | 思考摘要 5 段（标题都是英文，如「Assessing Shanghai Weather」）、搜索计 11 次 |
| 用量 | 输入约 1 万到 2.3 万个 token（搜索结果算进输入） | 输入只有几百个 token，输出 2700–4400（含思考） |

观察：

- OpenAI 的 `phase` 在 `added` 时就有，[里程碑 7b](search-and-process.md#里程碑-7b-定下的细节) 里的待定点已解决。
- OpenAI 的思考摘要很稀疏：不设推理强度时没有，`high` 时也只有一段；说明（`commentary`）在提示词要求下会出现。没有遇到组织验证的拒绝。过程展示对 OpenAI 来说主要是「说明 + 搜索」。
- 两家的思考摘要标题都是英文。之后在提示词里要求「思考也用与用户相同的语言、小标题用中文」再测一次：OpenAI 的摘要仍是英文（「Considering tool usage」），Gemini 的也仍是英文（「Analyzing Weather Prediction」），说明摘要的语言不受提示词控制，这句已从提示词里去掉。调用工具前的说明（`commentary`）则听提示词：要求「使用与用户相同的语言」后是中文，如「我先查上海今天和明天的天气，重点看气温、降雨和风力。」「查到了：上海市区两天都预计无雨，周六白天更暖。」
- Gemini 很爱搜索：一个问题计费 11 次查询（免费额度用完后约 0.15 美元），OpenAI 一般 1–4 次。
- Gemini 的引用链接都是 `vertexaisearch.cloud.google.com` 的跳转链接，打开后才跳到真正的来源；它们可能有有效期。
- Gemini 的输入 token 明显偏少：搜索结果占用的 token（`total_tool_use_tokens`）没有计入，用量会低估。

## 需要实测

实测前按 `AGENTS.md` 先取得用户同意。

- 附件地址的有效期：过多久就下载不到了。
- QQ 的小黄脸等系统表情以什么形式到达，是否也是 `<faceType=…>` 标记、带不带图片附件。
- 单聊消息里的昵称字段有没有值。官方示例里是空串，pyqbot 的样本里有值，但可能是脱敏后的占位。
- 单条消息的长度上限，长回复要不要拆条。
- 已是好友的人点邀请链接、机器人离线时有人添加，这两种情况会不会收到 `FRIEND_ADD`。
- 回答里带任意网站的引用链接时，平台会不会拒发。
- 「正在输入」每次请求 8 秒、有进展再请求，在手机上看起来是否自然。
