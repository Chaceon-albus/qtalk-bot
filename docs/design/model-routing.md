# 选模型

用 Decisions API 按消息选对话模型（里程碑 4）：模块、配置、选择规则、失败时的退路、坏响应的判定、决策记录与两家的差别。同一次决策调用里还有选话题与档案题，见 [memory.md](memory.md)；插话判断用同一套决策接口单独调用，见 [conversation.md](conversation.md)。

## 模块与流程

| 模块 | 职责 |
| --- | --- |
| `llm/decisions.py` | 与服务商无关的决策接口：一次调用问多道题，题型有选择题和是非题。不 import 任何 SDK |
| `llm/openai_decisions.py`、`llm/gemini_decisions.py` | 两个适配器 |
| `routing.py` | 选模型的核心：组装题目、选择规则、失败时的退路、生成决策记录。不碰 SDK 和数据库 |

流程：用户消息在收消息时就已入库（见 [conversation.md](conversation.md)）。开轮时（`respond()`）先在一个事务里复查授权、取出这一轮的输入与上下文，按本轮附件筛候选（本轮没有可答内容时只发说明、到此为止）；然后在后台发「正在输入」，再做决策（调用前复查授权），然后按选出的模型组装请求，按实际的请求发附件的说明，复查授权后调用模型。决策是联网操作，不在数据库事务里。

一次决策调用里可以有几道题：选模型（题目名 `model`）、选话题（`topic`）、档案题（`profile`）。接口和适配器不区分题目的用途，决策记录按题目名一道题一行。

## 配置

- `[decisions]`：不写这个表就不做决策，始终用默认模型（它不在候选里时用候选里排在最前面的）。字段是 `provider`（必填）、`model`（默认 `gpt-6-luna` / `gemini-decision-1`）、`instructions`（题面）、`timeout_seconds`（默认 3）、`history_turns`（默认 3）、`switch_margin`（默认 0.2）。
- `[[models]]` 的 `description`：一句话说明这个模型适合回答什么样的消息，就是选择题里这个选项的描述。配置了 `[decisions]` 且模型多于一个时必填。
- 配置了 `[decisions]` 时最多 255 个模型，这是两家选择题选项数的共同上限。
- 决策模型与同一家的对话模型共用客户端，`[providers.*]` 的接口地址与代理同样生效。
- 这些默认值都还没有实测依据。

## 选择规则

- 题目的输入是 JSON：最近几轮对话加当前这条消息，只含这个用户自己的内容。每条历史最多 1000 字，当前消息最多 4000 字，超出的部分截断。决策接口收得下的媒体（现在只有 Gemini 收本轮语音的原声）一并交给决策，见[「附件与多模态」](attachments.md)。
- 只在按本轮附件筛出的候选模型里选（见[「附件与多模态」](attachments.md)）。候选只有一个时不问选模型这道题；选话题、档案题也都不问时整次不调用决策。
- 取概率最高的模型。它和这个用户上一轮实际回答的模型不同时，只有高出至少 `switch_margin` 才换，否则沿用上一轮的；上一轮的模型不在候选里时这条不适用。
- 「上一轮实际回答的模型」取最近一条有文字送达的回复；只发了固定说明的失败轮次不算。
- 任何失败（超时、网络、HTTP 错误、拒答、安全拦截、坏响应）都不挡住回复：沿用上一轮的模型（它不在候选里时当作没有），没有上一轮就用默认模型（它也不在候选里时用候选里排在最前面的）。
- 选出的模型调用失败时，换它自己配置的 `fallback`。
- 决策最长要等 `timeout_seconds`，所以决策返回后、调用对话模型之前会再确认一次授权；这时已不能使用的，不调用对话模型，也不再发任何东西，已经发生的决策照常记账。

决策返回后的授权复查与真正启动对话模型之间仍有一个极小的窗口：管理员的 `/disable` 恰好在这一瞬间提交时，模型仍会启动。它与「停用发生在模型启动后的一瞬间」无法区分，消除它要让管理命令等待进行中的对话，所以接受。

## 坏响应的判定

两家 SDK 都不校验响应，还会做宽松的转换（漏掉题型时自动补上，布尔值的概率转成 1.0 / 0.0），所以适配器经原始响应接口（`with_raw_response`）拿到响应体，直接按原始 JSON 校验，逐题判定：

- **整次的坏响应**：整体结构不对（答案不是数组或对象、缺题、多出不认识的题、重名）时整次失败（`MALFORMED`），这次调用里的每道题都走各自的退路。
- **单道题的坏答案**：某一道题的题型对不上、选项缺了、重复或多出题目里没有的取值、概率不是 0 到 1 之间的数字、各选项的概率之和与 1 相差超过 0.02（`PROBABILITY_SUM_TOLERANCE`），只把那一道标成 `Malformed`，只有它记失败、走它的退路，同一次调用里的其它题照常用。
- 每一道题都坏时按整次的坏响应抛错，所以只问一道题时，它坏了就是整次失败。
- **拒答与拦截**：OpenAI 的拒答是逐题的（单道题返回 `refusal`，记成 `Refusal`），只有那道题走它的退路；Gemini 没有逐题的拒答，安全拦截（HTTP 400 的安全类错误码，或响应里带 `prompt_feedback.block_reason`）让整次调用按 `BLOCKED` 失败。

## 用量

用量的数字不可信时记空：不是整数、是负数，或单次调用超过 10 亿（`MAX_TOKENS_PER_CALL`）的 token 数，一律当作服务商没有报告，免得写库出错连带回滚整轮的记录。对话和决策两条路径都是如此；Gemini 的输出与思考用量先逐项检查再相加，无效的那一项按未报告处理，用量的问题不会让回答失败。`/usage` 用 SQLite 的 `total()` 汇总，即使库里有绕过检查的异常大数也不会溢出。

## 记录

- `decisions` 表每次决策调用每道题一行：属于哪条用户消息、题目名、服务商与模型、各选项的概率、最终选了谁、是否因 `switch_margin` 沿用了上一轮、耗时、失败时的错误分类。不记题目的输入文本。
- 用量表的 `purpose` 列区分用途，决策调用是 `decision`。`/usage` 的概要合计所有用途，明细里决策单列一行，见[「接入与授权」](access.md)。

## 两家的差别

由适配器抹平：

| | OpenAI | Gemini |
| --- | --- | --- |
| 调用 | `client.decisions.with_raw_response.create(...)` | `client.aio.decisions.with_raw_response.create(..., api_version="v1beta")` |
| 题目 | 带 `name` 的数组；是非题叫 `predicate` | 以题目名为键的对象；是非题叫 `noul` |
| 选项 | `choices: [{value, description}]` | `criteria: {取值: 描述}` |
| 输入里的媒体 | 不收 | 收 WAV（现在只用于本轮语音的原声） |
| 拒答与拦截 | 单道题返回 `refusal`，其它题照常有答案 | 安全拦截返回 HTTP 400，或响应里带 `prompt_feedback.block_reason` |

Gemini 的 Decisions 在 `v1beta` 下，而对话用的 Interactions 在 `v1` 下，所以决策调用单独指定了接口版本。

## 实测记录（2026-11-18）

两家各连发 5 次同一道选模型的题：

| 模型 | 耗时（最小 / 中位数 / 最大） | 概率 | 概率之和 | 输入 token |
| --- | --- | --- | --- | --- |
| `gpt-6-luna` | 205 / 227 / 1328 毫秒 | solve 1.000，support 0.000 | 1.0000 | 284 |
| `gemini-decision-1` | 225 / 332 / 440 毫秒 | solve 0.987，support 0.013 | 1.0000 | 245 |

- 题目是先倾诉工作压力、最后一句问 Python 排序，两家都按最后一句选了「解决问题」，五次结果完全一致。
- OpenAI 的第一次是 1.3 秒，之后都在 0.2 秒左右，应是首次建立连接的开销；机器人里客户端常驻复用，平时应接近后者，但空闲久了连接断开后的第一条消息仍会慢一些。默认的 3 秒时限两家都绰绰有余。
- 两家的概率之和都是 1，`PROBABILITY_SUM_TOLERANCE` 的 0.02 不会误伤正常结果。
- 两家都没有输出 token，与文档一致。
