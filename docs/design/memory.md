# 记忆

每个用户的记忆怎样存、怎样组装进上下文、怎样查看与遗忘：总体设计，留给以后的口子，话题线（里程碑 6a），用户档案、查看记忆与遗忘（里程碑 6b）。

每个用户存三样东西：

- **消息流水**：所有消息原样追加，是唯一的事实来源。
- **话题线**：自动划分的隐式 session，每条有标题、一段摘要和最近活跃时间。
- **用户档案**：几百字的稳定事实，如称呼、偏好、重要的人和事。

每轮的决策调用问两道题：

- **用哪类模型**：选项是配置里的模型列表，每项带一句类别描述。
- **属于哪条话题线**：选项是候选话题线的标题与一句话摘要，外加「新话题」。

Decisions 返回每个选项的概率，上下文按概率组装：

| 内容 | 何时带上 | 形式 |
| --- | --- | --- |
| 用户档案、话题目录（只有标题） | 每次 | 短文本，让模型知道别的话题存在 |
| 全局最近几轮 | 每次 | 原文，兜住「它」「刚才那个」这类指代 |
| 概率最高的话题线 | 每次 | 摘要加该话题最近若干轮原文 |
| 概率次高、超过阈值的话题线 | 拿不准时 | 只带摘要 |

这样一轮的上下文约 5k–8k token。几个候选模型的窗口都在 100 万 token 上下，限制不在窗口而在费用，所以不把整段历史都带上。

Decisions 只能选、不能写。新话题的标题、话题摘要和档案更新交给后台的小模型，在回复之后做，不占用户等待的时间。

用户引用旧消息或机器人的某条气泡时，pyqbot 给出被引用消息的索引（`message.ref_msg_idx`），`msg_elements` 里带回被引用的内容，可以直接定位话题，不必靠猜（见[「按引用定位」](#按引用定位)）。

## 留给以后的口子

为以后的拓展守住五条：

- **流水只追加，其余都是可重建的派生数据。** 话题归属、摘要、档案、文字版都能从流水重新算出来，以后换提示词、阈值或算法时可以对历史重跑。唯一的例外是用户要求遗忘：对应的流水要彻底删除，再重建受影响的摘要和档案。
- **每轮存一条决策记录**：候选、各选项的概率、最终选择、带了哪些上下文、耗时与 token。效果不好时靠它查原因，延迟实测的数据也从这里来。
- **三个接口**：决策、对话模型、语音转写，SDK 隔在接口后面。「生成候选话题」与「在候选里选」分成两步，以后可以给前一步加关键词或向量召回。
- **一次回复是若干段内容，不是一个字符串。** 现在只有文字，以后可以加语音或图片形式的回复（图片见[里程碑 10](image-generation.md)）。
- **工具不一定在本地执行。** 联网搜索由服务商在它那边执行，工具调用的流程不能假设每个工具都有本地的处理函数。

## 话题线

里程碑 6a。

### 启用与模块

- **只在配置了 `[decisions]` 时启用。** 不配就不分话题，上下文是最近 `[chat].history_turns` 轮。`Router(..., topics=settings.topics)`，没有 `[decisions]` 或没有决策模型时 `Router.topics` 为空，`Conversation` 据此判断是否分话题，不另设开关。启用后即使只有一个模型，也会为话题题调用决策。
- 模块：`topics.py` 是话题表与归属的数据层（候选、按引用定位、建行与归属、`set_summary()`）；话题里各轮的原文由 `journal.topic_history()` 取；选话题在 `routing.py`（`TopicQuery`、`choose_topic()`），与选模型同一个 `Selection`；合并历史在 `context.merge_history()`，记忆一段在 `prompt.Memory`；后台写标题与摘要在 `memory.py`。
- 表（迁移 V9）：`messages.ref_msg_idx`（被引用消息的引用索引，按 `(user_id, msg_idx)` 建了索引）；`topics`（`provisional_title`、`title`、`summary`、`summarized_through`、`created_at`、`active_at`、`last_message_id`）与 `topic_messages`（消息 → 话题，带 `user_id`）；机器人各条气泡的引用索引在发送记录 `sends`（迁移 V19，按 `(user_id, ref_idx)` 建了索引）。「最近活跃」按 `last_message_id`（归进来的最后一轮的回复编号）排序，不按时刻：时钟可能回拨，同一秒里也会有好几轮。
- 日志只记话题编号与概率，不记标题与摘要。

### 选话题

- **候选话题**：这个用户最近活跃的 `[topics].candidates` 条（默认 20），外加「新话题」。更久以前的话题会被判成新话题，以后再加关键词或向量召回。一条候选也没有时不问，直接开新话题。
- **一次决策问两道题**：选模型与选话题放在同一次 Decisions 调用里，共用 `[decisions].timeout_seconds`。插话判断仍然单独做。题目的输入与选模型共用（最近 `[decisions].history_turns` 轮加当前消息），最近几轮对话每条标上所在话题的编号。
- **选项**：取值是话题编号（十进制）与 `new`，描述是「标题：摘要的前 120 字」（压成一行，没有摘要时只有标题；标题用 `Topic.display_title`，有正式标题用它，没有用临时标题）；题面是 `routing.TOPIC_INSTRUCTIONS`。两家的官方文档都没有对选项描述设实际的长度上限（OpenAI 的字段上限是 1 MiB；Gemini 没写，受 262,144 token 的总上下文约束），120 字只为控制费用。
- **话题题失败**（超时、拒答、拦截、坏响应）：沿用这个用户最近活跃的话题；一条都没有就开新话题。坏响应逐题判定：某一道题的答案不合法只让那一道走退路，其余照常；只有整次失败时各道题才记同一个错误。判定规则见[「选模型」的「坏响应的判定」](model-routing.md#坏响应的判定)。
- **第二可能的话题**：除选中的以外概率最高的已有话题（不含「新话题」）；选中「新话题」时就是概率最高的已有话题。
- **决策记录**：话题题一行，题目名 `topic`，`probabilities` 的键是话题编号与 `new`，`chosen` 同理；话题题失败时 `chosen` 是退回的话题。同一次调用的几道题共用一行决策用量。被取消时问了的题各记一行 `cancelled`。

### 按引用定位

- 用户引用了自己的旧消息或机器人回复他的某条气泡时，只在这个用户自己的数据里找被引用的那条：他自己的消息按用户消息的 `msg_idx` 找，机器人的气泡按发送记录的引用索引找（见[「对话」的「发送记录」](conversation.md#发送记录)）。找到且有话题，就直接用那个话题，话题题不问（模型题照问）。拿不到索引的气泡定位不了，照常交给决策。
- **引用的来源**（已实测，见 pyqbot 的 `docs/errata.md`）：先取 pyqbot 的 `message.ref_msg_idx`（`message_scene.ext` 里的 `ref_msg_idx=`），没有时由本项目回退到 `msg_elements` 第一项的 `msg_idx`（pyqbot 不做这个回退）；超过 512 个字符的当作没有。实测四次都对上：引用机器人的普通消息时 `ref_msg_idx` 等于发送结果的 `ext_info.ref_idx`，引用流式消息时等于 `StreamMessage.ref_idx`，引用用户自己的消息时等于那条消息的 `msg_idx`；`msg_elements` 只有被引用的那一项，它的 `msg_idx` 与 `ref_msg_idx` 相同，所以回退只是兜底。一轮里有几条消息带引用时，从最新的一条看起，第一个找得到话题的为准。
- **机器人回复的索引**：这一轮的每条被动回复（过程消息、回答的每一条、改发的纯文本、固定说明、提醒列表、确认卡片、生成的图）各在发送记录里记一行，带它自己的引用索引；回复行不存（`messages.msg_idx` 只是用户消息的）。流式消息取 `StreamMessage.ref_idx`（pyqbot 实测：每个分片的响应，含结束分片，都带同一个 `ext_info.ref_idx`；仍在每个成功的分片与结束分片之后都看一次，第一个不为空的为准），普通消息（纯文本、Markdown、带按钮的 Markdown、图片）取发送结果的 `ext_info.ref_idx`；拿不到就留空，超过 512 个字符的也当作没有。`conversation.ReplyChannel` 的各个发送方法与过程消息的 `ReplyStream` 都返回发出的那条消息的引用索引（替身返回 `None` 即可），`conversation.py` 不依赖 pyqbot。
- **从气泡到话题**：按引用索引找到发送记录所属的回复行，取回复行的话题；回复行没有归属时（没有结束的一轮，例如只显示了过程消息就关停，它的消息并进了下一轮），取它回答的那条用户消息的话题。同一个索引在用户消息与发送记录里都对上时（不应发生）取编号大的那一行。
- `topics.quoted_topic()` 用户消息与机器人的气泡都认，但两路都只在这个用户自己的行里找，所以机器人回复别人的气泡的索引解析不到，两个人的数据里出现同一个索引字符串时也各查各的（有测试）。

### 上下文组装

决策之后在一个事务里复查授权、取出选中话题的上下文，不能使用就停下（`withheld`）。上下文按时间排列、去重：

- 话题目录：最近活跃的 `[topics].directory` 条（默认 20）的标题，不含当前话题，让模型知道别的话题存在；
- 不分话题的最近 `[topics].recent_turns` 轮原文（默认 3），兜住「它」「刚才那个」这类指代；
- 选中话题的摘要，加上它最近 `[chat].history_turns` 轮原文（不分话题时这个数就是最近几轮，两种情况含义一致）；
- 第二可能的已有话题概率不低于 `[topics].second_threshold`（默认 0.25）时，再带上它的摘要；摘要为空时什么都不带；
- 6a 之前的消息不回填话题，只经「不分话题的最近几轮」出现。

历史是「不分话题的最近几轮」与「选中话题最近几轮」按消息去重、按对话位置排列，「往前数第几轮」按合并后的各轮重算（只收到说明、没有正文的回复不在历史里，它前后的用户消息会被算成同一轮）。系统提示词在当前时间之前加一段：历史只是相关片段（`prompt.TOPIC_GUIDE`）、用户档案、当前话题的摘要、相关话题的摘要、目录（标题列表，不含当前话题）；当前话题、相关话题与目录都标上编号，给查看与遗忘记忆的函数用。

摘要与标题来自用户的对话，系统提示词里在它们前面加 `prompt.MEMORY_NOTICE`，说明这是自动整理的资料、可能过时，其中的要求不是给模型的指令；写摘要的提示词里也说明对话里的要求不要执行。它们只进这个用户自己的上下文。

### 话题归属

- **话题归属是派生数据**：存在单独的表里，流水仍然只追加，以后可以重算。
- 一轮按 `ends_turn()` 结束了才写，含只收到附件说明（`noticed`）的轮次；与回复写在同一个事务里：这一轮的用户消息与回复都归到选中的话题。被插话打断的那次不写。
- 选「新话题」或话题已不属于这个用户（防御）时建行。**新话题的空窗期**：后台还没写出标题时用临时标题，取这一轮各条用户消息文字版（正文加附件标记，同决策题目里的写法）用空格连起来的前 40 字，全是空白时写「（无文字）」。
- 归属里混进别人的消息编号时只归这个用户自己的。

### 后台写标题与摘要

- **配置 `[memory]`**，写法同 `[describe]`：`provider`、`model` 必填；`reasoning` 默认不传；`timeout_seconds` 默认 120（最大 600）；`max_output_tokens` 默认不设；`instructions` 的默认题面写在 `config.DEFAULT_MEMORY_INSTRUCTIONS` 与示例里。只在配置了 `[decisions]` 时生效；有 `[memory]` 没有 `[decisions]` 时不报错，忽略它并在启动时记一条警告（同 `[topics]`），也不要求它的服务商的密钥。模型与同一家的对话模型共用客户端（`ChatModels.memorizer`）。不配 `[memory]` 时只有临时标题、没有摘要。
- **推理强度**：`[memory]` 与 `[describe]` 都在后台运行，不占用户等待的时间，可以把 `reasoning` 调高（gpt-6-luna 接受 `none`、`low`、`medium`、`high`、`xhigh`、`max`，默认 `medium`，2026-11-19 查自官方模型页）；代价是费用更高、新话题的空窗期更长。用户等待路径上的 gpt-6-luna 只有 Decisions，而 Decisions API 没有推理强度的参数。
- **模块** `memory.py`（`Summarizer`），写法照 `describe.py`：后台任务、真正调用之前在事务里复查授权、受保护的记账、`stop()` / `aclose()` 收尾。接在 `__main__.py` 的关停顺序里，与 `Describer` 并列（第 7、8 步，见[「关停顺序」](conversation.md#关停顺序)）。关停只取消一次：`aclose()` 在已经 `stop()` 过时只等待、不再取消，免得打断模型响应流被第一次取消后的异步关闭；`Describer.aclose()` 同样如此。
- **排队**：每轮结束后在后台更新这一轮话题的标题与摘要。每个用户一个后台任务，依次处理排着的话题（按排的顺序、不重复）；正在写的话题又排进来，写完后再写一次；整个进程同时最多 `memory.CONCURRENCY`（2）个调用。只有正常结束（没有被取消）、写了归属的一轮才排。
- **输入**：旧的标题与摘要，加上次摘要之后的各轮文字版，写成 JSON（`title`、`summary`、`turns`）。`turns` 里用户消息是正文加附件的 `text`，回复是 `content`，只发了说明的回复不带；最多最近 20 轮，每条最多 2000 字，合计最多 12000 字，超出时丢掉更早的。没有新的轮次就不调用。
- **按轮次取**（`journal.topic_turns_after()`）：`summarized_through` 记的是覆盖到的那一轮的回复，下一次取回复编号更大的那些轮，带上它们各自 `reply_to` 覆盖的用户消息，不论用户消息的编号大小。不按消息编号取：回答进行中发来的下一轮问题编号比上一轮的回复小（问1、问2、答1、答2），只按消息编号取会漏掉问2。只发了说明的回复照样是轮次的边界，它的问题照常带上。覆盖范围推进到这次带上的各轮里最大的回复编号，所以超出上限被丢掉的更早轮次之后不会补写。
- **输出**：约定的两行纯文本「标题：……」「摘要：……」（摘要可以折行，压成一行），没有用结构化输出（对话接口没有这个参数）。标题超过 40 字、摘要超过 600 字（提示词建议的两倍）、缺一行、空白、模型没有正常写完（`FinishReason` 不是 completed）都按失败处理：只记日志，保留旧值，覆盖范围不动，下次带着更多轮重试。
- **写回** `topics.set_summary()`（覆盖范围只前进）。用量一行，用途 `memory`、`model` 列是 `memory`，挂在输入里最后一条用户消息上；迁移 V10 按 SQLite 的做法重建用量表，把 `memory` 加进 `purpose` 的 CHECK 约束（保留第 7 版的 `searches`）。
- 日志只记话题编号、字数与覆盖的消息条数，不记标题与摘要。

### 后台任务的输出上限

后台任务默认不设输出上限：后台用 gpt-6-luna 的任务几乎不花钱。`[describe]` 的 `max_output_tokens`、`file_max_output_tokens` 与 `[memory]` 的 `max_output_tokens` 都是可选的，不写就不向服务商传（`llm.ChatRequest.max_output_tokens` 可以为空，OpenAI 不带 `max_output_tokens`，Gemini 的 `generation_config` 里不带 `max_output_tokens`），由模型自己的上限兜底，失控时由 `timeout_seconds` 兜底；写了才传，含推理所用的 token。`[chat].max_output_tokens` 同样默认不设，见[「对话的输出上限与时限」](conversation.md#对话的输出上限与时限)。

## 用户档案

里程碑 6b 的一部分，模块是 `profiles.py`（数据层）、`memory.py`（后台重写）、`routing.py`（档案题）。和话题线一样，只在配置了 `[decisions]` 与 `[memory]` 时启用。

- **表** `profiles`（每个用户一行，迁移 V13 建、V15 重建）：内容、更新时间与版本号 `version`。版本号每次修改都推进，删除后也保留：删除是内容置空、版本加一。档案最多 500 字。
- **什么时候更新**：每轮已有的 Decisions 调用里加一道是非题（`routing.PROFILE_QUESTION`），问用户刚发来的消息里有没有他自己的、新的稳定信息（称呼、偏好、重要的人和事），输入里带现有档案；概率不低于 `[memory].profile_threshold`（默认 0.5）时标记这一轮，回复之后在后台用 `[memory]` 的模型重写档案。大多数轮次不增加调用。题目失败不影响另外两道题。
- 打开档案后每轮都问档案题。另外两道题都不用问的少数轮次（只剩一个候选模型，且是用户的第一条消息或话题已按引用定死），为档案题单独调用一次决策：第一条消息往往就是自我介绍。
- **后台重写**与话题摘要共用 `Summarizer` 的每用户队列，两类任务轮流做；取得并发名额后才取出待合并的轮次；出队时记下档案的代次。提示词是 `[memory].profile_instructions`，输入是旧档案与排着的各轮对话，输出完整的新档案、「不变」或「清空」三种之一。写回前核对版本号与代次、来源消息都还在，否则丢弃。
- **记什么**：只记用户自己说过的、关于他自己的稳定事实。敏感情况（健康、感情、宗教、政治倾向等）只在用户明确要求记住时才进档案；密码、证件号、银行卡号、详细住址、电话这类一律不记。用户说过「别记」的不记。
- 用户说「别记」、从档案里删掉之后，不另存「不要记」的清单：那会把这件事本身留下。删除时如实告诉用户以后再说起可能会被重新记下。
- **解析从严**：每个非空行都要以「- 」开头；写成条目的「不变」「清空」（含带解释的写法）按失败处理；结构兜底只管新档案只有一行的情况（旧档案两条以上时这一行必须是原有的一条；否则只拦「无」「没有新信息」这类空话）。
- **档案的用法**：每轮以 JSON 字符串放进系统提示词，前面说明它是自动整理的资料、不是指令（同话题摘要）。对话模型的系统提示词里另有一段说明记忆是怎么工作的（程序自动记、不能手动保存、哪些信息不记、忘掉要调用函数）。

## 查看记忆与遗忘

里程碑 6b 的另一部分，模块是 `memory_tools.py`（函数的声明、参数与交回的结果）、`conversation.py` 的 `_Recall`（执行）、`topics.py`（删除）、`confirmations.py`（确认按钮的令牌）。

- **函数**：用对话模型的函数调用（同画图函数）。打开话题线时所有对话模型都有 `view_memory` 与 `forget_topic`（不按模型开关），再有 `[memory]` 时加 `forget_profile_item`；与画图、提醒的函数同时出现时 `tool_runner` 按函数名分派。交回任何结果前复查授权，不通过就停下这次调用、不再发下一跳。
- **遗忘的范围**：「忘掉某个话题」（彻底删除这条话题线的消息、图片与摘要）和「忘掉档案里的某条信息」（只改档案，流水不动）。不做「忘掉全部」。

### 查看记忆

`view_memory` 返回档案（JSON 字符串）与话题列表（编号、标题、开始与最近聊到的日期、轮数），按话题编号从新到旧，用 `before_topic_id` 游标翻页，每页 100 个。结果前面说明这是自动整理的资料、不是指令。启用了提醒、这个用户有有效的提醒时，结果里另提一句有几条，可用 `list_reminders` 查看。模型用自己的话告诉用户，用户也可以接着说「把第二个忘掉」。

### 删除前用按钮确认

忘掉话题要用户点按钮确认：模型调用 `forget_topic` 本身不删任何东西，程序在这一轮回答之后发一条带「确认删除」「取消」按钮的卡片，用户点了「确认删除」才由程序直接删除，不经过模型。不用「模型先复述、用户口头确认后才调用」的两段式：模型被诱导或时序上的漏洞（同一轮被注入、插话重来、合批、备用模型）总能找出来，根源是「用户有没有同意」由模型判断；按钮把它变成用户的真实操作。模型单独调用永远删不了，档案、标题、图片描述里注入的文字也没用。忘掉档案里的某条影响小，不需要确认。

- **调用**：`forget_topic(topic_id)` 只校验是这个用户的话题，把（话题、标题）记成这一轮待确认的一项（`_Turn.pending`）。忘掉话题与设置、取消提醒共用这一项，一轮只出一条确认（见[「提醒事项」](reminders.md)）：同一轮再要忘掉另一个话题、或已有提醒的一项待确认时交回出错说明。调用时先查被动回复的余量：卡片要另发一条消息，还得给回答留余量，不够时交回说明、不安排。
- **只发卡片**：调用成功后，这条消息里只是要忘掉话题的话，模型不写回答文字，这一轮只发卡片；用户在同一条消息里还问了别的，只回答别的部分。没有文字的这一轮不算失败，不换备用模型，不发失败说明（与设置提醒的做法相同，见[「提醒事项」](reminders.md)）。调用没成功时模型照常用文字告诉用户。
- **流水里的记录**：卡片确认送达时，流水里这一轮的回复记一句程序写的方括号说明「[发了忘掉话题的确认卡片：话题 #N「标题」]」（`memory_tools.card_note()`），另起一行接在回答文字后面，没有文字时整条回复只有它。系统提示词告诉模型这种说明是系统记下的，它自己不要写；按钮消息和用户点了哪个按钮模型都看不到，用户问删了没有时调用 `view_memory` 看话题还在不在。
- **卡片的时机**：这一轮回答结束之后、记账之前发，与提醒的列表与卡片同一个时机，理由见[「提醒事项」](reminders.md)；只在这一轮会结束时发：没有结束的一轮会被并进下一轮，确认后删不干净。插话重来、取消、出错时不发。发之前在一个事务里复查授权（停用了就不发）并取这个用户有效提醒的条数。
- **卡片的内容**：对这一轮回复挂的那条用户消息发 Markdown 加两个回调按钮（数据分别以 `forget:`、`keep:` 开头，后接随机令牌）。写明要忘掉的话题编号与标题（标题经 `texts.escape_markdown()`）、会删掉这个话题里的全部对话、图片与摘要连同提出要求的这一轮、删了找不回来、按钮 10 分钟内有效。这个用户在库里有有效的提醒时，另起一段写「相关的提醒不会一起删。」：这一轮模型不写文字，只能写在卡片上；只看库里有没有有效提醒，不看 `[reminders]` 开没开，关掉时提醒仍在库里，重新打开后会接着发。模型拿到的函数结果里同样说明提醒不属于话题（启用了提醒、且这个用户有有效的提醒时），还有档案不保证跟着改（有 `[memory]` 时）。
- **令牌**（`confirmations.TokenRegistry`）：只在内存里、10 分钟（单调时钟）、只能用一次，重启就失效；记下用户、openid、话题与这一轮的用户消息。按钮被平台拒发时作废令牌，余量还够时补一句纯文字说明；送达说不准时令牌照旧有效。
- **点按钮**：`bot.py` 的 `on_interaction` 把确认按钮交给 `Conversation.press_button`，按 openid 找到用户（找不到不处理），在这个用户的锁里处理整次点击（与他的轮次和流式回复串行）。点的人与令牌记下的用户不符时只记日志，不回复、不处理，令牌照旧有效；令牌失效（过期、点过、重启过）时请用户再说一次。点「取消」什么都不删。
- **确认删除**：一个事务里删掉话题、提出要求那一轮的用户消息与回复（不论在哪个话题：这一轮的消息往往就属于要忘掉的话题，包括「忘掉它」这句本身）、因此变空的话题；仍有消息的受影响话题清掉摘要与正式标题、按剩下的第一条用户消息重取临时标题、重算最近活跃位置，并排摘要重写；用量与决策只断开引用。话题已经不在时照样删掉那一轮的消息。之后后台删附件文件、做 WAL 截断（被别的读者挡住时退避重试 3 次）；有档案且话题有摘要时，把摘要排进后台，尽量从档案里去掉只来自这条话题的信息（`Summarizer.schedule_profile_forget()`），这个后台任务调用模型前照旧复查授权。删除本身不看授权：这是用户自己的数据。

### 忘掉档案里的某条

`forget_profile_item(item)` 同步调用 `[memory]` 的模型，把档案按行编号交给它，它只输出要删的行号或「没有」，程序只删这些行、其余原样保留，按版本号写回，交回真实的结果（删掉了、本来就没有、失败、调用期间被改过）。复查授权后先作废这个用户排队与在途的档案更新。调用过它的一轮不再排整份档案重写：重写会绕过按行删除。

### 删干净

- 迁移 V14 把 `messages`、`attachments`、`topics` 改成 `AUTOINCREMENT`，删除后编号不再复用：否则后台写回可能落到复用了编号、属于另一个用户的新行上。V15 另建删除时外键要查的四个索引。
- 数据库连接打开 `secure_delete`，删除后做一次 WAL 检查点，免得删掉的内容留在文件里。备份里仍有旧数据，最多再留 `[backup].keep × interval_hours`（默认 7 天，见[「部署」的「备份」](deployment.md#备份)）。
