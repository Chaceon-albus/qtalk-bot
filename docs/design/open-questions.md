# 待定与薄弱处

还没定做法的事与已知的薄弱处。这里的内容实现到相应部分时先和用户确认。

## 其它待定

- **配额的具体规则**：每个用户的每日上限、全局预算。工具执行时的用户身份取自当前会话，不取模型给的参数。
- **时间感**：上下文里标注当前时间，以及距上次对话过了多久。
- **数据去留**：用户删除好友后数据保留多久，附件的磁盘清理。
- **情感类的风险处置**：涉及自伤等内容时走固定的模型与回应方式，不交给路由决定。
- **每个模型类别各自的上下文组装方式**：情感陪伴更依赖档案和最近的对话，不像一个个话题。
- **提示词**放在 TOML 里还是独立文件。
- **`/users`、`/invites` 的分页**：现在把全部结果拼成一条消息，用户多了会超出单条消息的长度。
- **pyqbot 可以改进的地方**（用户维护 pyqbot，改了之后这边相应简化）。下面几条 pyqbot 已在 main 上加好（提交 1bbc056..0cc674d），这边已经改用：
  - 已完成：QQ 侧的代理参数。`[qq].proxy` 传给 `pyqbot.Bot(proxy=...)`，作用于接口、网关与附件下载。
  - 已完成：「平台明确拒绝」的标志。`bot.is_rejection()` 改用 `QQBotError.outcome_unknown`（见[里程碑 2](access.md#里程碑-2-定下的细节)），不再按 pyqbot 的实现推断。
  - 已完成：只断开网关的 `Bot.stop()`。关停改为先停收事件，见 [5b 的「关停顺序」](conversation.md#里程碑-5b-定下的细节)。
  - 已完成：公开导出 `MessageElement`、`ArkData` 等。`bot.py` 删掉了按结构匹配的 Protocol，直接用 pyqbot 的类型。
  - 已完成：收到的消息带 `ref_msg_idx`、流式消息带 `ref_idx`。本项目不再自己解析 `message_scene.ext`，并能按引用定位到机器人的回复（见[里程碑 6a](memory.md#里程碑-6a-定下的细节)）。
  - 现状，不改：流式消息的「已确认送达的文字」（`StreamMessage.sent_text`）。`conversation._Outbox` 仍自己逐片发送、记录送达的内容：`conversation.py` 不依赖 pyqbot、要对替身同样成立；它仍要在第一片之前 `claim()`、送达不明时立即停读，还要把回答与接在后面的固定说明分开，改用 `sent_text` 省不掉这些，只会让每个替身多实现一个属性。
  - 以后再说：附件下载的 DNS 重绑定，见[里程碑 5a 的「已知的限制」](attachments.md#里程碑-5a-定下的细节)。

## 已知的薄弱处

都还没有定做法，实现到相应部分时先和用户确认：

1. **候选话题从哪来**：选择题最多 255 个选项，实际只会列最近几十条，很久以前的话题会被判成「新话题」。已定，见[里程碑 6a](memory.md#里程碑-6a-定下的细节)。
2. **新话题的空窗期**：后台还没写出标题和摘要时，下一条消息认不出这条话题。已定先用首条消息的开头当临时标题，见[里程碑 6a](memory.md#里程碑-6a-定下的细节)。
3. **决策调用失败或被拦**：超时、安全拦截、拒答都可能发生，情感类内容最容易触发。选模型这道题已在里程碑 4 处理（硬超时，失败就沿用上一轮的模型）；话题那道题的退路见[里程碑 6a](memory.md#里程碑-6a-定下的细节)。
4. **流水里记什么**：平台可能拒发或流式中途失败，要记用户实际看到的内容，而不是模型生成的内容。
5. **模型来回切换**：两个模型交替回答会像换了个人。已在里程碑 3、4 处理：各模型共用人设，切换要求概率有明显差距（`switch_margin`），跨服务商的历史只存纯文本。
6. **连发消息**：攒批的等待可以和决策调用同时进行；期间来了新消息就取消重来，生成过程中来的排到下一轮。
7. **重复推送**：平台可能重复推送同一条消息，pyqbot 不去重。已在里程碑 2 处理，见[「里程碑 2 定下的细节」](access.md#里程碑-2-定下的细节)。
8. **流式消息进行中给同一个用户的其它回复**：平台会因此提前结束正在写的流式消息（pyqbot 实测，40034019）。已处理：这个用户有一轮正在回答时，排队时的那句收到、不支持的内容（视频、卡片等）的「暂不支持」、Gate 的回复（管理员命令等）都回在那一轮回复挂的那条消息上，计进它的被动回复次数；是否在回答在真正发送的那一刻判断（「暂不支持」要先下载、复查授权）。那条消息的次数不够给兜底留余量时，「暂不支持」与 Gate 的回复退回回给新消息（可能截断回答，但不丢回复），记日志。一条 Gate 回复链逐条判断，发到一半时回答结束的，后面几条回给新消息。没有处理的竞态（评审指出）：这类回复的请求在途时（回给新消息，或回给上一轮的消息）下一轮已经开始流式回复，它晚到会把那一轮的流式消息提前结束；要在途好几秒才会发生，结果是那一轮流式被拒、按现有规则全文改发纯文本，内容不丢。排队时的那句收到另有等待（`ACK_WAIT_SECONDS`），不受影响。
